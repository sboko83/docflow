# Как пользоваться docflow

Процесс от идеи до архива: кто что делает, какие команды, что куда пишется.
Формат файлов, команды и коды выхода — [docs/design/](design/README.md); здесь —
порядок работы.

## Установка

### Установить CLI

Требования: macOS или Linux (amd64 или arm64), curl или wget. Go и sudo не
нужны:

~~~bash
curl -fsSL https://raw.githubusercontent.com/sboko83/docflow/main/install.sh | sh
~~~

Установщик определяет OS и архитектуру, скачивает последний релиз, сверяет
sha256 по checksums.txt, распаковывает архив и запускает из него
`docflow install`. Тот укладывает бинарник, скиллы и LICENSE в
`~/.docflow/versions/<X.Y.Z>/`, переключает симлинк `current` и создаёт
`bin/docflow`:

~~~
~/.docflow/
  bin/docflow     -> ../current/docflow
  current         -> versions/<version>
  versions/<version>/docflow
  versions/<version>/skills/<имя>/
  versions/<version>/LICENSE
  last-update-check
~~~

Затем `docflow install` добавляет `~/.docflow/bin` в PATH (блок в
`.zshrc`, `.bashrc` или `.bash_profile`) и ставит личные симлинки скиллов
агентам, чьи CLI найдены в PATH (`claude`, `codex`, `pi`), и в
`~/.zcode/skills`, если существует каталог `~/.zcode`. Симлинки ведут в
`~/.docflow/current/skills/<имя>` и не переписываются при обновлении.

Переменные окружения install.sh: `DOCFLOW_VERSION=X.Y.Z` — поставить
конкретный релиз вместо последнего; `DOCFLOW_RELEASE_URL` — базовый URL
релизов вместо GitHub Releases (по умолчанию
`https://github.com/sboko83/docflow/releases`).

После установки перезапустите оболочку или выполните
`export PATH="$HOME/.docflow/bin:$PATH"` и проверьте версию:

~~~bash
docflow --version
~~~

### Проверить комплект и подключить проект

После установки проверьте комплект для выбранного агента:

~~~bash
docflow doctor --agent codex
~~~

Для Pi укажите --agent pi: личные симлинки лягут в ~/.pi/agent/skills/, а
doctor добавит строку с версией Pi. Для Claude Code опустите --agent: это
цель по умолчанию. Команда
install-skills без --project ставит личные симлинки; --target DIR явно
задаёт другой личный каталог.

В проекте создайте документы docflow:

~~~bash
cd <project>
docflow init --agent codex
~~~

Для Claude Code достаточно docflow init. Чтобы сразу скопировать скиллы в
проект, добавьте --skills, например docflow init --agent codex --skills.
В уже подключённом проекте используйте docflow install-skills --project
--agent codex; для Claude опустите --agent. Проектные копии находятся в
.agents/skills/ для Codex, .pi/skills/ для Pi или .claude/skills/ для Claude и коммитятся вместе
с проектом.

Выберите личную установку для своих проектов или проектные копии для команды.
При одновременной установке одинаковые имена могут отображаться в Codex дважды;
правила приоритета каталогов Claude и Codex различаются —
[каталоги и приоритеты](design/skills.md#установка-скиллов).

`doctor` сравнивает файлы, но не подтверждает обнаружение скиллов агентом.
Для полного комплекта проверьте пять строк `<имя скилла>: ok`;
[коды выхода](design/cli.md#скрипт-docflow) не заменяют чтение этого вывода.

### Обновить CLI и проектные копии

~~~bash
docflow update --check   # только сообщить о новом релизе
docflow update           # скачать и активировать последний релиз
docflow --version
docflow doctor --agent codex
~~~

`docflow update` скачивает последний релиз тем же путём, что и install.sh,
сверяет sha256 и активирует новую версию переключением симлинка `current`:
в `~/.docflow/versions` остаются текущая и предыдущая версии, личные
симлинки скиллов продолжают указывать на `current`. Если нового релиза нет,
команда печатает `up to date`. Переменная `DOCFLOW_RELEASE_URL` действует
и здесь.

Вывод после `updated:` — строка на каждый каталог личных скиллов с числом
ссылок; `(N new)` — ссылки на скиллы, появившиеся в релизе. Сами ссылки не
переписываются: они указывают в `current` и сразу видят новую версию.
Проектные копии (`docflow install-skills --project`) — копии, а не ссылки;
update проверяет только копии проекта, из которого запущен, и печатает для
устаревших команду обновления. Остальные проекты проверяет `docflow doctor`
в их каталоге.

Откат на предыдущую версию — переключить `current` вручную:

~~~bash
ls ~/.docflow/versions                      # текущая и предыдущая
ln -sfn versions/<предыдущая> ~/.docflow/current
docflow --version
~~~

Скиллы откатываются вместе с CLI. Следующий `docflow update` заново скачивает
последний релиз поверх оставшегося каталога этой версии.

При каждом терминальном запуске docflow не чаще раза в сутки проверяет
последний релиз (таймаут 2 секунды) и пишет в stderr строку вида
`docflow 0.4.1 available (current 0.4.0): docflow update`. Отключается
переменной `DOCFLOW_NO_UPDATE_CHECK=1`.

Удаление standalone-установки:

~~~bash
docflow uninstall
~~~

Команда убирает `~/.docflow`, свой блок PATH из профилей оболочки и личные
симлинки скиллов, ведущие в `~/.docflow`; проектные копии скиллов и чужие
файлы не трогает.

В каждом проекте обновите принадлежащие docflow копии скиллов:

~~~bash
cd <project>
docflow install-skills --project --agent codex
docflow doctor --agent codex
~~~

Для Claude опустите --agent. Обновление заменяет содержимое распознанных
копий скиллов. Сохраните или просмотрите локальные правки проектной копии
до этого шага; чужие каталоги и симлинки установщик оставляет без
изменений и сообщает о конфликте.

### Режим разработки

Разработка ведётся из checkout репозитория (нужны Go 1.24+ и git):

~~~bash
git clone https://github.com/sboko83/docflow bsv-docflow
cd bsv-docflow
bash tools/install-dev.sh --dry-run
bash tools/install-dev.sh
~~~

Скрипт проверяет исходники, собирает bin/docflow, создаёт симлинк в
выбранном каталоге (`~/.local/bin` по умолчанию; другой — через `--bin-dir
DIR`) и ставит скиллы агентам, чьи CLI найдены в PATH (`claude`, `codex`,
`pi`), а также в `~/.zcode/skills`, если существует каталог `~/.zcode`.
Флаг `--no-skills` пропускает установку скиллов, `--dry-run` печатает план,
ничего не меняя. Скрипт не меняет PATH: если каталог не найден в PATH, он
напечатает команду для добавления в профиль оболочки. Сохраните checkout
на месте, пока используете CLI: симлинк ведёт в него.

`docflow update` и `docflow uninstall` в dev-сборке отказывают.
Обновление — переключить чистый checkout на новый тег и повторить
установщик; сначала проверьте локальные изменения и сохраните их отдельно,
не сбрасывая:

~~~bash
cd bsv-docflow
git status --short
git fetch --tags origin
git checkout vX.Y.Z
bash tools/install-dev.sh
docflow --version
docflow doctor --agent codex
~~~

Если личные скиллы ставились через произвольный `--target DIR` вне
`~/.zcode/skills`, повторите установку вручную командой
`docflow install-skills --target DIR`.

### Отдельное применение скиллов и Ruleblend

bsv-docs и bsv-changelog работают отдельно от docflow и подходят проектам без
docs/docflow.md. Три скилла bsv-docflow-* описывают процесс планирования,
исполнения и закрытия планов. Правила языка, релиза, коммитов и структуры
конкретного проекта имеют приоритет.

Ruleblend необязателен. Если используете его, импортируйте скиллы
git-импортом этого GitHub-репозитория. Ruleblend читает закоммиченный HEAD;
выбирайте тег как источник, не создавая отдельную копию скиллов.

## Подключение проекта

```bash
cd <project>
docflow init
```

- Создаёт `docs/docflow.md` (очередь, backlog), `docs/plans/`,
  `docs/archive/` и строку в `AGENTS.md`:
  `Plans: docflow (run docflow status), not the bsv-docs PLAN genre`.
- Существующий проект переводится только явно. Старый `docs/PLAN.md`
  после перевода не ведётся: открытые задачи — строками в Backlog.
- Architecture проекта (`docs/architecture.md` или что названо в AGENTS.md)
  остаётся: в ней текущее устройство и ссылки на `docs/archive/`.
- Стартовое чтение — необязательные ключи `docs/docflow.md`: `start_read`
  (пути и `path#anchor` через запятую, что читать в начале сессии) и
  `start_budget` (токены, размер / 4). `docflow status` печатает `start:`,
  превышение бюджета — ошибка `lint`.
- Проект с несколькими git-репозиториями (корень + вложенные) — ключ `repos:`
  во frontmatter `docs/docflow.md`: список путей через запятую (как `start_read`),
  без масок. Проверка чистоты, отпечаток `verify` и коммит юнита охватывают
  все репо из `repos:`; без ключа поведение прежнее (только корень).
- Закоммитить результат `init` до первого плана: `prompt` требует чистое
  дерево.
- Установка проектных копий скиллов для обоих агентов описана в разделе
  [«Установка»](#установка); закоммитьте их вместе с проектом.

## Жизненный цикл задачи

```
Backlog ──plan──▶ план draft ──docflow activate──▶ active ──run × N──▶ ready to close ──close──▶ archive
                                              │
                                                     └─ [!] блок ──replan──▶ active
```

| Этап | Что сказать агенту | Скилл | Коммит |
|---|---|---|---|
| Записать задачу | «добавь в backlog …» или руками | — | вместе с ближайшим изменением |
| Спланировать | «возьми в работу …», «составь план» | `bsv-docflow-plan` | `Pxxx: add plan` |
| Активировать | `docflow activate Pxxx` сам или «активируй Pxxx» | — | `Pxxx: activate plan` |
| Выполнить юнит | «продолжай», «следующий юнит», «юнит P004.1.2» | `bsv-docflow-run` | `Pxxx.N.M: …` |
| Перепланировать | «docflow status сообщает о блоке», «перепланируй» | `bsv-docflow-plan` | `Pxxx: replan` |
| Закрыть план | «закрой план» (готовый закрывается сразу) | `bsv-docflow-close` | `Pxxx: close plan` |
| Решение без плана | «запиши решение в архив» | `bsv-docflow-close` | `Pxxx: add note` |
| Бросить план | «брось план P00x» | `bsv-docflow-close` | `Pxxx: close plan` |

Где мы сейчас — `docflow status`: планы очереди с прогрессом, текущий юнит
или `blocked:`.

## Планирование

0. Задача помещается в один юнит — агент спрашивает «делаем без плана?»;
   да → работа, коммит, решение с «почему» — `docflow note`.
1. Агент читает `docs/docflow.md`, индекс architecture и нужные темы, затем
   только код, без которого задачу не разрезать.
2. `docflow new <slug>` — план `docs/plans/Pxxx-slug.md` в статусе `draft`,
   id в конец Queue.
3. Шапка: `Goal` (что будет после закрытия), `Context` (файлы для каждого
   юнита, repro бага — прозой), `Constraints`, `Traps`, `Decisions`.
4. Фазы и юниты. Юнит — одна сессия: ~100k контекста, 5–8 изменяемых
   файлов, один `Verify`. План, помещающийся в ~100k, — один юнит.
   Калибровка — `docflow stats`. План меняет то, что видит пользователь, —
   последний юнит «Приёмка»: сценарии по Goal и полный прогон тестов.
5. `docflow lint` без ошибок → план показывается пользователю.
6. Коммит `Pxxx: add plan` (план в `draft`), строка Backlog удаляется.
7. Активация — отдельно и только по решению человека: `docflow activate
   Pxxx` (lint плана, `status: active`) + коммит `Pxxx: activate plan`.
   План без явной просьбы агент не создаёт и после активации юнит сам не
   берёт.

Черновик (`draft`) `prompt` пропускает: план можно писать, не мешая
текущей работе.

## Выполнение юнита

```
docflow prompt → работа → docflow verify <id>* → docflow finish <id>
```

- `prompt` — промпт юнита: Goal, Constraints, Traps, Context, Decisions
  плана, сам юнит, Handoff юнитов из `Depends`, раздел `## Archive gotchas`
  (Gotchas записей архива, на которые ссылаются Context, Decisions или
  `Read:`; считаются как ловушки). Ставит `[~]`. Требует
  чистое дерево (кроме файла плана).
- Работа — ровно `Do:`. Найденное по пути — пункт Handoff или вопрос
  пользователю, не правка «заодно».
- `verify` — запускает `preflight:` из `docs/docflow.md`, если задан,
  затем `Verify:` и `gate:` плана; при
  падении печатает хвост вывода, при успехе — одну строку и снимает
  отпечаток дерева. `--no-gate` — быстрая итерация без gate, отпечатка нет.
- `finish --handoff "…" [--decision "…"]` — `verify`, `done` и `commit` одним
  вызовом; первый ненулевой код — стоп. Путь агента. Отдельные `verify`,
  `done`, `commit` — для промежуточных прогонов и раннера.
- `done --handoff "…" [--decision "…"]` — `[x]`, Handoff и Decisions в
  план. Handoff — то, чего следующий юнит не увидит в коде; decision —
  выбор, которого не было в плане: `решение — почему — альтернатива`.
- `commit` — `git add -A` и коммит с subject из `Commit:`, body из
  Handoff. Отказывает, если дерево изменилось после `verify`.

После отказа commit-hook `run` возвращает ошибку агенту в пределах `--attempts`.
Незавершённый коммит виден как `commit pending`: следующий `run` или `finish <id>`
завершает этот юнит перед следующим, сохраняя уже созданные коммиты вложенных репо.
Ошибки подписи и доступа останавливают запуск с причиной.

Один юнит — одна сессия: следующий юнит лучше начинать в новой сессии
(`/clear`), иначе контекст прошлого юнита оплачивается на каждом запросе.
Несколько мелких юнитов подряд в одной сессии допустимы.

`docflow stats [Pxxx]` — расход на юнит по транскриптам Claude: прокси
размера из `prompt`, число запросов, базовый и пиковый контекст, отношения
`peak/proxy` и `grow/proxy` с медианой каждого внизу. По ним калибруется
размер юнита.

## Автозапуск

```
docflow run --dry-run    # следующий юнит, агент, модель, команда — без запуска
docflow run --dry-run --all            # исполнители всех оставшихся юнитов
docflow run --dry-run --plan P002 --all  # то же для draft/frozen-плана
docflow run              # юниты текущего плана подряд до ready to close
```

- Перед запуском: чистое дерево и вход в CLI агента (`claude auth login`
  для профиля по умолчанию).
- Исполнитель юнита задаёт план: `executor: agent | model | effort` в шапке,
  `Executor:` в юните ([формат](design/format.md#план)). Тогда `run` берёт
  встроенные адаптеры без конфига, а `--config`, `--agent`, `--model`,
  `--effort` — ошибка: исполнителя меняют в плане. Назначения всех
  оставшихся юнитов проверяются до смены статуса, квоты и агента; ошибка —
  код 2 с `путь:строка` назначения.
- `fallback: agent | model | effort; ...` задаёт резервные маршруты в
  порядке попыток для плана с исполнителями. `--dry-run --all` печатает
  эту цепочку после маршрутов юнитов. При лимите подписки или недоступности
  провайдера раннер переключается на первый доступный маршрут с новой
  сессией и полным промптом; `throttle` повторяет текущий маршрут. Раннер
  ждёт ближайший срок сброса, только если недоступна вся цепочка. В строке
  завершённого юнита указывается резервный исполнитель, если он использован.
- `timeout: 60..86400` задаёт стенное время вызова агента в секундах и
  перекрывает профильный `timeout` для юнитов и replan. Без ключа плана
  применяется профильный таймаут.
- `--dry-run --all` — строка на каждый оставшийся юнит:
  `id [статус] заголовок: agent | model | effort (unit|plan|legacy)`.
  `--plan <id>` — dry-run названного плана (draft, active, frozen) без
  активации, thaw и правки Queue; без `--dry-run` и `--plan`, и `--all` —
  код 2. Dry-run не проверяет вход в CLI и квоту.
- Перед каждым юнитом раннер печатает `id заголовок -> agent | model | effort`;
  после переключения новый маршрут также виден в выводе юнита.
- Режим прав и предусловия: план объявляет `permissions: auto|full`
  (нет ключа — `auto`) и секцию `## Prerequisites` — пункты с командой
  проверки и пункты, которые обеспечивает только человек. Суффикс
  `(once)` помечает проверку, которую раннер выполняет до первого юнита;
  если хотя бы один юнит уже не `[ ]` и не `[-]`, при продолжении он
  пропускает такой пункт и печатает `prerequisite skipped (once, plan
  started): <текст>`. Остальные команды выполняются на старте из корня
  (провал — код 2 со строкой на каждый пункт), а `full` и оставшиеся
  пункты без команды подтверждает одним
  вопросом `continue? [y/N]`: `--yes` пропускает вопрос (без терминала
  обязателен); если после пропуска `(once)` пунктов для подтверждения не
  осталось и режим не `full`, вопрос не задаётся. Ответ «n» — код 1.
  Dry-run печатает `(once)` после текста или команды. `full` снимает песочницу: claude
  `--permission-mode bypassPermissions`, codex
  `--dangerously-bypass-approvals-and-sandbox`, Pi `--approve`; dry-run
  показывает режим и список предусловий.
- Авто-replan: `replan: agent | model | effort` в шапке плана — исполнитель
  перепланирования. Триггеры — блок `needs plan` и устаревшая ссылка
  `Read:`/Context (код 2): раннер вызывает replan-агента (те же
  механизмы, что юнит: попытки, таймаут, лимит, права), проверяет, что
  тронут только план и только разрешённые места (шапка, Goal,
  Constraints, Prerequisites, закрытые юниты, `lint`), коммитит
  `Pxxx: replan Pxxx.N.M` и продолжает прогон со строки `<id> replan ->
  …`; нарушение — план восстановлен, код 3. Лимиты — 2 replan на юнит и
  `--replans N` (по умолчанию 3) на прогон; `blocker: human` replan не
  вызывает.
- Флаги: `--max-units N`, `--model M` (ярус или id модели, на все юниты),
  `--effort E` (усилие на все юниты), `--attempts N`, `--replans N`
  (лимит авто-replan на прогон; по умолчанию 3, максимум 2 на юнит,
  0 выключает), `--agent NAME`
  (ассистент на все юниты вместо ярусов; эти три и `--config` — только для
  плана без исполнителей), `--no-wait` (не ждать, пока снова станет
  доступен исполнитель),
  `--no-notify` (не посылать уведомление в конце прогона),
  `--yes` (ответить на подтверждение старта без вопроса),
  `-v/--verbose` (токены, время сброса квоты, оценка остатка, лог каждого
  вызова; строка `quota:` на старте и с дельтой за юнит печатается и без
  него).
- Остановить сразу — Ctrl-C (или `kill`, или закрыть терминал): агент
  останавливается вместе с раннером, юнит остаётся `[~]`.
- Остановить после текущего юнита — `s` + Enter в терминале раннера или
  `docflow run --stop` из другого терминала; код 0.
- В конце любого прогона, кроме остановки сигналом, — системное
  уведомление: `план: ready to close`, блок юнита или причина остановки.
  darwin — `osascript`, linux — `notify-send`; `--no-notify` или
  `DOCFLOW_NOTIFY=0` выключают.
- На старте — предупреждение, если у агента плана нет скиллов docflow
  или они устарели, с командой обновления; прогон идёт дальше.
  `DOCFLOW_SKILLS_CHECK=0` выключает.
- После остановки — разобраться и запустить `docflow run` снова: юнит
  `[~]` продолжается с текущего дерева. Лог вызовов агента —
  `.git/docflow/run/<id>.<n>.out`.
- Код 2 перед юнитом — `prompt` отверг юнит: файл из `Read:` или
  `## Context` не найден (предыдущий юнит его переименовал или удалил).
  С ключом `replan:` раннер чинит план сам; без него — replan руками
  (`bsv-docflow-plan`), потом `run`.
- Код 3 — агент заблокировал юнит; класс блока виден в строке юнита и в
  Handoff: `needs human` — нужен человек (вход, доступ, секрет,
  устройство, решение); `needs plan` — править план: с ключом `replan:`
  раннер делает это сам, без — replan руками, потом `run`.
- Код 4 — `Verify` не прошёл за все попытки: работа агента лежит в дереве;
  доделать руками обычным циклом или запустить `run` снова.
- Код 5 — агент закоммитил файл плана, переписал историю или сменил статус
  юнита: разобрать коммит и план руками. Коммиты инструментов проекта,
  которые запускает юнит, раннеру не мешают.
- Код 7 — агент не справился: нет валидного result JSON, таймаут, лимит
  при `--no-wait`; причина — в логе.
- Закрытие плана раннер не делает: `bsv-docflow-close` вручную.

### Конфиг агентов

Конфиг — только для плана без исполнителей. TOML: `--config` >
`$DOCFLOW_AGENTS` > `$XDG_CONFIG_HOME/docflow/agents.toml` (`~/.config/…`);
файл из `--config` или `$DOCFLOW_AGENTS`, которого нет, — ошибка. Встроенные профили
`claude`, `codex` и `pi` (`docflow run --print-config`); файл накладывается на встроенные
профили по ключам (`model_extra` и `permissions` — тоже по ключам), добавляет новые профили
и накладывается на таблицу `[tiers]` ярус за ярусом, ключ за ключом:
`[tiers.<fast|default|strong|max>]` с ключами `agent` (имя профиля),
`model`, `effort`. Неизвестный ключ, неверный тип или ярус с несуществующим
профилем — код 2; прежние `models` и `default_agent` — тоже код 2 с
подсказкой, куда они переехали. Новый ассистент — конфиг, не код.

| Ключ профиля | Смысл |
|---|---|
| `cmd` | argv вызова; промпт — в stdin, если нет `{prompt}` |
| `model_args`, `resume_args` | добавляются к `cmd`, когда есть модель / сессия |
| `model` | модель профиля: берётся при `--agent` вместо модели яруса |
| `effort_args` | добавляются после `model_args` и `model_extra`, когда задано усилие |
| `model_extra` | таблица id модели (после маршрутизации) → аргументы после `model_args` |
| `permissions` | таблица режима прав плана → аргументы после `cmd` (`auto`/`full`); накладывается на встроенную по ключам; профиль без таблицы: `auto` — `cmd` как есть, `full` — код 2 |
| `result`, `text`, `session`, `error`, `cost` | пути `json:a.b` в JSON-выводе: result JSON, текст ответа, id сессии, флаг ошибки, стоимость |
| `tokens` | список путей `json:a.b`; сумма значений — токены вызова (`claude`: `usage.input_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`); ключа нет — токены не считаются |
| `stream` | декодер потока JSON Lines: `"claude"`, `"codex"`, `"pi"` или пусто; `claude` даёт квоту подписки и текущее действие агента, `pi` — объект `session`, `text`, `usage`, `cost`, `is_error`, `error`, `codex` — действие и сворачивает события в объект `thread_id`, `text`, `usage`, `is_error`, `error` для путей `json:`; без декодера остаются только итоги |
| `output_tokens` | путь `json:a.b` к числу выходных токенов вызова (`claude`: `usage.output_tokens`) |
| `turns` | путь `json:a.b` к числу ходов агента в вызове (`claude`: `num_turns`) |
| `limit`, `limit_wait` | regex сообщения о лимите; ожидание, если время сброса не найдено (1800 с) |
| `auth` | regex сообщения «CLI агента не залогинен»: прогон останавливается сразу, без повторов |
| `timeout` | положительное число секунд на вызов; 0, отрицательное значение или отсутствие ключа — без таймаута |
| `instructions` | текст в конец промпта юнита; только в режиме прав `auto` |
| `quota` | argv опроса квоты на старте `run`, без вызова модели; вывод разбирает `stream` (`claude`: текст `/usage`, `codex`: JSON-RPC `app-server`); пусто — не опрашивать; у Pi квота встроена для модели `zai/...`, ключ профиля не нужен |

Плейсхолдеры в аргументах: `{prompt}`, `{model}`, `{effort}`, `{schema}` (JSON-схема
result inline), `{schema_file}`, `{session}`.

Свой `~/.config/docflow/agents.toml` накладывается на встроенный
(`docflow run --print-config`) по ключам:

```toml
[tiers]
default = {model = "opus"}    # ярус default теперь opus
fast = {model = "claude-haiku-x"}
strong = {agent = "codex", model = "<id модели OpenAI>", effort = "high"}

[agents.claude.model_extra]   # модели без режима auto — явные права
claude-haiku-x = ["--allowedTools", "Write", "Edit", "Bash"]

[agents.codex]
timeout = 7200
```

Профиль `codex` запускает `codex exec --json --approve-for-me` в песочнице
workspace-write с сетью; запись вне репозитория агент просит с эскалацией,
её проверяет автоматический ревьюер. Модель — `-m`, усилие —
`-c model_reasoning_effort=`, продолжение сессии — `resume <thread_id>`.
Нужен собственный вход CLI (`codex login`).

Профиль `pi` запускает `pi -p --mode json`; промпт идёт в stdin. Модель —
`--model`, усилие — `--thinking` (`off`…`max`) один к одному, продолжение
сессии — `--session <id>`. В исполнителе плана модель — строка тройки как
есть: `executor: pi | zai/glm-5.3 | high`, `zai/glm-5.3-flash` (подписка
z.ai) или модель локального провайдера (`local-lan/<id>`). Квота Pi
опрашивается только для моделей `zai/…` — встроенным зондом API z.ai;
остаток других подписок Pi отдельной командой не отдаёт. Скиллы —
`docflow install-skills --agent pi`; в headless-режиме Pi пропускает
`.pi/skills/` без project trust (запись в `~/.pi/agent/trust.json` или
`--approve`), личный каталог trust не требует. Нужен вход в провайдера Pi.

Профиль без `result` берёт result JSON из последнего блока ` ```json `,
без `resume_args` повторяет попытку полным промптом. Запуск —
`docflow run --agent codex` для всех юнитов или `agent = "codex"` в нужном
ярусе.

## Ростер

Ростер подбирает маршруты ролей при составлении плана: `docflow roster
show` печатает готовые цепочки, `docflow roster apply Pxxx` пишет их в
шапку плана. Раннер и `lint` ростер не читают — план остаётся
воспроизводимым. Файл: `--roster PATH` >
`$XDG_CONFIG_HOME/docflow/roster.toml` (`~/.config/…`); файла нет — код 2
с путём.

```toml
spend = ["zai", "codex", "claude"]   # порядок расхода: первый тратится первым

[provider.zai]
check = true      # юниты этого провайдера проверяет ревью другим провайдером

[provider.claude]
trusted = true    # допускается к acceptance и replan

[role]            # роль -> минимальная ступень: cheap < standard < strong;
cheap      = "cheap"      # trusted = strong у провайдера с trusted
executor   = "standard"
heavy      = "strong"
review     = "strong"     # провайдеры с check исключены
acceptance = "trusted"
replan     = "trusted"

[route.glm-flash-high]
run  = "pi | zai/glm-5.3-flash | high"   # тройка, как у Executor
tier = "cheap"

[profile.save-claude]          # необязательно: заменяет spend и флаги
spend = ["zai", "codex"]       # перечисленных провайдеров; выбор --profile NAME
[profile.save-claude.provider.codex]
trusted = true
```

Провайдер маршрута: для `pi` — префикс модели до `/` (`zai/glm-5.3` →
`zai`, модель без `/` → `pi`), для остальных — имя агента. Подбор цепочки
роли: провайдеры в порядке `spend`, у каждого один маршрут — с наименьшей
ступенью не ниже требуемой (при равенстве — первый в файле); провайдер без
подходящего маршрута пропускается: квота общая на подписку, второй маршрут
того же провайдера был бы пустой попыткой. Для `review` провайдеры с
`check` исключены. Для `trusted` — сначала `strong` провайдеров с
`trusted`, затем запас: `strong` остальных провайдеров без `check` в
порядке `spend`. Цепочка короче двух маршрутов разных провайдеров — код 2:
без запаса лимит единственного провайдера останавливает прогон до сброса.

`roster show` печатает строку `spend: … · check: … · trusted: …` и шапку
плана: `executor:` — первый маршрут роли executor, `fallback:` — её
остальные маршруты, `cheap:`, `heavy:`, `review:`, `acceptance:`,
`replan:` — полные цепочки. Неизвестный ключ, неразбираемая тройка `run`,
ступень вне `cheap|standard|strong`, требование роли вне
`cheap|standard|strong|trusted`, неизвестная роль, провайдер маршрута вне
`spend`, повтор в `spend`, неизвестный профиль — код 2 с файлом и строкой.

## Блок и replan

- План разошёлся с кодом, `Verify` не проверяет честно, три `verify`
  подряд без прогресса → `docflow block <id> --reason "…"`; выдача юнитов
  останавливается (код 3).
- Replan правит только юниты `[ ]` и `[!]`; новые юниты — следующими
  номерами, существующие не перенумеровываются.
- Снятие блока: незакоммиченная работа остаётся в силе → `[~]`; работа не
  нужна → решает пользователь; работы нет → `[ ]`; юнит не нужен → `[-]`.
- `verify --skip "<причина>"` — только когда проверку нельзя запустить в
  окружении (нет устройства, сети) и пользователь согласен.

## Закрытие

1. `docflow status` пишет `ready to close` — все юниты `[x]`/`[-]`.
2. Ссылки на `docs/plans/Pxxx…` переводятся на будущую архивную запись.
3. `docflow close Pxxx` — архивная запись с перенесёнными `## Decisions`;
   план и строка Queue удаляются.
4. Агент заполняет запись: `Outcome`, сжатые `Decisions`, `Gotchas`,
   `Follow-ups`.
5. Architecture — текущее устройство и ссылка на запись; README — строки
   состояния; CHANGELOG — наблюдаемое поведение (нет файла — шаг
   пропускается); Follow-ups — строками в Backlog, включая незакрытые
   пункты Handoff `Unverified: …`; только наблюдение вне Goal, ждущее
   внешнего события, остаётся в записи строкой `Waits: …`.

Брошенный план закрывается так же: оставшиеся юниты вручную в `[-]`, в
`Decisions` — `план брошен — почему — что вместо`.

## Что куда идёт

| Информация | Место | Кто пишет | Живёт до |
|---|---|---|---|
| Идея, задача | строка `## Backlog` в `docs/docflow.md` | человек, `close` из Follow-ups | взятия в план |
| Порядок планов | `## Queue` в `docs/docflow.md` | `new`, `close` | закрытия плана |
| Цель, рамки, ловушки плана, repro | шапка плана | `bsv-docflow-plan` | закрытия плана |
| Что сделать в сессии | юнит: `Read`, `Do`, `Verify`, `Traps`, `Commit` | `bsv-docflow-plan` | закрытия плана |
| Статус юнита | маркер `[ ]` `[~]` `[x]` `[-]` `[!]` в плане | `docflow` | закрытия плана |
| Записка следующему юниту | `Handoff:` юнита | `docflow done` | закрытия плана, в архив не идёт |
| Решение по ходу | `## Decisions` плана | `docflow done --decision`, планировщик | переносится в архив |
| Почему так (закрытое) | `docs/archive/Pxxx-slug.md` | `close` + `bsv-docflow-close` | навсегда; правка — только `superseded_by` |
| Ловушки после закрытия | `## Gotchas` архивной записи | `bsv-docflow-close` | навсегда |
| Несделанное | `## Follow-ups` записи → Backlog, кроме `Waits:` | `bsv-docflow-close` | взятия в план |
| Текущее устройство | architecture проекта + ссылка на архив | `bsv-docflow-close` | пока решение действует |
| Текущее состояние | `README.md` | `bsv-docflow-close` | следующего изменения |
| Что изменилось для пользователя | `CHANGELOG.md` | `bsv-docflow-close` по `bsv-changelog` | навсегда |
| Изменения кода | git-коммит юнита | `docflow commit` | навсегда |
| Счётчики тестов, логи сборки | ответ в чате | агент | — в доки не пишется |

Отменённое решение: в architecture правится на новое, у старой архивной
записи — `superseded_by: Pyyy` во frontmatter.

## Ветки

- Один план — одна ветка или worktree; параллельно — только разные планы.
- Ветки создаёт и переключает пользователь, `docflow` их не проверяет.
- Совпадение id планов из разных веток ловит `lint` после merge.

## Типовые ситуации

| Ситуация | Что делать |
|---|---|
| `prompt`: `working tree is dirty` (код 5) | чужие изменения: закоммитить или убрать самому, агент их не трогает |
| `prompt`: `… is in progress` | другой юнит `[~]` — продолжить его: `docflow prompt` без id |
| `verify` падает (код 4) | исправить по хвосту вывода; три раза без прогресса — `block` |
| `status`: `blocked:` (код 3) | replan через `bsv-docflow-plan` |
| `status`: `ready to close` | закрыть через `bsv-docflow-close` |
| `next`/`prompt`: делать нечего (код 1) | очередь пуста или все планы ждут `close` |
| Код 2 и подсказка `docflow migrate` | формат старой версии: `docflow migrate`, затем `lint` |
| Мелкая правка что-то решила | `docflow note <slug>` — запись в архиве без плана |
| Нужно пропустить юнит | replan: `[-]` |
| Отложить план на время | `docflow freeze <id> --reason "…"` + коммит, затем `docflow thaw <id>` + коммит когда вернуться |
| Юнит меняет несколько репо | в плане указан ключ `repos:`, агент не коммитит сам — `docflow commit` охватит все |
