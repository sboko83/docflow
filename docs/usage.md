# Как пользоваться docflow

Процесс от идеи до архива: кто что делает, какие команды, что куда пишется.
Формат файлов, команды и коды выхода — [docs/design/](design/README.md); здесь —
порядок работы.

## Установка

### Установить CLI

Требования: macOS, Linux или Windows 10/11 (amd64 или arm64). Go и sudo не
нужны; install.sh требует curl или wget, install.ps1 — только PowerShell:

~~~bash
curl -fsSL https://raw.githubusercontent.com/sboko83/docflow/main/install.sh | sh
~~~

Windows, PowerShell:

~~~powershell
irm https://raw.githubusercontent.com/sboko83/docflow/main/install.ps1 | iex
~~~

Команда с install.sh работает и в Git Bash на Windows.

Установщик определяет OS и архитектуру, скачивает последний релиз, сверяет
sha256 по checksums.txt, распаковывает архив и запускает из него
`docflow install`. Тот укладывает бинарник, скиллы и LICENSE в
`~/.docflow/versions/<X.Y.Z>/`, переключает симлинк `current` и создаёт
`bin/docflow`:

~~~
~/.docflow/
  bin/docflow     -> ../current/docflow
  current         -> versions/<version>
  versions/<version>/docflow
  versions/<version>/skills/<имя>/
  versions/<version>/LICENSE
  last-update-check
~~~

Затем `docflow install` добавляет `~/.docflow/bin` в PATH (блок в
`.zshrc`, `.bashrc` или `.bash_profile`; на Windows — каталог `current`
в пользовательский PATH, а симлинки заменяют directory junction, без
Developer Mode и прав администратора) и ставит личные симлинки скиллов
агентам, чьи CLI найдены в PATH (`claude`, `codex`, `pi`, `opencode`), и в
`~/.zcode/skills`, если существует каталог `~/.zcode`. Симлинки ведут в
`~/.docflow/current/skills/<имя>` и не переписываются при обновлении.

Режим скиллов спрашивается один раз: `global` — личные симлинки в каталоги
агентов, как выше; `project` — каталоги агентов чистые, скиллы несут только
проектные копии. Ответ хранится одним словом в `~/.docflow/skills-mode` и
удаляется вместе с `~/.docflow`; `docflow update` следует ему без вопроса.
Вопрос пишется в stderr, ответ читается с управляющего терминала, поэтому
пайп `curl … | sh` его не гасит. Без терминала (скриптовая установка, CI)
действует `global`, файл не пишется и печатается одна подсказка. В
project-режиме скиллы в проект ставят `docflow init --skills` и
`docflow install-skills --project`; сам режим ничего не копирует.

Переменные окружения install.sh и install.ps1: `DOCFLOW_VERSION=X.Y.Z` —
поставить конкретный релиз вместо последнего; `DOCFLOW_RELEASE_URL` — базовый
URL релизов вместо GitHub Releases (по умолчанию
`https://github.com/sboko83/docflow/releases`); `DOCFLOW_SKILLS=global|project`
— ответить на вопрос о режиме скиллов заранее, установщик передаёт его как
`docflow install --skills`. В PowerShell переменную задают перед командой:
`$env:DOCFLOW_VERSION = 'X.Y.Z'`.

После установки перезапустите оболочку или выполните
`export PATH="$HOME/.docflow/bin:$PATH"` и проверьте версию:

~~~bash
docflow --version
~~~

### Проверить комплект и подключить проект

После установки проверьте комплект для выбранного агента:

~~~bash
docflow doctor --agent codex
~~~

Для Pi укажите --agent pi: личные симлинки лягут в ~/.pi/agent/skills/, а
doctor добавит строку с версией Pi. Для Claude Code опустите --agent: это
цель по умолчанию. Команда
install-skills без --project ставит личные симлинки; --target DIR явно
задаёт другой личный каталог.

В проекте создайте документы docflow:

~~~bash
cd <project>
docflow init --agent codex
~~~

Для Claude Code достаточно docflow init. Чтобы сразу скопировать скиллы в
проект, добавьте --skills, например docflow init --agent codex --skills.
В уже подключённом проекте используйте docflow install-skills --project
--agent codex; для Claude опустите --agent. Проектные копии находятся в
.agents/skills/ для Codex, .pi/skills/ для Pi или .claude/skills/ для Claude и коммитятся вместе
с проектом.

Выберите личную установку для своих проектов или проектные копии для команды.
При одновременной установке одинаковые имена могут отображаться в Codex дважды;
правила приоритета каталогов Claude и Codex различаются —
[каталоги и приоритеты](design/skills.md#установка-скиллов).

`doctor` сравнивает файлы, но не подтверждает обнаружение скиллов агентом.
Для полного комплекта проверьте пять строк `<имя скилла>: ok`;
[коды выхода](design/cli.md#скрипт-docflow) не заменяют чтение этого вывода.

### Обновить CLI и проектные копии

~~~bash
docflow update --check   # только сообщить о новом релизе
docflow update           # скачать и активировать последний релиз
docflow update --skills project   # переключить режим скиллов
docflow --version
docflow doctor --agent codex
~~~

`docflow update` скачивает последний релиз тем же путём, что и install.sh,
сверяет sha256 и активирует новую версию переключением симлинка `current`:
в `~/.docflow/versions` остаются текущая и предыдущая версии, личные
симлинки скиллов продолжают указывать на `current`. Если нового релиза нет,
команда печатает `up to date`. Переменная `DOCFLOW_RELEASE_URL` действует
и здесь.

Вывод после `updated:` — строка на каждый каталог личных скиллов с числом
ссылок; `(N new)` — ссылки на скиллы, появившиеся в релизе. Сами ссылки не
переписываются: они указывают в `current` и сразу видят новую версию.
Проектные копии (`docflow install-skills --project`) — копии, а не ссылки;
update проверяет только копии проекта, из которого запущен, и печатает для
устаревших команду обновления. Остальные проекты проверяет `docflow doctor`
в их каталоге.

Режим скиллов `docflow update` берёт из `~/.docflow/skills-mode` и не
спрашивает: в `global` ссылки ставятся, в `project` каталоги агентов остаются
чистыми. `docflow update --skills global|project` переключает режим и
применяет его к ссылкам, даже когда нового релиза нет: `global` создаёт личные
симлинки, `project` убирает только свои (ведущие в `~/.docflow`), оставляя
чужие ссылки и проектные копии. `docflow update --check` режим не трогает.

Откат на предыдущую версию — переключить `current` вручную:

~~~bash
ls ~/.docflow/versions                      # текущая и предыдущая
ln -sfn versions/<предыдущая> ~/.docflow/current
docflow --version
~~~

Скиллы откатываются вместе с CLI. Следующий `docflow update` заново скачивает
последний релиз поверх оставшегося каталога этой версии.

При каждом терминальном запуске docflow не чаще раза в сутки проверяет
последний релиз (таймаут 2 секунды) и пишет в stderr строку вида
`docflow 0.4.1 available (current 0.4.0): docflow update`. Отключается
переменной `DOCFLOW_NO_UPDATE_CHECK=1`.

Удаление standalone-установки:

~~~bash
docflow uninstall
~~~

Команда убирает `~/.docflow`, свой блок PATH из профилей оболочки и личные
симлинки скиллов, ведущие в `~/.docflow`; проектные копии скиллов и чужие
файлы не трогает.

В каждом проекте обновите принадлежащие docflow копии скиллов:

~~~bash
cd <project>
docflow install-skills --project --agent codex
docflow doctor --agent codex
~~~

Для Claude опустите --agent. Обновление заменяет содержимое распознанных
копий скиллов. Сохраните или просмотрите локальные правки проектной копии
до этого шага; чужие каталоги и симлинки установщик оставляет без
изменений и сообщает о конфликте.

### Режим разработки

Разработка ведётся из checkout репозитория (нужны Go 1.26+ и git):

~~~bash
git clone https://github.com/sboko83/docflow bsv-docflow
cd bsv-docflow
bash tools/install-dev.sh --dry-run
bash tools/install-dev.sh
~~~

Скрипт проверяет исходники, собирает bin/docflow и создаёт симлинк
`docflow-dev` в выбранном каталоге (`~/.local/bin` по умолчанию; другой —
через `--bin-dir DIR`). `docflow` на PATH остаётся установленным релизом.
Скиллы скрипт не трогает: симлинки скиллов переключает утилита
`bash tools/switch-skills.sh` (`dev` — на checkout, `release` — на релиз,
без аргумента — текущий режим). Флаг `--dry-run` печатает план, ничего
не меняя. Скрипт не меняет PATH: если каталог не найден в PATH, он
напечатает команду для добавления в профиль оболочки. Сохраните checkout
на месте, пока используете CLI: симлинк ведёт в него.

`docflow-dev update` и `docflow-dev uninstall` в dev-сборке отказывают.
Обновление — переключить чистый checkout на новый тег и повторить
установщик; сначала проверьте локальные изменения и сохраните их отдельно,
не сбрасывая:

~~~bash
cd bsv-docflow
git status --short
git fetch --tags origin
git checkout vX.Y.Z
bash tools/install-dev.sh
docflow-dev --version
docflow-dev doctor --agent codex
~~~

Если личные скиллы ставились через произвольный `--target DIR` вне
`~/.zcode/skills`, повторите установку вручную командой
`docflow install-skills --target DIR`.

### Отдельное применение скиллов и Ruleblend

bsv-docs и bsv-changelog работают отдельно от docflow и подходят проектам без
docs/docflow.md. Три скилла bsv-docflow-* описывают процесс планирования,
исполнения и закрытия планов. Правила языка, релиза, коммитов и структуры
конкретного проекта имеют приоритет.

Ruleblend необязателен. Если используете его, импортируйте скиллы
git-импортом этого GitHub-репозитория. Ruleblend читает закоммиченный HEAD;
выбирайте тег как источник, не создавая отдельную копию скиллов.

## Подключение проекта

```bash
cd <project>
docflow init
```

- Создаёт `docs/docflow.md` (очередь, backlog), `docs/plans/`,
  `docs/archive/` и строку в `AGENTS.md`:
  `Plans: docflow (run docflow status), only on an explicit request; not the bsv-docs PLAN genre`.
- Существующий проект переводится только явно. Старый `docs/PLAN.md`
  после перевода не ведётся: открытые задачи — строками в Backlog.
- Architecture проекта (`docs/architecture.md` или что названо в AGENTS.md)
  остаётся: в ней текущее устройство и ссылки на `docs/archive/`.
- Стартовое чтение — необязательные ключи `docs/docflow.md`: `start_read`
  (пути и `path#anchor` через запятую, что читать в начале сессии) и
  `start_budget` (токены, размер / 4). `docflow status` печатает `start:`,
  превышение бюджета — ошибка `lint`.
- Проект с несколькими git-репозиториями (корень + вложенные) — ключ `repos:`
  во frontmatter `docs/docflow.md`: список путей через запятую (как `start_read`),
  без масок. Проверка чистоты, отпечаток `verify` и коммит юнита охватывают
  все репо из `repos:`; без ключа поведение прежнее (только корень).
- Закоммитить результат `init` до первого плана: `prompt` требует чистое
  дерево.
- Установка проектных копий скиллов для обоих агентов описана в разделе
  [«Установка»](#установка); закоммитьте их вместе с проектом.

## Жизненный цикл задачи

```
Backlog ──plan──▶ план draft ──docflow activate──▶ active ──run × N──▶ ready to close ──close──▶ archive
                                              │
                                                     └─ [!] блок ──replan──▶ active
```

| Этап | Что сказать агенту | Скилл | Коммит |
|---|---|---|---|
| Записать задачу | «добавь в backlog …» или руками | — | вместе с ближайшим изменением |
| Спланировать | «возьми в работу …», «составь план» | `bsv-docflow-plan` | `Pxxx: add plan` |
| Активировать | `docflow activate Pxxx` сам или «активируй Pxxx» | — | `Pxxx: activate plan` |
| Выполнить юнит | «продолжай», «следующий юнит», «юнит P004.1.2» | `bsv-docflow-run` | `Pxxx.N.M: …` |
| Перепланировать | «docflow status сообщает о блоке», «перепланируй» | `bsv-docflow-plan` | `Pxxx: replan` |
| Закрыть план | «закрой план» (готовый закрывается сразу) | `bsv-docflow-close` | `Pxxx: close plan` |
| Решение без плана | «запиши решение в архив» | `bsv-docflow-close` | `Pxxx: add note` |
| Бросить план | «брось план P00x» | `bsv-docflow-close` | `Pxxx: close plan` |

Где мы сейчас — `docflow status`: планы очереди с прогрессом, текущий юнит
или `blocked:`.

## Планирование

0. Задача помещается в один юнит — агент спрашивает «делаем без плана?»;
   да → работа, коммит, решение с «почему» — `docflow note`.
1. Агент читает `docs/docflow.md`, индекс architecture и нужные темы, затем
   только код, без которого задачу не разрезать.
2. `docflow new <slug>` — план `docs/plans/Pxxx-slug.md` в статусе `draft`,
   id в конец Queue.
3. Шапка: `Goal` (что будет после закрытия), `Context` (файлы для каждого
   юнита, repro бага — прозой), `Constraints`, `Traps`, `Decisions`.
4. Фазы и юниты. Юнит — одна сессия: ~100k контекста, 5–8 изменяемых
   файлов, один `Verify`. План, помещающийся в ~100k, — один юнит.
   Калибровка — `docflow stats`. План меняет то, что видит пользователь, —
   последний юнит «Приёмка»: сценарии по Goal и полный прогон тестов.
   Исполнителей и запасные маршруты по ролям подбирает личный ростер —
   `docflow roster show` и `docflow roster apply` (см. [«Ростер»](#ростер)).
5. `docflow lint` без ошибок → план показывается пользователю.
6. Коммит `Pxxx: add plan` (план в `draft`), строка Backlog удаляется.
7. Активация — отдельно и только по решению человека: `docflow activate
   Pxxx` (lint плана, `status: active`) + коммит `Pxxx: activate plan`
   (забытый коммит делают сами `run`/`prompt`, пока дерево грязно только
   следами активации). План без явной просьбы агент не создаёт и после
   активации юнит сам не берёт.

Черновик (`draft`) `prompt` пропускает: план можно писать, не мешая
текущей работе.

## Выполнение юнита

```
docflow prompt → работа → docflow verify <id>* → docflow finish <id>
```

- `prompt` — промпт юнита: Goal, Constraints, Traps, Context, Decisions
  плана, сам юнит, Handoff юнитов из `Depends`, раздел `## Archive gotchas`
  (Gotchas записей архива, на которые ссылаются Context, Decisions или
  `Read:`; считаются как ловушки). Ставит `[~]`. Требует
  чистое дерево (кроме файла плана).
- Работа — ровно `Do:`. Найденное по пути — пункт Handoff или вопрос
  пользователю, не правка «заодно».
- `verify` — запускает `preflight:` из `docs/docflow.md`, если задан,
  затем `Verify:` и `gate:` плана; при
  падении печатает хвост вывода, при успехе — одну строку и снимает
  отпечаток дерева. `--no-gate` — быстрая итерация без gate, отпечатка нет.
- `finish --handoff "…" [--decision "…"]` — `verify`, `done` и `commit` одним
  вызовом; первый ненулевой код — стоп. Путь агента. Отдельные `verify`,
  `done`, `commit` — для промежуточных прогонов и раннера.
- `done --handoff "…" [--decision "…"]` — `[x]`, Handoff и Decisions в
  план. Handoff — то, чего следующий юнит не увидит в коде; decision —
  выбор, которого не было в плане: `решение — почему — альтернатива`.
- `commit` — `git add -A` (новые файлы с секретными именами, > 5 МиБ и добавленные строки с токенами (AWS, GitHub, Slack, Google, `sk-`, приватные ключи) — отказ кодом 5, обход `DOCFLOW_ALLOW_STAGED=1`) и коммит с subject из `Commit:`, body из
  Handoff. Отказывает, если дерево изменилось после `verify`.

После отказа commit-hook `run` возвращает ошибку агенту в пределах `--attempts`.
Незавершённый коммит виден как `commit pending`: следующий `run` или `finish <id>`
завершает этот юнит перед следующим, сохраняя уже созданные коммиты вложенных репо.
Ошибки подписи и доступа останавливают запуск с причиной.

Один юнит — одна сессия: следующий юнит лучше начинать в новой сессии
(`/clear`), иначе контекст прошлого юнита оплачивается на каждом запросе.
Несколько мелких юнитов подряд в одной сессии допустимы.

`docflow stats [Pxxx]` — расход на юнит по транскриптам Claude: прокси
размера из `prompt`, число запросов, базовый и пиковый контекст, отношения
`peak/proxy` и `grow/proxy` с медианой каждого внизу. По ним калибруется
размер юнита. Ниже — строки `review-blocks:` для ревью-юнитов, которые run-события
показывают заблокированными три раза и больше: ревью не сходится, нужно
решение человека.

`docflow stats --runs [Pxxx]` — сводка run-событий по юнитам за все
прогоны: версия docflow, попытки, провалы проверки, replan, блоки, правки
тестов, свои `Unverified:`, время, стоимость и `rework` — сколько коммитов
вне docflow (без префикса `Pxxx`) за 7 дней после коммита юнита правят
или удаляют внесённые им строки (при `repos:` — и во вложенных репо);
`--json` — то же JSON-отчётом
(`{"units": [...]}`).

## Автозапуск

```
docflow run --dry-run    # следующий юнит, агент, модель, команда — без запуска
docflow run --dry-run --all            # исполнители всех оставшихся юнитов
docflow run --dry-run --plan P002 --all  # то же для draft/frozen-плана
docflow run              # юниты текущего плана подряд до ready to close
```

- Перед запуском: чистое дерево и вход в CLI агента (`claude auth login`
  для профиля по умолчанию).
- Исполнитель юнита задаёт план: `executor: agent | model | effort` в шапке,
  `Executor:` в юните ([формат](design/format.md#план)). Тогда `run` берёт
  встроенные адаптеры без конфига, а `--config`, `--agent`, `--model`,
  `--effort` — ошибка: исполнителя меняют в плане. Назначения всех
  оставшихся юнитов проверяются до смены статуса, квоты и агента; ошибка —
  код 2 с `путь:строка` назначения.
- `fallback: agent | model | effort; ...` задаёт резервные маршруты в
  порядке попыток для плана с исполнителями. `--dry-run --all` печатает
  эту цепочку после маршрутов юнитов. При лимите подписки или недоступности
  провайдера раннер переключается на первый доступный маршрут с новой
  сессией и полным промптом; `throttle` повторяет текущий маршрут. Раннер
  ждёт ближайший срок сброса, только если недоступна вся цепочка. В строке
  завершённого юнита указывается резервный исполнитель, если он использован.
- `timeout: 60..86400` задаёт стенное время вызова агента в секундах и
  перекрывает профильный `timeout` для юнитов и replan. Без ключа плана
  применяется профильный таймаут.
- `--dry-run --all` — строка на каждый оставшийся юнит:
  `id [статус] заголовок: agent | model | effort (unit|plan|legacy)`.
  `--plan <id>` — dry-run названного плана (draft, active, frozen) без
  активации, thaw и правки Queue; без `--dry-run` и `--plan`, и `--all` —
  код 2. Dry-run не проверяет вход в CLI и квоту.
- Перед каждым юнитом раннер печатает `id заголовок -> agent | model | effort`;
  после переключения новый маршрут также виден в выводе юнита.
- Режим прав и предусловия: план объявляет `permissions: auto|full`
  (нет ключа — `auto`) и секцию `## Prerequisites` — пункты с командой
  проверки и пункты, которые обеспечивает только человек. Суффикс
  `(once)` помечает проверку, которую раннер выполняет до первого юнита;
  если хотя бы один юнит уже не `[ ]` и не `[-]`, при продолжении он
  пропускает такой пункт и печатает `prerequisite skipped (once, plan
  started): <текст>`. Остальные команды выполняются на старте из корня
  (провал — код 2 со строкой на каждый пункт), а `full` и оставшиеся
  пункты без команды подтверждает одним
  вопросом `continue? [y/N]`: `--yes` пропускает вопрос (без терминала
  обязателен); если после пропуска `(once)` пунктов для подтверждения не
  осталось и режим не `full`, вопрос не задаётся. Ответ «n» — код 1.
  Dry-run печатает `(once)` после текста или команды. `full` снимает песочницу: claude
  `--permission-mode bypassPermissions`, codex
  `--dangerously-bypass-approvals-and-sandbox`, Pi `--approve`; dry-run
  показывает режим и список предусловий.
  Песочница `auto` относится только к процессу агента: `preflight`,
  `Verify:` и `gate:` раннер запускает вне неё, с правами пользователя, а
  значит исполняет код, только что написанный агентом. Для недоверенных
  репозиториев и для `full` на часы запускайте `docflow run` в контейнере
  или под отдельной учётной записью; раннер изоляцию не создаёт
  ([граница песочницы](design/runner.md#граница-песочницы)).
- Авто-replan: `replan: agent | model | effort` в шапке плана — исполнитель
  перепланирования. Триггеры — блок `needs plan` и устаревшая ссылка
  `Read:`/Context (код 2): раннер вызывает replan-агента (те же
  механизмы, что юнит: попытки, таймаут, лимит, права), проверяет, что
  тронут только план и только разрешённые места (шапка, Goal,
  Constraints, Prerequisites, закрытые юниты, `lint`), коммитит
  `Pxxx: replan Pxxx.N.M` и продолжает прогон со строки `<id> replan ->
  …`; нарушение — план восстановлен, код 3. Лимиты — 2 replan на юнит и
  `--replans N` (по умолчанию 3) на фазу; `blocker: human` replan не
  вызывает.
- Флаги: `--max-units N`, `--model M` (ярус или id модели, на все юниты),
  `--effort E` (усилие на все юниты), `--attempts N`, `--replans N`
  (лимит авто-replan на фазу; по умолчанию 3, максимум 2 на юнит,
  0 выключает), `--agent NAME`
  (ассистент на все юниты вместо ярусов; эти три и `--config` — только для
  плана без исполнителей), `--no-wait` (не ждать, пока снова станет
  доступен исполнитель),
  `--no-notify` (не посылать уведомление в конце прогона),
  `--yes` (ответить на подтверждение старта без вопроса),
  `-v/--verbose` (токены, время сброса квоты, оценка остатка, лог каждого
  вызова; строка `quota:` на старте и с дельтой за юнит печатается и без
  него).
- Остановить сразу — Ctrl-C (или `kill`, или закрыть терминал): агент
  останавливается вместе с раннером, юнит остаётся `[~]`.
- Остановить после текущего юнита — `s` + Enter в терминале раннера или
  `docflow run --stop` из другого терминала; код 0.
- В конце любого прогона, кроме остановки сигналом, — системное
  уведомление: `план: ready to close`, блок юнита или причина остановки.
  darwin — `osascript`, linux — `notify-send`; `--no-notify` или
  `DOCFLOW_NOTIFY=0` выключают.
- На старте — предупреждение, если у агента плана нет скиллов docflow
  или они устарели, с командой обновления; прогон идёт дальше.
  `DOCFLOW_SKILLS_CHECK=0` выключает.
- После остановки — разобраться и запустить `docflow run` снова: юнит
  `[~]` продолжается с текущего дерева. Лог вызовов агента —
  `.git/docflow/run/<id>.<n>.out`.
- Смотреть работу агента вживую — `tail -f .git/docflow/run/<id>.<n>.out`:
  лог пишётся во время вызова — `$ argv`, затем `--- stdout` по мере
  прихода строк, после выхода агента `--- stderr` и `--- exit N` с
  суффиксом ` (timed out)` или ` (stalled)`. Спиннер TTY к id и времени
  добавляет число ходов и возраст последнего события:
  `<id> <elapsed> · turn <n> · <age> ago`, и `· tool <duration>`, пока
  инструмент в работе.
- Код 2 перед юнитом — `prompt` отверг юнит: файл из `Read:` или
  `## Context` не найден (предыдущий юнит его переименовал или удалил).
  С ключом `replan:` раннер чинит план сам; без него — replan руками
  (`bsv-docflow-plan`), потом `run`.
- Код 3 — агент заблокировал юнит; класс блока виден в строке юнита и в
  Handoff: `needs human` — нужен человек (вход, доступ, секрет,
  устройство, решение); `needs plan` — править план: с ключом `replan:`
  раннер делает это сам, без — replan руками, потом `run`.
  На `needs human` к строке остановки добавлена команда `docflow unblock
  <id> --note "…", then docflow run`. Если `run` стартует на юните `[!]`
  с таким блоком, то в терминале без `--yes` он печатает причину и спрашивает
  `done? [y/N] `, на `y` просит заметку, снимает блок (`unblock`) и
  продолжается с обычного старта; `n`, `--yes` или без терминала — стоп с
  кодом 3 и командой. Блок в середине прогона останавливает его, как раньше.
- Код 4 — `Verify` не прошёл за все попытки: работа агента лежит в дереве;
  доделать руками обычным циклом или запустить `run` снова.
- Код 5 — агент закоммитил файл плана, переписал историю или сменил статус
  юнита: разобрать коммит и план руками. Коммиты инструментов проекта,
  которые запускает юнит, раннеру не мешают.
- Код 7 — агент не справился: нет валидного result JSON, таймаут, лимит
  при `--no-wait`; причина — в логе.
- Закрытие плана раннер не делает: `bsv-docflow-close` вручную.

### Конфиг агентов

Конфиг — только для плана без исполнителей. TOML: `--config` >
`$DOCFLOW_AGENTS` > `$XDG_CONFIG_HOME/docflow/agents.toml` (`~/.config/…`);
файл из `--config` или `$DOCFLOW_AGENTS`, которого нет, — ошибка. Встроенные профили
`claude`, `codex`, `pi` и `opencode` (`docflow run --print-config`); файл накладывается на встроенные
профили по ключам (`model_extra` и `permissions` — тоже по ключам), добавляет новые профили
и накладывается на таблицу `[tiers]` ярус за ярусом, ключ за ключом:
`[tiers.<fast|default|strong|max>]` с ключами `agent` (имя профиля),
`model`, `effort`. Неизвестный ключ, неверный тип или ярус с несуществующим
профилем — код 2; прежние `models` и `default_agent` — тоже код 2 с
подсказкой, куда они переехали. Новый ассистент — конфиг, не код.

| Ключ профиля | Смысл |
|---|---|
| `cmd` | argv вызова; промпт — в stdin, если нет `{prompt}` |
| `model_args`, `resume_args` | добавляются к `cmd`, когда есть модель / сессия |
| `model` | модель профиля: берётся при `--agent` вместо модели яруса |
| `effort_args` | добавляются после `model_args` и `model_extra`, когда задано усилие |
| `model_extra` | таблица id модели (после маршрутизации) → аргументы после `model_args` |
| `permissions` | таблица режима прав плана → аргументы после `cmd` (`auto`/`full`); накладывается на встроенную по ключам; профиль без таблицы: `auto` — `cmd` как есть, `full` — код 2 |
| `result`, `text`, `session`, `error`, `cost` | пути `json:a.b` в JSON-выводе: result JSON, текст ответа, id сессии, флаг ошибки, стоимость |
| `tokens` | список путей `json:a.b`; сумма значений — токены вызова (`claude`: `usage.input_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`); ключа нет — токены не считаются |
| `stream` | декодер потока JSON Lines: `"claude"`, `"codex"`, `"pi"`, `"opencode"` или пусто; `claude` даёт квоту подписки и текущее действие агента, `pi` — объект `session`, `text`, `usage`, `cost`, `is_error`, `error`, `codex` — действие и сворачивает события в объект `thread_id`, `text`, `usage`, `is_error`, `error` для путей `json:`, `opencode` — сворачивает события `run --format json` в объект `session`, `text`, `usage`, `cost`, `is_error`, `error`; без декодера остаются только итоги |
| `output_tokens` | путь `json:a.b` к числу выходных токенов вызова (`claude`: `usage.output_tokens`) |
| `turns` | путь `json:a.b` к числу ходов агента в вызове (`claude`: `num_turns`) |
| `limit`, `limit_wait` | regex сообщения о лимите; ожидание, если время сброса не найдено (1800 с) |
| `auth` | regex сообщения «CLI агента не залогинен»: прогон останавливается сразу, без повторов |
| `timeout` | положительное число секунд на вызов; 0, отрицательное значение или отсутствие ключа — без таймаута. Наступивший, пока агент активен (последние события моложе 60 с или инструмент в работе), — не отказ: попытка продолжается на той же сессии, в итоге прогона строка `hint: <id> needs more than <cap> on <route>: split the unit or set timeout: in the plan header` |
| `idle_timeout` | секунд тишины потока без инструмента в работе, после которых вызов снимают как зависший: 0 — выключено, 5–86400; у встроенных профилей 1200 |
| `instructions` | текст в конец промпта юнита; только в режиме прав `auto` |
| `quota` | argv опроса квоты на старте `run`, без вызова модели; вывод разбирает `stream` (`claude`: текст `/usage`, `codex`: JSON-RPC `app-server`); пусто — не опрашивать; у Pi квота встроена для модели `zai/...`, ключ профиля не нужен |

Экран квоты настраивает таблица `[display]` — рядом с `[tiers]` и `[agents]`;
её ключи известны только эти, неизвестный ключ, значение или тип — код 2:

| Ключ `[display]` | Смысл |
|---|---|
| `quota` | `"used"` (по умолчанию) — доля израсходованного окна; `"left"` — остаток: процент, полоса, дельта и цвета считаются от него, пороги зеркальные (>50% зелёный, 21–50% жёлтый, ≤20% красный) |
| `resets` | `true` (по умолчанию) — время сброса окна в строке квоты: `↻ HH:MM` для окна 5h, `↻ Mon HH:MM` для более длинных; `false` — без него. В текстовом выводе время сброса, как и раньше, только с `-v` |

Плейсхолдеры в аргументах: `{prompt}`, `{model}`, `{effort}`, `{model_variant}`
(модель с вариантом `model#effort`, без усилия — модель без `#`; для
`opencode`), `{schema}` (JSON-схема
result inline), `{schema_file}`, `{session}`.

Свой `~/.config/docflow/agents.toml` накладывается на встроенный
(`docflow run --print-config`) по ключам:

```toml
[tiers]
default = {model = "opus"}    # ярус default теперь opus
fast = {model = "claude-haiku-x"}
strong = {agent = "codex", model = "<id модели OpenAI>", effort = "high"}

[display]
quota = "left"                # остаток подписки, а не израсходованное

[agents.claude.model_extra]   # модели без режима auto — явные права
claude-haiku-x = ["--allowedTools", "Write", "Edit", "Bash"]

[agents.codex]
timeout = 7200
```

Профиль `codex` запускает `codex exec --json --approve-for-me` в песочнице
workspace-write с сетью; запись вне репозитория агент просит с эскалацией,
её проверяет автоматический ревьюер. Модель — `-m`, усилие —
`-c model_reasoning_effort=`, продолжение сессии — `resume <thread_id>`.
Нужен собственный вход CLI (`codex login`).

Профиль `pi` запускает `pi -p --mode json`; промпт идёт в stdin. Модель —
`--model`, усилие — `--thinking` (`off`…`max`) один к одному, продолжение
сессии — `--session <id>`. В исполнителе плана модель — строка тройки как
есть: `executor: pi | zai/glm-5.3 | high`, `zai/glm-5.3-flash` (подписка
z.ai) или модель локального провайдера (`local-lan/<id>`). Квота Pi
опрашивается только для моделей `zai/…` — встроенным зондом API z.ai;
остаток других подписок Pi отдельной командой не отдаёт. Скиллы —
`docflow install-skills --agent pi`; в headless-режиме Pi пропускает
`.pi/skills/` без project trust (запись в `~/.pi/agent/trust.json` или
`--approve`), личный каталог trust не требует. Нужен вход в провайдера Pi.

Профиль `opencode` запускает `opencode run --format json --agent build`;
промпт идёт в stdin. Модель и вариант — одним аргументом
`--model provider/model#variant` (плейсхолдер `{model_variant}`; маршрут
без усилия — модель без `#`), продолжение сессии — `--session <id>`.
Режимы `auto` и `full` оба добавляют `--auto`: песочницы у OpenCode нет,
`--auto` снимает подтверждения, не отменяя явные запреты пользователя;
`full` изоляцией не является. Квота подписки go: `opencode api get
/api/experimental/usage/limits` отдаёт окна `rolling`, `weekly` и
`monthly` — процент использования, флаг `limited` и время сброса; docflow
печатает их в строке `quota:`, пропускает исчерпанное окно до сброса и
берёт из него сброс лимитного отказа. Запрос идёт через локальный сервер
opencode и генерации не тратит. Стоимость и токены декодер собирает из
`step_finish` (на подписке go cost 0). Отказ провайдера приходит
событием `error` — код выхода не сигнал. Пример тройки исполнителя:
`opencode | opencode-go/deepseek-v4.1-flash | high`. Скиллы —
`docflow install-skills --agent opencode` (`.opencode/skills` в проекте,
`~/.config/opencode/skills` лично). Нужен собственный вход CLI.

Профиль без `result` берёт result JSON из последнего блока ` ```json `,
без `resume_args` повторяет попытку полным промптом. Запуск —
`docflow run --agent codex` для всех юнитов или `agent = "codex"` в нужном
ярусе.

## Терминальное приложение

```
docflow tui    # полноэкранное рабочее место проекта в текущем терминале
docflow tui --attempts 1 --replans 0    # явные лимиты управляемого прогона
docflow tui --roster ~/work/roster.toml # другой файл ростера для экрана «Ростер»
```

Лимиты прогона задаются флагами: `--attempts N` — вызовы агента на юнит
(по умолчанию 3, не меньше 1), `--replans N` — авто-replan на фазу (по
умолчанию 3, `0` выключает). Действующие значения видны в диалоге старта
рядом с назначениями; обычный `docflow run` и его флаги не меняются.
`--roster PATH` выбирает файл ростера для экрана «Ростер» так же, как
`--roster` у `docflow roster`; без флага берётся
`$XDG_CONFIG_HOME/docflow/roster.toml`, иначе
`~/.config/docflow/roster.toml`.

Нужен интерактивный терминал: без TTY команда отказывает с кодом 2 и
указывает на обычные `docflow status`, `docflow prompt` и `docflow run`.
Минимальный размер экрана — 32x10; меньше — приложение просит растянуть
терминал. Мышь не используется, все действия — с клавиатуры. Платформы —
macOS, Linux и Windows; сборка одна, без runtime-зависимостей.

Рабочее место состоит из четырёх экранов; вкладки сверху —
`1 Проект  2 Ростер  3 Прогон  4 История`, справа состояние прогона
(`run:…`). От 100 колонок каждый экран показывает свои панели рядом, на
более узком терминале — одну панель, `Tab` переключает её. Нижняя строка
называет клавиши текущего экрана, `?` открывает помощь экрана с общими
клавишами отдельным блоком.

| Клавиши | Действие |
|---|---|
| `1`–`4` | экран: Проект · Ростер · Прогон · История |
| `q`, `Ctrl+C` | выход (живой прогон спрашивает) |
| `r` | перечитать рабочее место; на «Истории» — журналы прогонов |
| `s`, `R` | запустить текущий план Queue; продолжить checkpoint |
| `p`, `S`, `x` | пауза · остановка после юнита · остановка сейчас |
| `a`, `F`, `T`, `C` | activate · freeze · thaw · close плана |
| `Tab`, `Shift+Tab` | панель текущего экрана |
| `?`, `Esc` | помощь текущего экрана; закрыть поиск, диалог или overlay |

### Проект

Слева Queue с прогрессом `x/N` и полосой, Frozen и строка Backlog со
счётчиком; справа карточка выбранного плана, фазы или юнита: Goal,
маршруты шапки, последний прогон, Do, Verify, Depends, Handoff и блок
Recovery. Карточка плана предупреждает `⚠ вариант NAME меняет N ключей`,
когда активный вариант ростера расходится с шапкой. `Enter` на юните
открывает карточку; живой поток юнита — отдельный экран «Прогон».

| Клавиши | Действие |
|---|---|
| `↑/k`, `↓/j`, `PgUp/PgDn`, `Home/End` | перемещение по дереву |
| `Enter` | раскрыть или свернуть план, фазу, юнит; открыть карточку |
| `←/h`, `→/l` | свернуть или раскрыть выбранное |
| `Tab`, `Shift+Tab` | дерево и карточка |
| `/` | поиск по планам, фазам и юнитам |
| `d`, `v` | на карточке: git diff рабочего дерева · последний лог verify юнита |
| `N`, `e`, `c` | новый план · открыть редактором · коммит служебных файлов |
| `o` | параметры проекта, выбранного плана и следующей сессии |
| `b` | Backlog |
| `A` | шапка плана из активного варианта ростера |
| `Esc` | закрыть поиск, диалог, overlay или вернуться к дереву |

`N` спрашивает slug и запускает `docflow new`: появляются план `draft` и
строка Queue. `e` приостанавливает экран и открывает выбранный план
редактором (`$VISUAL`, затем `$EDITOR`; на Windows без переменных —
Notepad), после возврата рабочее место перечитывается. `c` показывает
изменённые файлы из `docs/docflow.md`, `docs/plans/`, `docs/archive/` и
`docs/roster.variants.toml` и последнюю подсказку `Commit:`;
подтверждение коммитит только эти пути.

`o` открывает параметры: проекта (`read_budget`, `start_read`,
`start_budget` из `docs/docflow.md`), выбранного плана (`permissions`,
`timeout`, `gate`) и следующей сессии (`attempts`, `replans`). Стрелки
выбирают строку, `Enter` редактирует и сохраняет одно значение. Правка
файла идёт через парсер docflow и проверяется `lint`; при отказе файл
восстанавливается из исходных байтов. `permissions: full` требует
отдельного подтверждения, что режим снимает песочницу агента. Лимиты
сессии действуют со следующего старта и живут только в памяти TUI.

`b` открывает Backlog: стрелки и `PgUp/PgDn` выбирают пункт, `+`
добавляет, `Enter` открывает многострочный редактор (`Enter` вставляет
перевод строки, `Ctrl+S` сохраняет, `Esc` отменяет), `D` удаляет пункт
после подтверждения. `P` на пункте приостанавливает TUI и запускает
интерактивный CLI агента в корне проекта: маршрут — первый `heavy`
свежего брифа ростера, без него первый `executor`; промпт просит взять
строку Backlog в план по скиллу `bsv-docflow-plan`. Тело плана пишет
агент. Недоступный CLI оставляет прокручиваемый промпт, `y` копирует его
через OSC 52 (нужна поддержка терминала). После возврата планы, Queue и
ростер перечитываются, а изменённые файлы нужно закоммитить до старта
прогона.

### Ростер

Рабочее место ростера: слева варианты трёх слоёв (`roster.toml`,
глобальный и проектный файлы вариантов) с отметкой активного пресета, в
центре доступы с переключателем, бюджетом, allowlist, `check`/`trusted` и
датами `off --until` и `expires`, справа цепочки ролей с бюджетом и
предупреждения. Экран пишет условия и файлы вариантов, а `roster.toml`
остаётся рукописным: TUI его не переписывает.

| Клавиши | Действие |
|---|---|
| `↑/k`, `↓/j`, `PgUp/PgDn`, `Home/End` | перемещение по вариантам или доступам; на цепочках — прокрутка |
| `Tab`, `Shift+Tab` | панель: варианты · доступы · цепочки |
| `Space` | на доступе: включить или выключить; диалог спрашивает дату `off --until`, пусто — бессрочно |
| `←/h`, `→/l` | на доступе: бюджет `prefer` · `normal` · `lean` · `minimal` · `off` |
| `Enter` | на доступе: модели каталога; на варианте: сделать активным пресетом; на v1-ростере: миграция |
| `a`, `x`, `Backspace` | в списке моделей: разрешить · запретить · снять условие |
| `Backspace` | на варианте: снять активный пресет |
| `n`, `D` | сохранить условия как вариант · удалить вариант машинного файла |
| `A` | шапка выбранного на «Проекте» плана: разница и запись |
| `u` | собрать каталог: `roster scan` без `--online`, в фоне |
| `Esc` | закрыть список моделей или вернуться на «Проект» |

`n` сохраняет действующие условия как вариант: диалог спрашивает имя, а
`Tab` выбирает слой — глобальный `roster.variants.toml` рядом с политикой
или проектный `docs/roster.variants.toml`, который коммитится с проектом.
Файлы вариантов машинные, TUI переписывает их целиком; комментарии и
ручной порядок `roster.toml` при этом не теряются. Имя обязано быть
уникальным во всех трёх слоях: дубль — ошибка политики с путями обоих
файлов. `Enter` на варианте делает его активным пресетом, `Backspace`
снимает; `D` удаляет вариант машинного файла, пресет `roster.toml`
удаляется только вручную. Условие, которое пресет выразить не может
(дата, запрет модели, уровень `normal`), — ошибка, а не вариант с другим
смыслом.

`A` открывает диалог шапки плана, выбранного в дереве на «Проекте»: у
«Ростера» нет своего списка планов. В диалоге — активный вариант, разница
`ключ: старое → новое` из `roster explain` и предупреждения ролей плана;
`Enter` пишет шапку тем же `roster apply`, `Esc` оставляет файл как был.
Отказ (открытый юнит без цепочки, чужой `run.lock`, ошибка `lint`)
остаётся в диалоге рядом с разницей. Успешная запись даёт notice
`commit: Pxxx: apply roster`: шапка меняет файл в рабочем дереве, и до её
коммита `prompt` откажет на грязном дереве.

`u` собирает каталог так же, как `docflow roster scan` без `--online`:
скан идёт в фоне, в нижней строке стоит `scanning…`, по завершении —
сводка доступов с числом моделей. Полные предупреждения источников —
строками в панели цепочек. Отсутствующий `roster.toml` экран не создаёт,
v1-ростер показывает объяснением и открывает миграцию по `Enter`:
предпросмотр нового текста с прокруткой, `Enter` пишет файл с бэкапом
`roster.toml.bak`, `Esc` не пишет ничего.

### Прогон

Сводка прогона, юниты плана и живой поток выбранного юнита на всю ширину.
Шапка показывает план, время прогона, позицию `n/m`, попытку `k/N`,
токены usage и текущий маршрут; неизвестные значения — `?`. Слева юниты
со статусом, длительностью и маршрутом, под ними этапы текущего юнита
`prompt · work · verify · done · commit`.

| Клавиши | Действие |
|---|---|
| `↑/k`, `↓/j`, `PgUp/PgDn`, `Home/End` | движение по записям потока |
| `Enter` | раскрыть или свернуть запись |
| `Tab` | панели юнитов и потока |
| `t` | свернуть все рассуждения до первой строки или раскрыть обратно |
| `[` `]` | листать большой результат или сообщение по 4 KiB |
| `f`, `End`, `G` | включить follow и перейти к новейшей записи |
| `/` | поиск по потоку; `Esc` очищает |
| `d`, `v` | git diff рабочего дерева · последний лог verify юнита |
| `Esc` | закрыть overlay, поиск или вернуться на «Проект» |

Рассуждения идут полным текстом, приглушённо, с префиксом `◇`; `t`
сворачивает все блоки до первой видимой строки и обратно. Сообщения
агента показываются целиком. Вызов инструмента занимает одну строку
`⚙ имя · аргумент · состояние · длительность`, `Enter` открывает его
результат страницами, `✎ путь` отмечает изменённый файл. Дельты одного
сообщения объединяются в один блок, а текст блока ограничен 64 KiB:
продолжение читается страницами из лога вызова. Вытеснение старых
записей не теряет сводку времени, usage и этапов.

### История

Список прошлых прогонов, новейшие сверху, и карточка выбранного: id,
план, начало, длительность, числа done/failed/blocked, вызовы (включая
повтор и fallback), смены маршрута и replan, токены usage, причина и код
завершения. Неизвестное показано `?`, незавершённый журнал не получает
выдуманный код или длительность.

| Клавиши | Действие |
|---|---|
| `↑/k`, `↓/j`, `PgUp/PgDn`, `Home/End` | выбор прогона или прокрутка карточки |
| `Tab` | список и прокручиваемая карточка |
| `Enter` | открыть выбранный прогон на «Прогоне» в режиме просмотра |
| `r` | перечитать журналы |
| `Esc` | вернуться из просмотра в историю |

Просмотр восстанавливает поток из журнала и логов вызовов: план и
checkout lock ему не нужны. `Tab` открывает панель юнитов, стрелки
выбирают юнит, `Enter` возвращает фокус потоку. Управляющие клавиши
прогона в просмотре отказывают с подсказкой, `1` возвращает живое рабочее
место. Отсутствующий лог вызова даёт блок `лог недоступен`, остальной
поток остаётся читаемым.

### Исполнители

Назначения прогона берутся только из шапки плана (`executor`, роли,
`fallback:`, `replan:`) — так же, как в `docflow run`. Пери-прогонный
оверлей (редактор `m` и `<git-dir>/docflow/tui/configuration.json`)
удалён: изменить маршруты плана можно правкой плана или применением
варианта ростера к шапке. Старый файл `configuration.json` на диске
игнорируется без ошибки и удаляется вручную.

Диалог старта показывает все эффективные назначения: открытые юниты и
роли, порядок маршрутов и резервные ступени. После исчерпания лимита
провайдера раннер переключается на следующую ступень, поэтому фактический
исполнитель может отличаться от первого — назначения из плана
подчиняются `fallback:`. Приложение по умолчанию запускает с тремя
попытками на юнит и тремя replan на фазу; лимиты меняются флагами
`--attempts`/`--replans` команды `docflow tui`, а режим прав, таймаут и
`replan:` остаются из плана.

### Пауза, остановка и выход

- `s` — старт текущего плана Queue; с «Проекта» открывается «Прогон».
  Раннер сам показывает подтверждение с режимом прав, предусловиями и
  назначениями; отказ ничего не запускает.
- `p` — пауза: текущий вызов агента прерывается, дочерние процессы
  останавливаются, устойчивая граница дописывается и пишется checkpoint.
  `Paused` появляется только после этого. Время паузы не расходует
  таймаут, а уже потраченные токены учтены.
- `S` — остановка после текущего юнита: юнит доводится до done/commit,
  прогон завершается успешно. Это не пауза и checkpoint не нужен.
- `x` — остановка сейчас без checkpoint: журнал пишет `stopped` и код 0,
  продолжить такой прогон нельзя, его начинают заново.
- `q` или `Ctrl+C` при живом прогоне сначала спрашивают: остаться или
  остановить и выйти. После закрытия агент не продолжает работу.
- Закрытие терминала и сигналы (SIGINT, SIGTERM, SIGHUP) идут тем же
  путём паузы: процесс не завершается, пока не записан checkpoint и не
  освобождён checkout lock.

### Блок человека и восстановление

Если прогон остановился на `needs human`, после остановки предлагается
`Continue`: введите заметку — приложение выполнит `docflow unblock` с ней
и запустит прогон снова. Проверка условия остаётся за агентом, как в CLI.

Checkpoint лежит в `<git-dir>/docflow/tui/checkpoint.json`. При первом
успешном открытии и после завершения прогона приложение сводит его с
планом, HEAD, отпечатком плана и новейшим журналом и показывает диалог
восстановления:

- `R`/`Enter` продолжает прерванный юнит с тем же agent/model/effort;
  незавершённый коммит доводится существующим циклом, юнит не выполняется
  заново. После смены исполнителя или недоступной сессии стартует новая
  сессия с полным промптом и сводкой прерывания.
- `s` начинает новый прогон. Если план или HEAD сдвинулись, юнит уже
  завершён, а также для паузы внутри `replan` или `close`, `R`
  отказывает с причиной: такие операции не возобновляются, план
  остаётся восстановленным.
- Повторные перезагрузки и собственная пауза приложения не открывают
  диалог заново: исход остаётся в статусной строке и карточке юнита.

### Ограничения

- Один управляемый прогон на checkout. Живой чужой раннер не
  перехватывается: просмотр разрешён, запуск, `R` и действия жизненного
  цикла отказывают с его pid. Нечитаемый lock считается неизвестным, а
  не свободным. Lock перечитывается в момент каждого действия.
- Lifecycle-клавиши и `unblock` выполняют те же проверки, что CLI, через
  общий код; собственных послаблений у приложения нет.
- Пути логов в событиях относительны корня checkout и разрешаются в
  момент чтения: приложение можно запускать из подкаталога.
- Ограничения терминала: нет мыши, узкий экран показывает одну панель,
  альтернативный экран восстанавливается при выходе, а очень большой
  diff усечён с пометкой.
- Вывод агента, включая рассуждения и логи, проходит очистку
  escape-последовательностей: управляющие коды из потока не исполняются.
- На юнит приходится ограниченное число записей потока: старые вытесняются,
  но сводка времени, usage и этапов остаётся.

Устройство и события — [design/tui.md](design/tui.md) и
[design/runner.md](design/runner.md#интерактивный-хост).

## Ростер

Ростер подбирает маршруты ролей при составлении плана, а не во время
прогона: `docflow roster brief` показывает цепочки, бюджеты и объяснение,
`docflow roster apply Pxxx` пишет их в шапку плана. `run`, `lint` и
`cycle` ростер не читают, формат плана остаётся `docflow: 3` —
[P036](archive/P036-roster.md). Устройство подсистемы, правила резолвера и
бюджета — [design/roster.md](design/roster.md); локальный маршрут
`strata/…` отображается как `Local` без квоты
([P043](archive/P043-local-worker.md)).

Ростер состоит из файлов:

| Файл | Что это |
|---|---|
| `~/.config/docflow/roster.toml` | политика: доступы, allowlist, доверие, классы моделей, роли, пресеты; рукописный файл |
| `$XDG_CACHE_HOME/docflow/roster/catalog.json` | каталог: что нашли `scan` и пробы авторизации; расходный кэш вне рабочего дерева |
| `~/.config/docflow/roster.state.toml` | временные условия: выключения, бюджеты, expiry, сужения моделей |
| `~/.config/docflow/roster.variants.toml` | глобальные варианты: пресеты, созданные в `docflow tui`; машинный файл |
| `docs/roster.variants.toml` | варианты проекта от корня checkout; машинный файл, коммитится с проектом |

Путь политики переопределяется `--roster PATH`; файл состояния лежит
рядом и называется так же с `.state.toml`, глобальный файл вариантов —
`roster.variants.toml` там же. Нет файла состояния — нет условий, это не
ошибка; нет файла вариантов — пустой слой, тоже не ошибка.

Пресеты трёх слоёв — `roster.toml`, глобальные и проектные варианты —
сливаются, а имя обязано быть уникальным во всех трёх: дубль — ошибка
политики с путями обоих файлов, ведь `--preset NAME` должен значить одно
и то же. `roster.toml` человек правит руками, файлы вариантов TUI
переписывает целиком. Создаёт, выбирает и удаляет варианты, правит
условия и применяет их к шапке плана экран «Ростер» в `docflow tui`;
CLI-команды вариантов не пишут.

### Каталог

```sh
docflow roster scan            # Pi, OpenCode, Codex/Claude, auth-пробы
docflow roster scan --online   # плюс необязательные метаданные models.dev
docflow roster models          # модели доступов из ростера
docflow roster models zai      # модели одного доступа
docflow roster status          # каналы, auth, число моделей, условия
```

`scan` пишет кэш и печатает сводку доступов. Проблема одного источника
(нет CLI, HTML вместо JSON, битый кэш) — предупреждение в stderr, код
успеха остаётся 0; каталог при этом частичный. Модели и пробы не
вызываются, квота не тратится, значения ключей не печатаются.
`models` и `status` читают только кэш и не сканируют; пустой кэш — код 0 с
подсказкой `docflow roster scan`, неизвестный `models ACCESS` — код 2 со
списком известных доступов. Неизвестные контекст, `max_out` и цена
печатаются как `unknown`, а не нулём.

### Политика `roster.toml`

Версия формата — `version = 3`. Ростер старого формата (v1 без версии,
v2 с `[model]`/`[effort]`) даёт код 2 и подсказку `docflow roster migrate`.

```toml
version = 3

[access.opencode-go]
agents  = ["pi", "opencode"]   # два канала, один доступ и одна квота
kind    = "subscription"       # subscription | metered | local
budget  = "prefer"             # prefer | normal | lean | minimal | off
trusted = true
models  = ["deepseek-*"]       # allowlist; нет ключа — все модели
exclude = []

[access.zai]
agents = ["pi"]
kind   = "subscription"
budget = "lean"
check  = true                  # нужен независимый ревьюер
models = ["glm-5.3*"]

[access.codex]
agents = ["codex"]
kind   = "subscription"
budget = "minimal"             # только acceptance и replan
trusted = true

[access.claude]
agents  = ["claude"]
kind    = "subscription"
budget  = "normal"
trusted = true

[access.local]
agents = ["pi"]
kind   = "local"
budget = "off"
check  = true

[role]
cheap      = "cheap"
executor   = "standard"
heavy      = "strong"
review     = "standard"
acceptance = "trusted"
replan     = "trusted"

[route."zai/glm-5.3"]
high = "strong"                # усилие → класс

[route."codex/gpt-6.1-sol"]
medium = "strong"

[preset.low]
off     = ["claude", "local"]
lean    = ["zai"]
minimal = ["codex"]
prefer  = ["opencode-go"]
order   = ["opencode-go", "zai", "codex"]
models  = { zai = ["*flash*"] }
```

`[access]` — стабильная политика. Доступ — единица квоты и
независимости: `opencode-go` через `pi` и через `opencode` — один доступ,
и fallback повторяет доступ, а не пару `agent|model`. `agents`
обязателен. `check` и `trusted` взаимоисключающи: доступ, требующий
независимой проверки, не судит. `budget = "minimal"` требует
`trusted = true`, иначе это ошибка политики. `[role]` обязан объявить все
шесть ролей. `[route."ACCESS/MODEL"]` — таблица «усилие → класс»:
класс принадлежит паре «модель + усилие», `"-"` — усилие не передавать.
Модель без записи в `[route]` отдаётся с автоматическим классом по
семейству (`flash/mini/lite → cheap`, `pro/sol/opus → strong`, остальное
`standard`) и усилием по лестнице классов. `[preset]` — сохранённый набор условий; `off/lean/minimal/
prefer` взаимоисключающи на один доступ, `order` ставит доступы первыми,
`models` сужает allowlist (пустой список — ни одной модели), а
`check`/`trusted` пресет не переопределяет.

Бюджет доступа задаёт роли: `prefer`/`normal` — все, `lean` — без
`heavy`, `acceptance` и `replan`, `minimal` — только `acceptance` и
`replan`, `off` — никакие. Резолвер выбирает минимальный подходящий класс,
затем цену `input + output`, затем больший контекст, затем id; неизвестная
цена идёт после известной.

### Условия

Постоянное условие пишется в `roster.state.toml` и не меняет политику:

```sh
docflow roster off claude --until 2026-11-30  # до конца дня включительно
docflow roster on claude                      # снять off, дату и бюджет off
docflow roster budget codex minimal
docflow roster expire zai 2026-12-31
docflow roster allow zai '*flash*'            # сузить allowlist
docflow roster deny zai '*-thinking'          # скрыть модели
docflow roster reset                          # удалить файл состояния
```

Временное условие может сузить стабильный allowlist, но не расширить.
Неизвестный доступ, уровень или пресет — код 2 до записи: опечатка в
мёртвом условии должна падать. Истёкший `off` отбрасывается при загрузке,
файл переписывает только следующая мутация.

Разовое условие — флаг вопроса, он применяется в памяти и не
сохраняется:

```sh
docflow roster brief --off claude,local --minimal codex --lean zai \
  --only 'zai=*flash*' --prefer opencode-go
docflow roster brief --preset low
```

`--preset NAME` применяет пресет политики; `--off`, `--minimal`, `--lean`,
`--prefer` (списки доступов через запятую), `--expires A=DATE` и
`--only A=GLOB` действуют на один вызов. Те же флаги принимает `roster
apply`: бриф и запись шапки видят одно и то же условие, а
`roster.state.toml` не меняется. Постоянное условие — только команды
`off`/`on`/`budget`/`expire`/`allow`/`deny`/`reset`.

### Бриф, объяснение и применение

```sh
docflow roster brief
docflow roster show             # алиас brief
docflow roster explain P055
docflow roster apply P055 --preset low --dry-run
docflow roster apply P055 --preset low
docflow roster apply P055 --off claude,local --minimal codex --lean zai \
  --only 'zai=*flash*' --prefer opencode-go
```

`brief` печатает условия в силе, по строке на роль (`chain`, `budget`,
`scope`), матрицу `review:`, раздел `why:` с объяснением выбора и
предупреждения. `budget` — рекомендация чтения для нарезки юнита, а не
ключ плана и не проверка `lint`; у судейских ролей бюджета нет, их
`scope` — `diff/test`. Пустая цепочка роли и цепочка из одного маршрута —
предупреждения брифа: он не знает, какие роли использует план. `apply`
отказывает до записи, если пустая цепочка нужна открытому юниту. Если
`check`-доступ остался без независимого ревьюера — ошибка политики, а не
self-review.

`explain PLAN` сравнивает шапку плана с брифом и печатает
`ключ: старое → новое` и предупреждения только тех ролей, которые план
использует; файлы он не меняет.

`apply PLAN` пишет в шапку `docs/plans/` ключи `executor:`, `fallback:`,
`replan:` и ключи ролей, на которые ссылается `Role:` хотя бы одного
юнита. Ключи ролей без юнитов удаляет, `Executor:` юнитов не трогает,
прочие ключи и их порядок сохраняет, новые ставит после
`executor:`/`fallback:`. Открытый юнит, которому условия не дают цепочки
`executor` или его роли, останавливает `apply` до записи: иначе план
ушёл бы в legacy-маршрут или упал бы на `lint` уже после правки. План —
`draft`, `active` или `frozen`, иначе код 2; идёт прогон (`run.lock`) —
код 5. После записи план проверяется
`lint`, при ошибке файл восстанавливается — код 2. Предупреждения
(юнит с `Executor:` вне текущих условий, `Read:`-прокси больше бюджета,
роль без fallback) идут в stderr и не меняют код успеха. Изменений нет —
код 1; `apply` не коммитит. `--dry-run` печатает изменения без записи,
`--json` сохраняет код выхода.

Пример приёмки: `claude` и `local` выключены, `codex` по минимуму, `zai`
только flash, `opencode-go` первым. `brief` даёт `executor` —
`opencode-go/deepseek-v4.1`, `cheap` — `opencode-go/deepseek-v4.1-flash >
zai/glm-5.3-flash`, `heavy` пуст, `review` — `opencode-go/deepseek-v4.1`,
`acceptance` и `replan` — `codex/gpt-6.1-sol`; `apply` пишет эту шапку, а
`run --dry-run --all` показывает маршруты юнитов и `fallback:` уже без
участия ростера.

### Миграция

```sh
docflow roster migrate           # напечатать v2-политику
docflow roster migrate --write   # заменить roster.toml, сохранив .bak
```

`migrate` переводит `spend`, `[provider]`, `[role]`, `[route]` и
`[profile]` в доступы, классы, `[effort]` и пресеты; профиль становится
пресетом, а доступы, которые профиль не называет, получают `off` — так
«беречь claude» сохраняется. Уже v2-ростер — код 2, ничего не пишется.
Любая другая команда на старом файле даёт код 2 с подсказкой
`docflow roster migrate`; флаг `--profile` удалён вместе с форматом, его
место занял `--preset`.

## Бенчмарк

Эталонный корпус сравнивает выполнение задач `small`, `medium` и `large` на
общей базе. Сначала проверьте, что скрытые оракулы падают на базе и проходят
на эталонных решениях:

```sh
go run ./tools/bench validate --task all
```

Перед живым запуском просмотрите задачи, маршруты и рабочие пути:

```sh
go run ./tools/bench run --task all --dry-run
```

Затем запускайте выбранные задачи, например:

```sh
go run ./tools/bench run --task small

Прогон вызывает модели, расходует квоту и может идти долго; `large` занимает

`bench/results/`; `run --results DIR` выбирает другой каталог внутри checkout.
Перестроить таблицу тренда из записей можно командой (для другого каталога
добавьте `--results DIR`):

```sh
go run ./tools/bench report
```

## Блок и replan

- План разошёлся с кодом, `Verify` не проверяет честно, три `verify`
  подряд без прогресса → `docflow block <id> --reason "…"`; выдача юнитов
  останавливается (код 3).
- Шаг, который доступен только человеку (вход в аккаунт, устройство,
  доступ, решение) → `docflow block <id> --reason "…" --needs human`;
  прогон встаёт (код 3), `status` по последнему пункту `Blocked` печатает
  `(needs human)` и строку `unblock:` с командой.
- Снял человеческий блок сам человек:
  `docflow unblock <id> --note "что сделано"` → юнит снова `[~]`, в
  Handoff — пункт `Unblocked: …`; снятый юнит сначала проверяет условие
  блока, заметка — заявление, не доказательство. Команда не коммитит и
  блок `plan` не снимает (код 5).
- Replan правит только юниты `[ ]` и `[!]`; новые юниты — следующими
  номерами, существующие не перенумеровываются.
- Replan не трогает опорные проверки: `Verify:`, `Do:`, `Role:` юнитов
  `Role: review` и `Role: acceptance` и их переход в `[-]` запрещены;
  статус и `Depends:` опорных юнитов менять можно. Открытый юнит не
  помечается `[x]` — раннер `[x]` пропускает, проверка исчезла бы молча.
- Смену `Verify:` обычного юнита docflow записывает в `## Decisions` сам:
  пункт `Replan changed check: …` виден в сводке прогона и в промптах
  review и acceptance. Правки тестов юнита помечает его коммит: блок
  `Test changes:` в теле и строки `test change:` в выводе — они видны
  ревью, приёмке и человеку.
- Файлы коммита, которых не называют `Read/Do/Traps/Verify` юнита (путь, имя
  файла или каталог; файл плана не считается), раннер печатает под юнитом
  строками `outside Do:` — подсказка человеку, юнит не падает.
- Снятие блока `plan`: незакоммиченная работа остаётся в силе → `[~]`; работа
  не нужна → решает пользователь; работы нет → `[ ]`; юнит не нужен → `[-]`.
- `verify --skip "<причина>"` — только когда проверку нельзя запустить в
  окружении (нет устройства, сети) и пользователь согласен.

## Закрытие

`docflow run --close` поручает агенту закрыть план после последнего юнита
или сразу, если план уже `ready to close` при старте. Используется цепочка
`cheap:`, без неё — `executor:` + `fallback:`; маршрут виден в
`docflow run --dry-run --close`. Без `--close` раннер оставляет готовый план
для отдельного закрытия.

Агент следует `bsv-docflow-close` и сам выполняет шаги ниже. Раннер проверяет
удаление файла плана, наличие архивной записи, `docflow lint` и допустимые
пути изменений (`docs/`, `CHANGELOG.md`, `README.md`, `README.ru.md`), затем
коммитит `<id>: close plan`. Провал проверки — код 2 со списком причин;
изменения сохраняются для исправления. Вызовы записаны в
`<git-dir>/docflow/run/<id>.close<N>.out`, результат — в событии `close`
[потока JSONL](design/runner.md).

1. `docflow status` пишет `ready to close` — все юниты `[x]`/`[-]`.
2. Ссылки на `docs/plans/Pxxx…` переводятся на будущую архивную запись.
3. `docflow close Pxxx` — архивная запись с перенесёнными `## Decisions`;
   план и строка Queue удаляются.
4. Агент заполняет запись: `Outcome`, сжатые `Decisions`, `Gotchas`,
   `Follow-ups`.
5. Architecture — текущее устройство и ссылка на запись; README — строки
   состояния; CHANGELOG — наблюдаемое поведение (нет файла — шаг
   пропускается); Follow-ups — строками в Backlog, включая незакрытые
   пункты Handoff `Unverified: …`; только наблюдение вне Goal, ждущее
   внешнего события, остаётся в записи строкой `Waits: …`.

Брошенный план закрывается так же: оставшиеся юниты вручную в `[-]`, в
`Decisions` — `план брошен — почему — что вместо`.

## Что куда идёт

| Информация | Место | Кто пишет | Живёт до |
|---|---|---|---|
| Идея, задача | строка `## Backlog` в `docs/docflow.md` | человек, `close` из Follow-ups | взятия в план |
| Порядок планов | `## Queue` в `docs/docflow.md` | `new`, `close` | закрытия плана |
| Цель, рамки, ловушки плана, repro | шапка плана | `bsv-docflow-plan` | закрытия плана |
| Что сделать в сессии | юнит: `Read`, `Do`, `Verify`, `Traps`, `Commit` | `bsv-docflow-plan` | закрытия плана |
| Статус юнита | маркер `[ ]` `[~]` `[x]` `[-]` `[!]` в плане | `docflow` | закрытия плана |
| Записка следующему юниту | `Handoff:` юнита | `docflow done` | закрытия плана, в архив не идёт |
| Решение по ходу | `## Decisions` плана | `docflow done --decision`, планировщик | переносится в архив |
| Почему так (закрытое) | `docs/archive/Pxxx-slug.md` | `close` + `bsv-docflow-close` | навсегда; правка — только `superseded_by` |
| Ловушки после закрытия | `## Gotchas` архивной записи | `bsv-docflow-close` | навсегда |
| Несделанное | `## Follow-ups` записи → Backlog, кроме `Waits:` | `bsv-docflow-close` | взятия в план |
| Текущее устройство | architecture проекта + ссылка на архив | `bsv-docflow-close` | пока решение действует |
| Текущее состояние | `README.md` | `bsv-docflow-close` | следующего изменения |
| Что изменилось для пользователя | `CHANGELOG.md` | `bsv-docflow-close` по `bsv-changelog` | навсегда |
| Изменения кода | git-коммит юнита | `docflow commit` | навсегда |
| Счётчики тестов, логи сборки | ответ в чате | агент | — в доки не пишется |

Отменённое решение: в architecture правится на новое, у старой архивной
записи — `superseded_by: Pyyy` во frontmatter.

## Ветки

- Один план — одна ветка или worktree; параллельно — только разные планы.
- Ветки создаёт и переключает пользователь, `docflow` их не проверяет.
- Совпадение id планов из разных веток ловит `lint` после merge.

## Типовые ситуации

| Ситуация | Что делать |
|---|---|
| `prompt`: `working tree is dirty` (код 5) | чужие изменения: закоммитить или убрать самому, агент их не трогает |
| `prompt`: `… is in progress` | другой юнит `[~]` — продолжить его: `docflow prompt` без id |
| `verify` падает (код 4) | исправить по хвосту вывода; три раза без прогресса — `block` |
| `status`: `blocked:` + `unblock:` (код 3) | сделать шаг самому, затем `docflow unblock <id> --note "что сделано"` |
| `status`: `blocked:` (код 3) | replan через `bsv-docflow-plan` |
| `status`: `ready to close` | закрыть через `bsv-docflow-close` |
| `next`/`prompt`: делать нечего (код 1) | очередь пуста или все планы ждут `close` |
| Код 2 и подсказка `docflow migrate` | формат старой версии: `docflow migrate`, затем `lint` |
| Мелкая правка что-то решила | `docflow note <slug>` — запись в архиве без плана |
| Нужно пропустить юнит | replan: `[-]` |
| Отложить план на время | `docflow freeze <id> --reason "…"` + коммит, затем `docflow thaw <id>` + коммит когда вернуться |
| Юнит меняет несколько репо | в плане указан ключ `repos:`, агент не коммитит сам — `docflow commit` охватит все |
