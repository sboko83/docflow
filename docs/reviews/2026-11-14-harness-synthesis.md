## Ограничения, названные 2026-11-14

- Claude Code использовать нельзя — выбывает из кандидатов на любую роль.
- ZCode: приложения нет, пуши недоступны — Remote Control не канал.
- OpenCode: срок выхода мобильного приложения неизвестен.
- Есть Apple-аккаунт (iOS-приложения доступны) и свой VPS (always-on хост
  и self-host доступны).

Это снимает два открытых вопроса
[харнес-пульта](2026-11-13-harness-control-plane.md#открытые-вопросы):
always-on хост есть, мобильный клиент не обязан быть продуктом вендора.

## С чем сходятся все пять

1. **Узкое место — канал человека, не runner.** Блоки и лимиты —
   осознанная политика unattended-безопасности; проблема в том, что
   человеку нечем прийти к стопу. Состояние для удалённого пульта уже
   есть в коде (события JSONL, `runner.Control`, checkpoint, пауза/резюм)
   — не хватает сетевого слоя и политики эскалации.
2. **Модель не владеет состоянием плана.** «Модель вместо `docflow run`»
   в лоб теряет три работающих свойства: юнит = свежий контекст, проверка
   не автором, коммитится ровно проверенное дерево. Docflow сохраняет
   формат плана, SDD, `verify→done→commit`, ростер как данные, атомарные
   команды (`status/next/prompt/verify/done/commit/block/unblock`).
3. **Политику блоков переписывать в любом варианте:** класс блока → свой
   путь (ошибка реализации → ремонт; устаревший путь → локальный replan;
   повтор → другой исполнитель; лимит → ожидание/смена маршрута; решение
   человека → вопрос). Эскалация — «нет допустимого следующего действия»,
   а не сам факт неудачи.
4. **Ничего не проверено живьём.** Все пять записок — анализ по
   документации на 2026-11-12. Пилот обязателен до любых изменений.

## Чем разрешились споры

- **Walker против supervisor → supervisor.** Walker (юнит = сессия, модель
  ведёт план) переносит в промпт то, что Go делает детерминированно и с
  тестами: квоты, fallback-цепочки, ожидание сброса, resume, fingerprint
  дерева; контекст растёт; юнит идёт 10–60 минут против ~10-минутного
  лимита хода в харнесе. Supervisor оставляет `docflow run` двигателем,
  видит только стопы — контекст не растёт, и для пилота не нужен ни один
  обход харнеса. Оговорка [пульта](2026-11-13-harness-control-plane.md):
  модель в любой из ролей должна ходить через инструменты docflow, а не
  владеть состоянием.
- **Архитектура.** Из трёх (A: run + свой тонкий пульт; B: docflow как
  MCP, ведёт агент; C: харнес как runtime) пульт по A «нужен в любом
  варианте и не сужает ростер»; B и C — только по данным пилота.
- **Промпт supervisor'а уже готов** в харнес-нейтральном виде:
  [четыре примитива](2026-11-13-supervisor-prompt.md) RUN_BG / WAIT_EXIT /
  NOTIFY / ASK, мандат, жёсткие лимиты, запись `- Supervisor:` в
  `## Decisions`, метрики. Headless-режим (петля-скрипт + одноразовый
  агент на стоп) не требует харнеса вообще.

## Сборная рекомендация

Слои разделяются; каждая записка внесла свой кусок.

1. **Движок** — `docflow run` остаётся: юниты, квоты, verify/commit,
   replan. Замена — только по данным пилота.
2. **Supervisor** — headless-петля на VPS + промпт из черновика.
   Supervisor'у не нужен харнес с пушами: пуши живут в канале, а не у
   модели. Роль supervisor'а может играть любой CLI (zcode, `opencode
   run`, `codex exec`); модель — дешёвая, она спит и разбирает стопы.
3. **Канал — Telegram.** «Приложение с пушами» уже есть; строить нужно
   только мост. Telegram-бот закрывает все четыре примитива: пуш
   (NOTIFY), вопрос с кнопками, ответ = продолжение петли (расширяет
   headless ASK из черновика, где он был «NOTIFY + стоп»), кнопки
   pause/stop/continue. ntfy — запасной канал. Стоимость 1–2 дня,
   полный ростер, без чужих серверов.
4. **Страховка в docflow** — заменить жёсткий выбор
   `osascript`/`notify-send`/`\a` настраиваемой командой уведомления
   (обобщение существующего; заморозку роста формата не задевает).
   `docflow serve` (SSE из потока событий) — только если понадобится
   план-уровень UI.
5. **Готовые харнесы — вторая линия.** HAPI self-host на VPS (PWA/Web
   Push/Telegram; нативные приложения платные) и T3 Code — спайком, если
   тонкого канала не хватит или захочется готовый план-уровень UI.
   Политика (park & continue, общий бюджет прогона, структурный вопрос,
   один класс — один путь) — по данным первых прогонов, не заранее.

**Первый шаг:** петля supervisor + Telegram-бот на VPS, маленький план
3–4 юнита, метрики из промпта. Один прогон проверяет и канал, и
supervisor.
