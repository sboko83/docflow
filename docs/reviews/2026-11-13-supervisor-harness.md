# Дирижёр поверх docflow в харнессе с мобильным клиентом — 2026-11-13

Заметка-оценка, не решение. Ничего в коде и формате не меняет.

## Вопрос

Задумка docflow: план режется на юниты, разные модели исполняют и
проверяют друг друга с учётом лимитов подписок, человек получает пуш только
когда нужно его решение. На деле:

1. Сложный план почти на каждом шаге встаёт: блок, `replan limit reached`,
   `review budget spent`.
2. `docflow run` живёт в терминале, управлять им неудобно.
3. Пушей нет: конец прогона — `osascript`/`notify-send`/`\a` на той же
   машине ([runner.md](../design/runner.md#вывод-прогона)). О стопе
   узнаёшь, только глядя в терминал.

Предложение: оставить планирование, формат, ростер и роли; вместо
`docflow run` запускать в харнессе с мобильным приложением модель, которая
ведёт план по правилам и разбирает возникшие проблемы.

## Короткий ответ

Получится, но не в том виде, «модель вместо `docflow run`». Получится как
**дирижёр поверх `docflow run`**: раннер остаётся детерминированным
двигателем, модель в харнессе — слой решений между раннером и человеком.
Харнесс — Claude Code (Remote Control + мобильное приложение Claude).

И важное: смена харнесса закрывает проблемы 2 и 3, но не 1. Частые стопы —
свойство защит раннера, а не терминала. Дирижёр помогает с 1 только
потому, что принимает решения, которые сейчас ждут человека. Это надо
делать явно и с аудитом, иначе он тихо снимет защиты, ради которых они
вводились.

## Почему стопы частые

Стоп с кодом 3 — это каждый случай, где раннер не уполномочен решать:

- `blocker: human` — агент считает шаг человеческим (часто перестраховка:
  нет доступа, «нужно подтверждение», неоднозначность в плане);
- `blocker: plan` сверх лимитов: 2 replan на юнит, 3 на фазу
  ([P037](../archive/P037-replan-phase-limit.md));
- опорный юнит с третьим `Blocked (plan)` — `review budget spent`
  ([P056](../archive/P056-resilient-runs.md));
- нарушение правил replan (`check_replan`) — план откатывается.

Каждая защита оправдана отдельно: ревью без них ходило по кругу (P052:
юнит ревью блокировался 10 раз, 19 юнитов исправлений), replan без них
переписывал проверки. Но в сумме у автономного прогона два исхода —
«справился сам» и «стоп, ждём человека», третьего нет. Чем сложнее план,
тем чаще второй. Человек на стопе обычно делает одно из немногих: снимает
блок с заметкой, сам чинит мелочь, переносит находку в Handoff, добавляет
юнит, перезапускает. Это и есть работа для дирижёра.

## Два варианта

### А. Модель вместо `docflow run`

Модель сама читает план, вызывает `docflow prompt`, запускает исполнителя
(`codex exec`, `opencode run`, `pi`…), гоняет `verify`/`done`/`commit`.

Против:

- в промпт переезжает то, что Go делает детерминированно и с тестами:
  квоты, fallback-цепочки, ожидание сброса, таймауты, детект зависания,
  resume сессии, поток событий, отпечаток дерева;
- контекст дирижёра растёт с каждым выводом исполнителя — ровно та
  деградация длинной сессии, от которой docflow и защищает;
- юнит идёт 10–60 минут, вызов команды в харнессе обычно ограничен
  ~10 минутами: всё равно нужен фон и пробуждение по событию;
- классификатор авто-режима Claude Code уже отказывал в запуске агента с
  `danger-full-access` напрямую (dsh, 2026-11-08) — модель, сама
  запускающая исполнителей с полными правами, будет упираться в это
  постоянно.

### Б. Дирижёр поверх `docflow run` (рекомендую)

```
телефон ── пуш / ответ ──▶ харнесс (сессия-дирижёр)
                              │  фон: docflow run --yes
                              │  пробуждение: выход процесса
                              ▼
                     docflow run (Go): юниты, квоты, fallback,
                     verify/commit, replan, события JSONL
                              │
                     исполнители по ростеру
```

- Дирижёр запускает `docflow run --yes` фоном и спит. Харнесс будит его
  по выходу процесса (код и последняя строка `run_end.reason` в
  `<git-dir>/docflow/run/<run-id>.events.jsonl`).
- Код 0 / `ready to close` — закрывает план или пушит «готово».
- Код 3/4 — разбирает конкретный стоп: `docflow status`, Handoff юнита,
  хвост лога попытки. Решает в пределах мандата (ниже), перезапускает.
- Вне мандата — пуш человеку с вопросом и вариантами; ответ с телефона
  продолжает ту же сессию.

Почему контекст почти не растёт: дирижёр не видит работу исполнителей,
только стопы. Каждый стоп — сотни строк, а не сотни тысяч токенов. И сама
сессия одноразовая: всё состояние в репозитории (в этом весь docflow),
так что её можно рвать на каждом плане или после N инцидентов, а новая
начинает с `docflow status`.

Изменений docflow для первой проверки не нужно вообще: нужен только текст
мандата в промпте сессии.

## Мандат дирижёра

Без явного мандата дирижёр — это способ обойти защиты. Черновик:

Может сам:
- снять `blocker: human`, если причина проверяема и снимается
  (команда есть, файл есть, неоднозначность разрешается Goal/Decisions),
  через `docflow unblock <id> --note`;
- на `review budget spent` — то, что сейчас делает человек: мелкие
  находки исправить сам одним коммитом, остальные записать в Handoff, не
  открывая новый круг ревью;
- на `replan limit reached` — один ручной replan в рамках тех же правил,
  что `check_replan`;
- перезапустить прогон после временного сбоя (сеть, квота, флейк,
  воспроизведённый на HEAD).

Не может, только пуш человеку:
- менять Goal, Constraints, `Verify:` опорных юнитов, ослаблять проверки;
- снимать блок второй раз на том же юните;
- всё, что выходит из репозитория: секреты, доступы, деньги, публикация,
  push.

Каждое решение — пункт в `## Decisions` плана с префиксом (например
`Supervisor:`), чтобы потом прочитать с телефона или в архиве, что было
решено без человека. Метрика успеха: доля стопов, закрытых без
человека, и число решений дирижёра, которые человек потом откатил.

## Какой харнесс

Критерии: мобильный клиент с пушем и ответом; Windows и macOS (работа
идёт на обеих); фоновые процессы с пробуждением по событию; выбор модели
дирижёра; права на запуск раннера без постоянных подтверждений.

| Харнесс | Мобильный клиент и пуш | Windows | Фон и пробуждение | Модель дирижёра | Минусы |
|---|---|---|---|---|---|
| **Claude Code** + Remote Control | официальное приложение Claude, пуш с v2.1.110 (апрель 2026) | да | фоновые команды с пробуждением по выходу, Monitor, `/loop`, хуки | только Anthropic | пуши Remote Control в 2026 ловили баги доставки; лимиты подписки Claude; классификатор авто-режима |
| Happy (обёртка над Claude Code и Codex) | своё приложение, пуш, E2E | да (Node) | как у обёрнутого CLI | Anthropic или OpenAI | сторонний сервер синхронизации; ещё один слой |
| Codex CLI + ChatGPT mobile | официально, `codex remote-control` с мая 2026, preview | Windows-хост «скоро» | слабее, чем у Claude Code | только OpenAI | preview, Windows не готов |
| OpenCode | только неофициальные клиенты и плагины (бета) | да | сервер с HTTP API | любая из ростера | мобильная часть сырая |

Выбор — **Claude Code**:

- в нём уже есть всё для варианта Б: фон, пробуждение по выходу,
  Monitor для потока событий, push-уведомления, хуки, скиллы;
- на обеих ОС одинаково, и это уже основной инструмент работы;
- дирижёр почти всё время спит, будится на стопах — достаточно Sonnet,
  Opus только на тяжёлый разбор; расход подписки несопоставим с
  исполнением юнитов.

Запасной вариант на случай, если пуши Remote Control окажутся
ненадёжными, — Happy поверх того же Claude Code. Codex становится
интересен как второй дирижёр, когда его мобильный клиент выйдет из
preview на Windows.

Не путать роли: харнесс дирижёра не обязан совпадать с исполнителями.
Исполнители остаются по ростеру (opencode-go, zai, codex…), их запускает
`docflow run`, а не дирижёр.

## Риски

- **Права.** Классификатор авто-режима может отказать в фоновом
  `docflow run` с `permissions: full`. Нужно явное правило разрешения на
  `docflow run` в настройках проекта — решение человека, не дирижёра.
- **Тихая эрозия качества.** Главный риск варианта Б. Лечится мандатом,
  записью решений в план и разбором первых прогонов вручную.
- **Надёжность пуша.** Внешний канал, на который нельзя полностью
  полагаться. Дешёвая страховка независимо от харнесса — команда
  уведомления в `docflow run` (например, ntfy), но это уже изменение
  docflow, см. ниже.
- **Лимиты дирижёра.** Подписка Claude общая с интерактивной работой;
  ранее пять параллельных сессий Opus съели лимит Pro. Один дирижёр на
  Sonnet — не та нагрузка, но мерить.

## Что проверить до любого кода

Один живой прогон на рабочем проекте, без изменений docflow:

1. Сложный план (такой, что раньше вставал часто), Claude Code с Remote
   Control, сессия на Sonnet.
2. Стартовый промпт ([черновик](2026-11-13-supervisor-prompt.md)):
   запустить `docflow run --yes` фоном; на выходе
   разобрать стоп по мандату; вне мандата — пуш; каждое решение —
   `Supervisor:` в `## Decisions`.
3. Записать: число стопов, сколько закрыто без человека, сколько пушей,
   сколько решений дирижёра пришлось откатить, расход дирижёра.

Если доля закрытых стопов заметная и откатов нет — оформлять:

- мандат — отдельный скилл (`bsv-docflow-supervise` или раздел
  существующего), это не ключ формата и не команда CLI, заморозку не
  задевает;
- уведомления — заменить жёсткий выбор `osascript`/`notify-send`/`\a`
  настраиваемой командой (обобщение существующего, а не новая
  сущность);
- отдельно — пересмотреть, какие из стопов раннера стоит превратить из
  «ждём человека» в «будим дирижёра»: это ответ на проблему 1, и он
  виден только по данным прогона.
