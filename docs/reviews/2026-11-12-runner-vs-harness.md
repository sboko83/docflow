# Замена `docflow run` на walker в харнесе с мобильным управлением

Дата: 2026-11-12. Статус: анализ для решения — ничего не принято, ничего не
менялось. Ссылки на внешние продукты проверены на эту дату.

## Боль

Исходная идея docflow: запланировать работу → разные модели сами ведут план
до конца, проверяют друг друга, учитывают лимиты подписок, и человек получает
сигнал только когда нужно его решение. Что есть на деле:

- сложный план упирается в блоки и лимит репланов почти на каждом шагу;
- `docflow run` живёт в терминале, управлять им неудобно;
- о проблеме узнаёшь, только если сам смотришь в терминал — ни пушей, ни
  мобильного.

## Диагноз

Блоки и лимит репланов — не баг, а политика unattended-безопасности.
Runner спроектирован в предположении «человека нет»: вместо вопроса —
жёсткий guard (`Attempts: 3, Replans: 3`, `[!]`, остановка). Пока человека
нет, guard'ы обязательны. Но человек есть — ему просто нечем прийти:
канала доставки решения нет, а терминал им не является.

Это подтверждается историей проекта: P052 (интерактивное терминальное
управление) и P058 (TUI) — два плана, потраченные на управляемость runner'а
*в терминале*. При этом живая приёмка P052.4.2 встала блоком «квота Codex
исчерпана, нужно решение человека» — и решение можно было увидеть только
глядя в терминал. Канал — узкое место, и мы уже дважды платили за надстройки
над ним.

Отсюда вывод: менять надо не runner, а канал человека. Runner при этом
теряет бо́льшую часть своей работы (переключение исполнителей по лимитам,
безопасные остановки, guard'ы) — эти функции существуют именно из-за
отсутствия канала.

## Что остаётся, что заменяется

| Слой | Судьба |
|---|---|
| Формат плана, SDD-доки, handoff, lint, архив | остаётся полностью |
| Ростер, роли, политики (`roster scan/brief/apply`) | остаётся как данные + CLI; runner их не читает, значит walker может |
| Команды цикла `prompt/verify/done/commit` | остаётся — их вызывает и walker; fingerprint-верификация и «коммитится ровно проверенное» живут тут, а не в runner'е |
| `docflow run`: страты, переключение по лимитам, guard'ы, TUI | замораживается; заменяется walker-сессией |
| Взаимные проверки моделей | остаются: headless вызовы `codex exec` / `opencode run` / `claude -p` из walker-сессии — то же, что runner делает внутри |

## Как выглядит walker

Без нового кода. «Юнит = сессия»: сессия читает `docflow-dev status`, берёт
готовый юнит с его `Read:`-списком, выполняет, прогоняет `Verify:`, закрывает,
выходит. Следующий юнит — новая сессия. Состояние живёт в плане, а не в
контексте — это ровно та часть docflow, которая уже работает; контекст
walker'а поэтому не растёт.

Правила walker'а — почти готовый скилл `bsv-docflow-run` минус
runner-специфика. Единственное содержательное изменение — политика:

- реплан разрешён свободно, с пометкой в логе плана (лимит репланов
  отпадает вместе с «человека нет»);
- блок — только на human-only шаг или необратимое действие;
- «спросить» = написать в сессию — человек получит пуш и ответит с телефона.

## Что смена харнеса честно не решает

- **Квоты.** Облачная рука (Claude web, Codex cloud) — это одна подписка на
  задачу. Ростер «разные подписки на разные роли» живёт только в локальном
  исполнении.
- **Машина.** Локальный харнес = Mac включён и онлайн всё время прогона.
- **Квота walker'а.** Walker сидит на чьей-то подписке — столько же, сколько
  сейчас ест `docflow run`, не больше. Новый режим отказа: дрейф длинной
  сессии — лечится дисциплиной «юнит = сессия».
- **Политика.** Сами по себе блоки не исчезнут: правила walker'а всё равно
  переписываются руками, иначе те же guard'ы воспроизведутся в новом месте.

## Кандидаты (проверено 2026-11-12)

| Вариант | Где выполняется | Пуши | Управление с телефона | Fit с docflow |
|---|---|---|---|---|
| **ZCode Remote Control** (уже стоит) | локально, наш Mac | не заявлены; Bot Channel — для возврата позже, природу пушей проверить | полный пульт текущего окна: задачи, сессии, ввод ([docs](https://zcode.z.ai/en/docs/remote-control)) | нулевая цена: GLM-квота та же, локальный ростер работает, миграции нет |
| **Claude Code + Remote Control + приложение Claude** | локально | да, официально: задача завершена / нужно решение ([docs](https://code.claude.com/docs/en/mobile); пуски через `/rc`; известный баг доставки — [issue](https://github.com/anthropics/claude-code/issues/28765)) | приложение Claude: мониторинг и ответы | GLM Coding Plan заводится в Claude Code ([гайд](https://www.reddit.com/r/ZaiGLM/comments/1ron472/ensuring_the_model_in_claude_code_cli_w_zai), [обзор](https://flaviocopes.com/zcode)); файлы, `docflow-dev` и headless-ростер на месте |
| **Happy / Happier** (open-source клиенты) | локально | да, пуши на вопросы и готовность | полный клиент сессии ([Happy](https://happy.engineering), [код](https://github.com/slopus/happy); [Happier](https://happier.dev) — 11+ агентов и git с телефона) | сторонний relay, E2E и стабильность пушей — проверить в пилоте |
| **Codex cloud + ChatGPT mobile** | облако OpenAI | частично: пуш на approval ещё сырой ([request](https://community.openai.com/t/codex-approval-requests-should-trigger-mobile-push-notifications/1381134), [баг iOS 26.5](https://github.com/openai/codex/issues/32908)) | задачи с телефона ([docs](https://learn.chatgpt.com/docs/mobile)) | облачная рука = одна подписка, локального ростера нет; годится запасной рукой, не каналом |
| **Vibe Kanban** | локально, веб | нативных нет | браузер (Tailscale): дашборд попыток, диффы, ревью ([код](https://github.com/BloopAI/vibe-kanban)) | оркестратор для 10+ CLI (Claude Code, Codex, OpenCode…); это дашборд, а не walker — поверх всё равно нужен walker-скилл |

Вердикт по кандидатам: единственный локальный вариант с нативными пушами
«нужно решение» — Claude Code Remote Control; ZCode Remote Control уже стоит
и проверяется бесплатно; Happy — запасной клиент, если пушей Claude не
хватит; Codex cloud и Vibe Kanban — не основные каналы.

## Рекомендация: пилот на вечер вместо миграции

1. **Шаг 0 (30 минут).** Включить ZCode Remote Control на текущем окне
   (иконка телефона в левом сайдбаре), открыть bsv-docflow с телефона,
   подать пару инструкций в живую сессию. Проверить, пушит ли Bot Channel —
   если пушит, вопрос может закрыться вообще без смены харнеса.
2. **Шаг 1.** Взять маленький план на 3–4 юнита в тестовом репо. Walker =
   ZCode или Claude Code со скиллом `bsv-docflow-run`, правило «юнит =
   сессия», политика из раздела выше.
3. **Шаг 2.** Тот же план в Claude Code с GLM-роутером + `/rc` + приложение
   Claude.

Критерии успеха пилота:

- пуш на каждое «нужно решение» приходит и виден;
- решение с телефона не ломает сессию и не выкидывает из контекста;
- три юнита подряд без заглядывания в терминал;
- контекст walker'а не пухнет (handoff берётся из плана);
- headless `codex exec` / `opencode run` вызываются из walker-сессии и
  видны в её логе;
- расход квоты наблюдаем.

Если пилот зелёный: оформить walker-скилл, переписать политику блоков и
репланов в `docs/design/runner.md` и `cycle.md`, заморозить `docflow run`
и TUI (не удалять — runner остаётся фичей релиза, просто не развивается).
Если красный — вернулись, потрачен вечер.

## Открытые вопросы

- Пушит ли Bot Channel у ZCode и что это технически (бот в мессенджере?).
- Качество GLM в Claude Code через роутер на длинных сессиях.
- Happy: relay-сервер, приватность, стабильность пушей.
- Стратегический: если пилот зелёный, docflow из «оркестратора с раннером»
  становится «методологией + тулкитом для любого харнеса». Это пивот
  позиционирования — решение за человеком, не за пилотом.
