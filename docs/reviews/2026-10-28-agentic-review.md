# Оценка docflow с позиции агентной разработки — 2026-10-28

Срез на релизе 0.18.0 (`31483ac`): дизайн-доки, скиллы, код цикла и
раннера, архив P001–P049. Локальный `go test ./...` зелёный (7 мин 20 с на
Windows, из них 416 с — `internal/runner`), `go vet` чист.

**Вердикт.** Инженерно сильный проект с правильной базовой идеей и
несколькими редкими механиками. Главный риск — проект вырос в сложную
систему правил, ценность которой не измерена, а ключевая гарантия «что
проверено, то и закоммичено» может выродиться в формальность, если агент
ослабит саму проверку.

## Сильные стороны

1. **Состояние в репо, а не в контексте.** Юнит = сессия, холодный агент,
   handoff. Индустрия пришла к тому же (Kiro, Spec Kit, OpenSpec), но
   docflow цикл не рекомендует, а **принуждает**.
2. **Отпечаток verify → commit** (`internal/cycle/verify.go`, `fingerprint`)
   — редкая механика: нельзя закоммитить не то, что прошло проверку.
3. **CLI делает переходы, а не агент**, плюс предохранитель
   `DOCFLOW_RUNNER_UNIT` (команды отказывают кодом 5) — понимание, что
   запреты в промпте слабая модель нарушает.
4. **Мультивендорный роутинг** с ролями cheap/heavy/review/acceptance и
   fallback по квотам. Вендоры строят оркестрацию только под себя — ниша
   реальная.
5. **Архив решений + Gotchas, которые сами подмешиваются в промпт** —
   работающая долгосрочная память проекта.
6. **Дисциплина `Unverified:`** — честность агента как формат.
7. **Инженерная гигиена:** тестов ≈ кода (~20k / ~20k строк), CI на трёх
   ОС, parity-e2e, release tooling, `audit-public`, измерение контекста
   (`context-audit`, `read-audit`, `stats`).

## Слабые стороны

1. **Формат и поверхность разрастаются.** 21 команда, ~15 ключей
   frontmatter, 3 версии формата, цепочки ролей, replan, fallback,
   `(once)`, Frozen, `repos:`, `preflight:`, `gate:`, `whole_read_limit`.
   Скилл планирования ~5.5k токенов, `runner.md` и `usage.md` по ~14k.
   Каждый план добавляет в спеку абзац-исключение — проект сам копит
   «контекстный долг», с которым борется.
2. **Доказательная база — один репозиторий.** Почти все 49 планов этого
   репо — о самом docflow (раннер, Windows, установка, вывод, квоты).
   *Уточнение автора:* docflow уже ведёт несколько других проектов, так что
   внешнее использование есть — но оно не измеряется, и вывод тот же:
   неизвестно, даёт ли система выигрыш. Пункт Backlog про Xcode/Gradle
   (дорогой и нестабильный Verify) не проверен.
3. **Ценность не измерена.** Главная гипотеза — «docflow run даёт лучший
   результат и/или дешевле, чем одна сессия агента» — не проверена;
   бенчмарк лежит в Backlog. Единственное реальное измерение (P047): **~42 %
   токенов юнита — чтения вне `Read:`**, то есть механика ограниченного
   контекста соблюдается наполовину.
4. **Калибровка под модели прошлого поколения.** «Слабые модели деградируют
   после 80–120k», юнит ≈ 100k, «понятен слабому агенту». Для фронтирных
   моделей узкие юниты — накладные расходы: каждый юнит заново читает
   старт-доки, Context и Read, handoff теряет нюансы. Размер юнита стоит
   привязать к исполнителю (cheap — дробно, heavy — крупно).
5. **Медленный gate.** `go test ./...` как `gate:` этого репо — ~7 мин на
   Windows на каждый юнит и каждую попытку.

## Дыры

1. **Агент может ослабить собственную проверку.** Отпечаток гарантирует
   идентичность дерева, не осмысленность проверки. Исполнитель свободно
   правит тесты, которые гоняет `Verify:`. `checkReplan`
   (`internal/runner/replan.go`) защищает шапку, Goal, Constraints,
   Prerequisites и закрытые юниты — **но `Verify:` и `Do:` открытых юнитов,
   включая юнит приёмки, replan-агент переписать может.** Сценарий: юнит не
   проходит → агент блокирует с `blocker: plan` → дешёвый replan-маршрут
   смягчает `Verify:` → зелёный коммит без человека.
2. **Песочница в `auto` частично иллюзорна.** Агент пишет код в песочнице,
   а docflow сам, с правами пользователя, запускает `Verify`/`gate`/
   `preflight` через `sh -c` — то есть исполняет только что написанный
   агентом код. Prompt-injection (зависимость, issue, README) обходит
   песочницу через тест.
3. **`git add -A` в `commit`** (`internal/cycle/commit.go`). Коммитится всё,
   что агент оставил вне `.gitignore`: временные файлы, дампы,
   потенциально `.env`. В интерактиве список файлов печатается, в
   автономном прогоне его никто не смотрит.
4. **`permissions: full` = `bypassPermissions`** на часы автономного прогона
   после одного y/N на старте. Для такого режима нужен контейнер, не
   подтверждение.
5. **Хрупкая связь с внутренностями вендоров:** парсинг транскриптов
   `~/.claude/projects`, классификатор отказов по тексту ошибок (не сверен с
   живыми отказами, P032), опрос квот подписок. Релиз Claude Code или Codex
   ломает это тихо. Плюс риск ToS: автоматизацию подписочных лимитов через
   headless провайдеры ужесточают.
6. **Мелкое:** handoff только от прямых `Depends` (транзитивное знание
   теряется, качество handoff не проверяется); внутри плана нет
   параллельности, хотя индустрия ушла в параллельных агентов в worktree.

## Перспективы

Ниша — **детерминированная вендор-нейтральная оболочка над
недетерминированными агентами**. Верхний слой «задача → план → задачи»
съедят Claude Code (plan mode, субагенты, hooks), Codex cloud, Kiro, Spec
Kit. Уникальное у docflow — принуждённый цикл verify → commit, архив
решений, роутинг по квотам; на этом и фокус. Направления: принуждение
цикла и в интерактиве через hooks/MCP, параллельные юниты в worktree,
собственный eval-харнесс, адаптивный размер юнита.

## Приоритеты («надо было вчера»)

1. Закрыть дыру 1: replan не меняет `Verify:` открытых юнитов без ревью;
   правки тестов и Verify-скриптов фиксируются и видны в сводке run.
2. Бенчмарк ценности: те же задачи — docflow run против одной сессии
   агента; качество, стоимость, время. Данные (`stats`, `events.jsonl`) уже
   собираются; без них изменения оптимизируются вслепую.
3. Заморозить рост формата: новый ключ — только с удалением или обобщением
   старого; скилл планирования ужать до ~2.5k токенов.
4. Пилот на проекте не на Go с дорогим или флейки Verify.
5. Изоляция: `full` и запуск проверок — в контейнере; перед коммитом —
   проверка на секреты и крупные бинарники.
6. Контрактные тесты на форматы вендоров: снапшоты реальных выводов плюс
   регулярный canary-прогон на дешёвой модели.
