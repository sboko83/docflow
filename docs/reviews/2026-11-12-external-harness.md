# Docflow с внешним харнесом — 2026-11-12

Исследовательская записка. Предлагаемое направление, не принятое изменение
архитектуры. Установки, интеграции и живого прогона кандидатов не было.
Возможности внешних продуктов сверены с первичными источниками на эту дату;
описанная возможность ещё не доказывает надёжность на длинном плане.

## Вывод

Идея реализуема. Docflow полезно сохранить как формат работы и механизм
проверяемых переходов, а удалённое управление и жизнь агентных сессий отдать
готовой системе. Это позволяет проверить исходную задумку без разработки
собственного мобильного приложения.

**Первый кандидат для пробного прогона — T3 Code.** Он управляет существующими
агентами и подписками, имеет приложения для телефона и средства передачи
работы агентам. **HAPI — ближайшая альтернатива**, особенно если нужны Pi,
DeepSeek Harness и Telegram. Happy интересен более глубокой оркестрацией,
но его собственный runtime и ограничения дерева агентов требуют отдельной
проверки.

Замена `docflow run` одним длинным чатом сама по себе не даёт ни малого
контекста, ни восстановления после лимита, ни независимого ревью. Эти свойства
должны обеспечиваться устройством запуска, а не обещанием модели.

## Что сейчас не совпадает с исходной целью

| Требование | Что есть в Docflow | Чего не хватает |
|---|---|---|
| План проходит сам | Повторы, fallback, авто-replan, сохранение состояния | Решения по сложным отклонениям часто превращаются в остановку |
| Разные модели исполняют и проверяют | Роли, маршруты плана, ростер, контекст ревью | Удобное наблюдение и вмешательство в общую работу |
| Человек нужен только для решения | Разделение блоков `plan` и `human` | Доставка вопроса на телефон, ответ и продолжение |
| Управление вне терминала | События прогона и встроенный Go API управления | Готовый удалённый клиент |
| Ограниченный контекст | Юнит, `Read:`, `prompt`, Handoff, Decisions | Контроль роста истории внутри сессии и у координатора |
| Использование подписок | Цепочки исполнителей, обнаружение отказов и ожидание | Полная политика распределения доступного бюджета между подписками |

Это два разных разрыва: управление работой и восстановление после проблем.
Мобильная оболочка закрывает первый, но не меняет второй автоматически.

В текущем раннере по умолчанию три попытки исполнения, не более двух replan
на юнит и трёх на фазу. После трёх записей `Blocked (plan):` у опорного юнита
ревью/приёмки включается дополнительная остановка. Это настоящие ограничения,
а не только требование скилла:
[цикл раннера](../design/runner.md#цикл-на-юнит),
[авто-replan](../design/runner.md#авто-replan),
[реализация](../../internal/runner/replan.go).

При этом неверно считать, что обработки квот и уведомлений совсем нет.
Раннер переключает маршруты при лимите/недоступности и умеет ждать сброса.
В конце прогона он отправляет локальное системное уведомление, с запасным
сигналом терминала. Доставки вопроса на телефон и обратного канала нет:
[fallback](../design/runner.md#смены-исполнителя-и-ожидание-лимита),
[уведомления](../../internal/runner/helpers.go).

## Сравнение кандидатов

| Кандидат | Телефон и уведомления | Разные исполнители | Оценка для этой задачи |
|---|---|---|---|
| **T3 Code** | iOS, Android, пуши и открытие нужного чата | Claude Code, Codex, OpenCode и другие; средства делегирования | Первый пробный запуск: сохранить привычные агенты, заменить интерфейс управления |
| **HAPI** | Нативные приложения, PWA, Telegram; несколько каналов уведомлений | В том числе Claude Code, Codex, OpenCode, Pi, dsh | Предпочтителен при обязательном сохранении Pi/dsh и приоритете своего сервера |
| **Happy** | iOS и Android, удалённое управление теми же сессиями | Собственный runtime и подключение внешних харнесов, агенты разных моделей | Ближе к единой оркестрации, но требует проверки ограничений и режима подключения подписок |
| **Codex + Remote** | Официальный мобильный интерфейс, управление и уведомления | Основная сессия Codex; другие CLI требуют отдельного подключения | Самый короткий эксперимент, если сначала достаточно одного ведущего провайдера |
| **Claude Code + Remote Control** | Официальные приложения, вопросы и пуши | Основная сессия Claude Code; другие CLI требуют отдельного подключения | Прямой вариант при ведущем Claude, без общего мультивендорного планировщика |

### Почему первым T3 Code

Он сохраняет существующие агентные CLI и их вход в подписки. Можно отделить
Docflow от интерфейса исполнения, не переходя сразу на другой агентный цикл.
Список агентов в [README релиза v0.1.9](https://github.com/pingdotgg/t3code/blob/v0.1.9/README.md)
включает Claude Code, Codex и OpenCode. Более новая
[ветка main](https://github.com/pingdotgg/t3code/blob/main/README.md)
перечисляет также Pi и другие интеграции; её нельзя считать списком
возможностей установленного стабильного релиза.

Уведомления о завершении, ошибке, запросе разрешения или ответа уже описаны
в [документации релиза](https://github.com/pingdotgg/t3code/blob/v0.1.9/docs/user/mobile-notifications.md).
Они требуют T3 Connect и включённой публикации активности. Есть переход
в чат и отображение текущей активности на телефоне.

[Учёт лимитов](https://github.com/pingdotgg/t3code/blob/v0.1.9/docs/user/usage.md)
показывает окна подписок и время сброса. Это наблюдение за бюджетом,
а не доказательство автоматической маршрутизации по политике ростера.

Внешний агент может через
[MCP](https://github.com/pingdotgg/t3code/blob/main/docs/user/outside-agents.md)
создавать, читать и направлять чаты; часть инструментов подагентов доступна
только агентам внутри T3. Значит, предусмотрены пути для координатора
и отдельных исполнителей. Выполнение Docflow целиком без ручных перезапусков
остаётся гипотезой для живой проверки.

Для macOS и Linux предусмотрена
[фоновая служба](https://github.com/pingdotgg/t3code/blob/v0.1.9/docs/user/background-service.md).
На Mac всё равно нужны работающая машина, активный вход пользователя и сеть.
Восстановление службы не означает автоматическое продолжение каждого
оборванного агентного хода.

### Когда выбрать HAPI

[Матрица интеграций](https://hapi.run/docs/guide/agents) прямо перечисляет
Pi через RPC и dsh через ACP наряду с Claude Code, Codex и OpenCode.
Это ближе к уже имеющемуся набору исполнителей Docflow, если его нужно
сохранить целиком.

Есть [нативные приложения](https://hapi.run/docs/guide/native-apps),
но они платные; Web/PWA бесплатен. Встроены
[уведомления](https://hapi.run/docs/guide/notifications) через приложения,
Web Push и Telegram. Runner позволяет создавать сессии удалённо.

HAPI прежде всего управляет агентными сессиями. Наличие нескольких
поддерживаемых агентов не доказывает наличие общего координатора, который
сам распределит юниты и обеспечит ревью. Кроме того,
[жизненный цикл Codex](https://hapi.run/docs/guide/codex-shared-sessions)
зависит от запуска: закрытие исходного терминала завершает принадлежащий
ему app-server; запуск через Runner обходится без основного терминала.

### Почему не выбрать Happy без дополнительной проверки

Нынешний [Happy](https://happy.engineering/how-it-works/) — уже собственный
харнес, а не только прежняя мобильная обёртка. У него есть сохраняемые
сессии, сообщения между агентами и работа после закрытия окна.
[Мобильный клиент](https://happy.engineering/mobile/) позволяет отвечать,
останавливать ход, менять модель и запускать сессии.

Но [описание подагентов](https://happy.engineering/agents/) ограничивает
дерево пятью агентами, включая завершённых. Нельзя предполагать, что длинный
план получится пройти, каждый раз создавая нового подагента. Повторное
использование сохраняет его историю; для свежего контекста нужно проверить
другой способ создания сессий или смены координатора.

[Пулы аккаунтов](https://happy.engineering/models/) умеют переключаться
после ошибки авторизации или исчерпания квоты. Однако
[подключённые внешние харнесы](https://happy.engineering/recepies/harnesses/)
не ротируются такими пулами. Возможности собственного цикла Happy нельзя
автоматически переносить на режим Claude Code/Codex CLI внутри Happy.

Отдельно важен способ использования Claude-подписки. Собственный цикл,
читающий её OAuth-данные, и запуск неизменённого Claude Code — разные
варианты. [Условия Anthropic](https://code.claude.com/docs/en/legal-and-compliance)
разделяют нативное использование и стороннюю маршрутизацию запросов
через подписочные credentials. Заявление оболочки «поддерживаем подписки»
само по себе не подтверждает допустимость любого режима подключения.

### Официальные приложения тоже подходят для эксперимента

[Codex Remote](https://developers.openai.com/blog/mastering-codex-remote-for-engineering)
позволяет с телефона запускать и направлять работу, отвечать на запросы,
смотреть изменения и получать уведомления. Цели поддерживают продолжение
работы через несколько ходов. Это не следует путать с автоматическим
распределением бюджета между разными провайдерами.

[Claude Code Remote Control](https://code.claude.com/docs/en/remote-control)
тоже поддерживает управление локальной работой с телефона и мобильные пуши
о вопросе или завершении. Локальный процесс должен продолжать работать.
Официальный клиент может быть достаточным первым шагом, если проблему
мультивендорного координатора временно вынести за границы эксперимента.

## Предлагаемая граница ответственности

**Docflow сохраняет:** формат плана, зависимости, Decisions и Handoff,
сборку контекста юнита, ростер и роли, `verify → done → commit`, архив.
Проверка дерева перед коммитом полезна независимо от того, кто управляет
сессией. Она не заменяет содержательное ревью проверки.

**Внешняя система обеспечивает:** интерфейс телефона, фоновые процессы,
сессии исполнителей, доставку вопросов и ответов, наблюдение за работой.

**Координатор решает:** какой юнит брать, какой маршрут использовать,
как исправить отклонение, когда нужен другой исполнитель и когда вопрос
действительно относится к человеку. Его состояние восстанавливается из
репозитория, а не только из истории чата.

Нужные атомарные команды уже существуют:
[`status`, `next`, `prompt`, `verify`, `done`, `commit`, `block`, `unblock`](../design/cli.md#cli-docflow).
Новый способ выполнения можно сначала проверить поверх них, сохранив
`docflow run` как альтернативный путь. Для такой проверки не требуется
заранее менять формат плана или добавлять команды.

## Как удерживать контекст

Одна новая рабочая сессия на юнит получает результат `prompt <id>` и
нужные файлы. Ревьюер получает требования, diff и результаты проверок
в своей сессии. Координатор получает короткий итог, ссылки на изменения,
причину проблемы и следующий шаг. Полные логи остаются доступными по запросу.

У координатора история тоже растёт. Его нужно уметь заменять с восстановлением
из состояния плана, например на границе фаз. Повторное обращение к старому
подагенту не равно новой сессии. Компактация сокращает историю, но не даёт
гарантии постоянного размера контекста.

Это согласуется с [пилотом Docflow](2026-11-09-pilot-summary.md#время-и-контекст):
бюджет чтения был близок к начальному контексту наблюдаемых сессий,
но не предсказывал их пик.

## Что делать с блоками и лимитами

Снимать все ограничения повторов опасно: можно получить бесконечное
переписывание плана или ослабление приёмки. Полезнее различать причины.

| Причина | Предлагаемая реакция |
|---|---|
| Ошибка реализации при прежних требованиях | Исправление в рамках юнита и повторная проверка |
| Устаревший путь, порядок или размер юнита | Локальное перепланирование с сохранением цели и приёмки |
| Повторяется одна ошибка без новой информации | Другой исполнитель или независимый разбор; затем остановка по бюджету |
| Исчерпан доступ к модели | Другой разрешённый маршрут либо ожидание сброса |
| Меняются цель, цена, внешние обязательства; нужен доступ или выбор пользователя | Вопрос на телефон с конкретными вариантами |

Критерий эскалации — отсутствие допустимого следующего действия, а не
сам факт неудачной попытки. При этом расход времени и подписок остаётся
ограниченным. Нужна политика расхода, а не только список запасных моделей.

Самый неудобный случай — лимит **у координатора**. Он уже не сможет
сам решить, кем себя заменить. Автономное восстановление должно выполнять
окружение: сохранить точку продолжения и позже разбудить сессию либо
запустить замену. Пуш об ошибке сообщает о проблеме, но её не устраняет.
Пока этот сценарий не проверен, обещать автономность всего плана нельзя.

## Как проверить гипотезу перед интеграцией

Нужен один настоящий многошаговый план в отдельном тестовом проекте,
длиннее нескольких первых делегирований. Начать с T3 Code и одного
координатора; выбирать конкретную модель по доступным подпискам.
На каждый юнит — свежий исполнитель, на контрольные точки — отдельный
ревьюер. Один писатель в общем рабочем дереве; параллельное редактирование
не нужно для проверки этой гипотезы.

Проверить последовательно:

1. Обычный путь: юниты, проверки, коммиты, независимая приёмка и закрытие
   плана проходят без ручной передачи промптов.
2. Исправимые отклонения: устаревший `Read:` и найденный ревьюером дефект
   исправляются без вопроса человеку и без ослабления требований.
3. Недоступность исполнителя: контролируемый отказ переводит работу
   на следующий маршрут. Не тратить подписку ради искусственного исчерпания.
4. Перезапуск координатора: состояние восстанавливается из репозитория;
   завершённая работа не повторяется и два писателя не запускаются.
5. Настоящий выбор пользователя: приходит пуш на заблокированный телефон,
   ответ из приложения возобновляет работу.
6. Конец плана: достигнута исходная цель, а не только закрыты маркеры;
   контекст новых исполнителей не содержит стенограмм предыдущих юнитов.

Отдельно проверить политику уведомлений: завершение каждого внутреннего
агента не должно превращаться в поток пушей. Целевой режим — вопросы,
которые требуют решения, итог плана и сбой самого механизма продолжения.
Точность такой фильтрации у выбранного клиента пока не установлена.

Если требуется ручное «продолжай» после каждого юнита, лимита или обычного
ревью, исходная цель не достигнута. Если цикл проходит, основание для
изменения архитектуры появляется из наблюдения. До этого достаточно
сохранить Docflow и проверить другой способ исполнения поверх его команд.
