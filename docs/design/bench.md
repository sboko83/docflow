# Эталонный бенчмарк

Бенчмарк измеряет, как изменения docflow влияют на выполнение фиксированных
задач. Все задачи используют одну базу `bench/base/`: `small` добавляет
фильтры дат и JSON-вывод, `medium` — категории, бюджеты и месячные отчёты,
`large` — валюты, конвертацию, импорт/экспорт, повторяющиеся записи и блокировку
журнала, `hard` — стабильные ID записей, запись журнала несколькими процессами
под замком с ожиданием и снятием устаревшего замка и атомарную замену файла с
имитацией сбоя. План, скрытый оракул и эталонное решение каждой задачи находятся в
`bench/tasks/<name>/`. Модуль `bench/go.mod` не даёт фикстурам Go попасть в
сборку основного модуля.

Решения — [P051](../archive/P051-benchmark.md).

## Проверка корпуса

`go run ./tools/bench validate --task NAME` сначала проверяет план через
`docflow lint`, затем запускает `go test -json ./benchoracle/...` отдельно на
копии базы и на копии базы с наложенным решением. Оракул должен провалиться на
базе и пройти на решении; количество пройденных тестов служит оценкой ветки.
Собственные тесты базы и решения (`go test ./...`) также должны проходить
до наложения оракула.
Оракул не копируется в рабочее дерево и не передаётся в промпте до оценки.
Копии лежат внутри checkout: отдельной изоляции файловой системы нет, поэтому
это защита от передачи ответа в задаче, а не от намеренного поиска решения.

## Прогон

`single` получает весь план за одну сессию Codex, по умолчанию `codex |
gpt-6.1-sol | high`; `--single-route` задаёт другой маршрут. `docflow`
исполняет план через `docflow run` и ростер `bench/roster.toml`. Маршруты
ростера с первого живого прогона: `zai` объявлен первым доступом, поэтому
его модели стоят во главе цепочек — исполнитель и роль `cheap` идут
`pi | glm-5.3-flash | high` (дешёвый исполнитель с известной ценой),
проверяющие и replan — `pi | glm-5.3 | max`, а `codex | gpt-6.1-sol | high`
остаётся сильным фолбэком. Требование роли в v2 — минимальный класс модели,
а порядок доступов один для всех ролей, поэтому закрепить за ролями разные
доступы порядок объявления не позволяет. Ветка
`docflow-one` доступна в `--arms` для сравнения цикла без смены маршрутов.
Ростер — в формате v2, а каталог моделей лежит рядом с ним в
`bench/catalog.json`: `roster apply` выбирает модели из каталога, поэтому
бенчмарк резолвит одинаковые маршруты на любой машине, а не из личного
скана. `chains` в результате — цепочки того же резолвера, что пишет шапку
плана; `roster_sha` остаётся хешем файла ростера.
По умолчанию CLI docflow собирается из текущего checkout (`go build
./cmd/docflow` в каталоге прогона); `--docflow PATH` указывает другой бинарь.
Цепочки `bench/roster.toml` после перехода на v2 отличаются от v1 в двух
местах, и старые результаты из-за этого не перезапускаются: роли `review`,
`acceptance` и `replan` идут `codex`, затем `zai` (в v1 доверенный `zai`
стоял первым, а v2 сортирует по бюджету и порядку доступов), и `zai/glm-5.3`
во всех ролях получает `max` (в v1 он был `high` в standard-маршруте и `max`
в strong, а у пары ACCESS/MODEL в v2 одно усилие). Маршрут executor
при переходе на v2 не изменился. Сначала
запустите `go run ./tools/bench run --task NAME --dry-run`: команда
показывает задачи, маршруты и рабочие пути без запуска агентов и записи
результатов. Обычный `run` вызывает модели, расходует квоту и коммитит
результаты; `large` может выполняться несколько часов.

Каждая ветка получает отдельную копию только `bench/base/`. После завершения
ветки на её дереве запускается оракул. Логи и копии остаются в локальном
`work/bench/<run-id>/`; ветка не получает каталог задач, оракул или историю
docflow.

## Результаты

`bench/results/runs.jsonl` хранит по записи на задачу и ветку. Схема `v: 1`
содержит: `run_id` (идентификатор прогона), `ts` (epoch seconds), `task` и
`task_sha` (задача и хеш её входов), `arm` (ветка), `route` (маршрут `single`),
`roster_sha` и `chains` (хеш ростера и цепочки маршрутов), `docflow_version`,
`docflow_commit` и `docflow_dirty` (сборка, которой прогнали ветку), `status`,
`oracle` с `passed`/`failed`/`total`, `seconds`, `cost` (USD, `null`, если
неизвестна), `tokens`, `units` с `total`/`done`/`blocked`, `attempts`,
`replans`, `test_changes`, `check_changes`, `unverified` и `diff` с числом
файлов, вставок и удалений. Необязательные поля маршрута и ростера могут
отсутствовать для неприменимых веток. Время `ts` — Unix epoch в секундах.

Каждый прогон записывается, включая прерванную ветку со статусом
`interrupted`. Перед запуском каталог результатов должен быть чистым.
`--results DIR` меняет каталог внутри checkout; прогон
коммитит только выбранный каталог с сообщением `bench: run <run-id>`. Файлы
`runs.jsonl`, сгенерированный `README.md` и сводка в
`bench/results/<run-id>/` сохраняют публичный ряд. Сырые логи и копии проектов
хранятся локально в `work/bench/<run-id>/` и не коммитятся.

`go run ./tools/bench report` заново строит README по `runs.jsonl`.
README показывает результаты по задаче и ветке, версии docflow, долю пройденных
проверок оракула, её изменение, стоимость и её изменение, минуты, попытки и
replan. Сравнение делается с предыдущим прогоном той же задачи при неизменном
SHA задачи. Для новой версии задачи изменение отмечается отдельно, без
сравнения оценок как эквивалентных.

Число юнитов берётся из `run_start`, завершённые и заблокированные — из
`unit_end`. Токены и стоимость читаются из логов вызовов, на которые ссылаются
события `attempt`, включая replan; события версии 1 не содержат токенов.
Если логи не дают стоимость, используется сумма из `unit_end`. `Unverified`
берётся только из тел коммитов юнитов после базового коммита копии. Размер
изменений включает новые файлы и исключает оракул и служебные логи бенчмарка.

## Живые прогоны

Первые живые прогоны прошли 2026-10-31 и 2026-11-01: полная схема
«модель × цикл» на трёх задачах — single на `codex | gpt-6.1-sol` и на
`zai | glm-5.3` (через `--single-route`), docflow на дешёвом стеке
(исполнитель `glm-5.3-flash`, проверяющие `glm-5.3`) и docflow-one.
Каждая ветка прошла оракул полностью: корпус не разделяет ветки по
качеству — все задачи закрывает даже дешёвый one-shot. Измеряются время,
токены и цена: полный корпус docflow-стеком стоит $1.49 против $3.15 у
one-shot `glm-5.3`; замер n=1. Данные — `bench/results/`
(`runs.jsonl`); single-маршруты различаются полем `route`, в сводке
README колонки маршрута нет.

Серия 2026-11-01 проверила, где живёт цена цикла: роли review и
acceptance в `roster.toml` переведены на `glm-5.3-flash`, исполнитель и
replan без изменений. Docflow-рука прошла все три задачи с полным
оракулом, 0 блокировок и 0 репланов — $0.026/$0.119/$0.304 против
$0.027/$0.41/$1.05: от medium вверх в 3.4–3.5× дешевле, small ценово
нейтрален, по времени на 1.3–1.6× медленнее. Полный корпус docflow
теперь $0.45 против $1.49 (trusted-review) и $3.15 (one-shot
`glm-5.3`): качество корпус по-прежнему не разделяет, но ценовой
градиент сложился — дорогой частью цикла были проверяющие роли;
ростер оставлен на дешёвых review/acceptance, замер n=1. Следующее
реальное измерение — жёсткий корпус, где one-shot падает; его оракул
должен запускать собранный бинарник: сейчас и тесты задач, и сценарий
оракула вызывают `run()` напрямую, поэтому unverified-пункты прогонов
повторяют одни и те же слепые зоны (запуск бинарника, конкурентные
процессы, crash-during-migration).

Жёсткая задача `hard` добавлена 2026-11-05 под это требование: её оракул
запускает собранный бинарник отдельными процессами — 12 параллельных
писателей, ожидание и таймаут замка, устаревший замок, сбой перед rename,
в том числе посреди миграции журнала. План называет ловушки (`## Traps`),
но тесты, вызывающие `run()` в одном процессе, их не ловят. Живых прогонов
`hard` ещё нет; разделяет ли она ветки по качеству, покажет первый прогон.
На Windows создание замка, который другой процесс как раз удаляет, отвечает
отказом в доступе, а не «файл существует»: реализация, которая не повторяет
попытку на этой ошибке, падает только на Windows.
