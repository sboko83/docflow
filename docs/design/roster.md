# Ростер

Ростер — отдельная подсистема планирования: собирает доступные модели,
применяет стабильную политику и временные условия, а на выходе даёт
цепочки маршрутов ролей, бюджет чтения юнита и объяснение выбора.
Резолвинг идёт только при составлении плана; **раннер ростер не читает**,
`run`, `lint` и `cycle` не получают новой логики, формат плана остаётся
`docflow: 3` без новых ключей. Временное условие действует на новый план
или на явный `roster apply`, а не на идущий прогон: это цена
воспроизводимости плана.

Раннер по-прежнему проверяет квоту на старте прогона; живые квоты в v2 не
опрашиваются. Осознанная граница первого релиза: планирование использует
auth-статус, expiry и условия, второго источника правды о квоте нет.

## Слои

| Слой | Файл | Что хранит | Кто меняет |
|---|---|---|---|
| Каталог | `$XDG_CACHE_HOME/docflow/roster/catalog.json` | найденные доступы, модели, контекст, цену, ризонинг, auth | `roster scan` |
| Политика | `~/.config/docflow/roster.toml` (или `--roster PATH`) | доступы, allowlist, доверие, классы, роли, пресеты | человек |
| Варианты | рядом с политикой, `roster.variants.toml` | пресеты, созданные в TUI: условия доступов и порядок | `docflow tui` (машинный файл) |
| Варианты проекта | `docs/roster.variants.toml` от корня checkout | пресеты проекта, общие для всех машин | `docflow tui`, файл коммитится |
| Условия | рядом с политикой, `roster.state.toml` | `off/on`, бюджеты, expiry, модели, пресет | `roster off|on|budget|expire|allow|deny|reset` |
| Резолвер | — | кандидаты, цепочки, матрица ревью, бюджет, предупреждения | `roster brief/show/explain/apply` |

Каталог расходный: его перезапишет следующий `scan`, файл с незнакомым
`version` считается отсутствующим. Условия не переписывают политику —
временное состояние живёт отдельным файлом и в `roster.toml` не попадает.
Пакет `internal/roster` не импортирует `internal/runner`; `apply` вправе
использовать `cycle`, `format` и `lint`.

Связь с прошлым: формат `Role:` и ключи ролей в шапке — [P036](../archive/P036-roster.md);
локальный маршрут `pi | strata/…` и отображение `Local` без квоты —
[P043](../archive/P043-local-worker.md). Этот документ заменяет v1-описание
ростера (`spend`, `[provider]`, `[route]`, `[profile]`) на политику v2 —
замена проведена [P055](../archive/P055-roster-v2.md): каталог, условия,
резолвер, миграция и удаление v1-пути.

## Каталог

`roster scan` собирает каталог из источников в порядке слияния:

| Источник | Что даёт |
|---|---|
| `pi-store` | `~/.pi/agent/models-store.json` — точные модели Pi |
| `pi-models` | `~/.pi/agent/models.json` — собственные провайдеры пользователя |
| `pi-list` | `pi --list-models`, если store отсутствует: модели и округлённый контекст |
| `opencode` | `opencode api get /api/model` через CLI, не напрямую по сети |
| `builtin` | встроенная офлайн-таблица Codex и Claude |
| `auth` | пробы авторизации Pi, OpenCode, Codex, Claude |
| `models.dev` | необязательное обогащение с `--online` |

Правила:

- `ScanPi` сливает store, затем `pi-list` (только при отсутствии store),
  затем `models.json`: точный конфиг перекрывает округлённую таблицу, а
  неизвестное поле остаётся заполненным предыдущим источником. Пустое не
  затирает непустое, поэтому `reasoning = false` не перекрывает `true`.
- `Agents` доступа при слиянии объединяются: `opencode-go` может
  приходить через `pi` и через `opencode`, и это один доступ — одна
  единица квоты. `ModelInfo.Provider` — имя провайдера, как его отдал
  источник; `family`/`headers` OpenCode не декодируются (в `headers` есть
  идентификаторы организации).
- У OpenCode цена — массив живого API, берётся первый элемент; `Efforts`
  — id вариантов, потому что роутер передаёт их как `#variant`.
- Контекст и `max_out`, равные нулю, означают «неизвестно», а не ноль
  токенов. `Cost` — указатель: `nil` значит «цена неизвестна», и модель не
  выдаётся за бесплатную.
- `Provenance map[string]string` хранит источник каждого поля: единый
  `Source` — это последний вклад, он скрывает, пришёл ли контекст из
  точного store или из округлённой таблицы `pi --list-models`.
- Auth-статус — одно поле на доступ (`ready`, `not_ready`, `unknown`);
  готовый канал побеждает. Claude без конфига и без CLI — `unknown`, не
  `not_ready`: скан не догадывается о машине, которой не видел.
- Ошибка источника (HTML вместо JSON, битый JSON, отсутствующий CLI) —
  предупреждение рядом с частичным каталогом, код успеха остаётся 0.
  Тело ответа в текст предупреждения не попадает; пробы печатают статусы,
  не секреты.
- Сканеры вызывают только `agentio.CallAgent` с таймаутом 30 с, не
  запускают модели и не тратят квоту; каталог сортируется на выходе.
- `models.dev` заполняет только неизвестные поля и никогда не перекрывает
  значение сканера или встроенной таблицы. Доступ сопоставляется с
  провайдером models.dev явной картой (`codex`/`openai` → `openai`,
  `claude`/`anthropic` → `anthropic`, `opencode` и `opencode-go` →
  `opencode`, `zai` → `zai`), не по префиксу. Кэш `models.dev.json` лежит рядом с каталогом, TTL — сутки,
  `--refresh` ходит в сеть заново; без сети остаются встроенные метаданные.
- Встроенная таблица Codex берёт `context_window` самого CLI (500k у
  `gpt-6.1-sol`, 272k у `gpt-6-luna`), а не API-окно models.dev: CLI
  определяет, сколько реально доступно юниту.
- Кэш каталога пишется атомарно, `version = 1`; файл с другим `version`
  читается как пустой без ошибки. `--refresh` пересканирует локальные
  источники и игнорирует свежий кэш models.dev; без `--online` флаг
  ничего не меняет.

## Политика `roster.toml`

Версия формата — `version = 3`. Ростер старого формата (v1 без `version`,
v2-политика с `[model]`/`[effort]`) даёт код 2 и подсказку
`docflow roster migrate`. Разбор строгий: неизвестный ключ, ссылка
`[route]`/пресета на несуществующий доступ, имя доступа с пробелом, `/`,
`|`, `,` или `=` — ошибка с файлом и строкой.

```toml
version = 3

[access.opencode-go]
agents  = ["pi", "opencode"]     # каналы одного доступа
kind    = "subscription"         # subscription | metered | local
budget  = "prefer"               # prefer | normal | lean | minimal | off
trusted = true                   # допускается к acceptance и replan
models  = ["deepseek-*"]         # allowlist; пусто/нет ключа — все модели
exclude = []                     # что доступ не отдаёт никогда
expires = "2026-12-31"           # необязательная дата

[access.zai]
agents = ["pi"]
kind   = "subscription"
budget = "lean"
check  = true                    # нужен независимый ревьюер
models = ["glm-5.3*"]
exclude = ["glm-5.3-thinking"]

[access.codex]
agents = ["codex"]
kind   = "subscription"
budget = "minimal"               # только acceptance и replan
trusted = true

[access.claude]
agents  = ["claude"]
kind    = "subscription"
budget  = "normal"
trusted = true

[access.local]
agents = ["pi"]
kind   = "local"
budget = "normal"
check  = true                    # нужен независимый ревьюер

[route."zai/glm-5.3"]
high = "strong"                  # усилие → класс: cheap | standard | strong

[route."opencode-go/deepseek-v4.1"]
low  = "cheap"                   # одна модель — разные классы под усилия
high = "standard"

[route."codex/gpt-6.1-sol"]
medium = "strong"

[role]
cheap      = "cheap"
executor   = "standard"
heavy      = "strong"
review     = "standard"
acceptance = "trusted"
replan     = "trusted"

[preset.low]
off     = ["claude", "local"]
lean    = ["zai"]
minimal = ["codex"]
prefer  = ["opencode-go"]
order   = ["opencode-go", "zai", "codex"]
models  = { zai = ["*flash*"] }  # пустой список — ни одной модели
```

- **Доступ** — единица квоты и независимости, а не провайдер. Подписка
  `opencode-go` одна, даже если к ней ходят `pi` и `opencode`; fallback
  повторяет доступ, а не пару `agent|model`.
- `agents` обязателен и непуст. `kind` подсказывает, откуда маршрут:
  `local` — локальный сервер, `metered` — оплата за токены.
- `check` и `trusted` взаимоисключающи: доступ, требующий независимой
  проверки, не может сам быть финальным судьёй. `check` исключает доступ
  из `review`, `acceptance` и `replan`; `trusted` без `check` допускает к
  судейским ролям.
- `minimal` требует `trusted = true`: минимальный бюджет обслуживает
  только acceptance и replan, а это судейские роли. `minimal` без
  `trusted` — ошибка политики, а не тихое отключение.
- `[role]` обязан объявить все шесть ролей. Требование — `cheap`,
  `standard`, `strong` или `trusted`; `trusted` означает «trusted-доступ
  плюс модель класса strong».
- `[route."ACCESS/MODEL"]` — таблица «усилие → класс»: класс принадлежит
  паре «модель + усилие», одна модель может быть cheap на low и
  standard на high. Ключ — уровень усилия (`low/medium/high/max` или
  другое слово агента), значение — `cheap`, `standard` или `strong`;
  дублирующее усилие в одной таблице — ошибка. Ключ `-` — усилие не
  передавать (модель без уровней ризонинга). Модель без таблицы в
  `[route]` отдаётся с автоматическим классом по семейству
  (`flash/mini/lite → cheap`, `pro/sol/opus → strong`, остальное
  `standard`) и усилием по лестнице классов (`cheap → low`,
  `standard/strong → high`).
- `[preset.NAME]` — стабильный набор условий: `off/lean/minimal/prefer`
  взаимоисключающи на один доступ, `order` ставит доступы первыми,
  `models` сужает allowlist. Пресет не переопределяет `trusted`/`check`:
  это свойства политики. Противоречивое условие — ошибка политики.

### Варианты `roster.variants.toml`

Слои вариантов введены [P058](../archive/P058-tui-workspace.md).
Пресет варианта — тот же `[preset.NAME]`, что и в политике, но в
отдельном файле: глобальный `roster.variants.toml` лежит рядом с
`roster.toml`, проектный — `docs/roster.variants.toml` от корня checkout.
Файл содержит `version = 2` и только таблицы `[preset.NAME]`; любой
другой ключ — ошибка с файлом и строкой. Грамматика пресета общая с
политикой: те же массивы доступов, `order` и `models`, та же ошибка
взаимоисключающих условий.

```toml
version = 2

[preset.project-low]
off     = ["claude", "local"]
lean    = ["zai"]
minimal = ["codex"]
prefer  = ["opencode-go"]
order   = ["opencode-go", "zai", "codex"]
models  = { zai = ["*flash*"] }
```

- Загрузчик политики сливает пресеты трёх слоёв: `roster.toml`,
  глобальные варианты, варианты проекта. `Preset.Source` называет слой —
  `roster`, `variants`, `project`, — чтобы интерфейс показал, откуда
  пресет. Одно имя в двух файлах — ошибка политики с обоими путями:
  `--preset NAME` обязан значить одно и то же везде, молчаливое
  перекрытие проектом запрещено.
- Пресет варианта, называющий неизвестный доступ, — ошибка, как в
  `roster.toml`; отсутствие файла вариантов — пустой слой, не ошибка.
  Проектный слой виден только внутри checkout; вне его он пуст, а
  `--roster PATH` переносит глобальный слой к указанной политике.
- Файлы вариантов машинные: TUI пишет файл целиком (`SaveVariants`),
  поэтому комментарии и ручной порядок не сохраняются. Запись
  атомарная: временный файл перечитывается парсером и только потом
  заменяет цель, ошибка оставляет прежний файл. `roster.toml` человек
  правит руками, и TUI его не переписывает.

## Условия `roster.state.toml`

Условия — временный слой поверх политики, соседний файл
`roster.state.toml` (у `--roster PATH` — то же имя с `.state.toml`).
Отсутствие файла — отсутствие условий, не ошибка. Файл пишут только
команды условий; команды чтения его не переписывают.

```toml
version = 2
preset = "low"
off = ["claude", "local"]

[until]
claude = "2026-11-30"      # последний день, когда off ещё действует
[budget]
zai = "lean"
[expires]
codex = "2026-12-31"
[models]
zai = ["*flash*"]          # заменяет allowlist политики, не расширяет
[exclude]
zai = ["*-thinking"]       # запреты накапливаются
```

- `off ACCESS [--until DATE]` выключает доступ до конца указанного дня
  включительно или до `on`. Истёкший `off` отбрасывается в памяти при
  загрузке; файл переписывает только следующая мутация.
- `on ACCESS` снимает `off`, его дату и бюджет `off`, и ничего больше:
  это отмена переключателя, а не стабильной политики и не сужений.
- `budget ACCESS LEVEL` задаёт `prefer|normal|lean|minimal|off`; `minimal`
  на untrusted-доступе — ошибка, как и в политике.
- `expire ACCESS DATE` убирает доступ после даты; `allow ACCESS PATTERN…`
  заменяет allowlist доступа глобами, `deny ACCESS PATTERN…` скрывает их.
  Временное условие может сузить стабильный allowlist, но не расширить.
- `reset` удаляет файл состояния.
- Разовые флаги `brief`/`show`/`explain`/`apply` (`--preset`, `--off`,
  `--minimal`, `--lean`, `--prefer`, `--expires`, `--only`) применяются к
  in-memory состоянию и никогда не сохраняются: состояние на диске —
  единственный источник правды, флаг — вопрос. `--only` накапливается с
  glob-условиями из файла.
- Условие, называющее доступ, уровень бюджета или пресет, которых нет в
  политике, — код 2 до любой записи. Опечатка в мёртвом условии должна
  падать, а не тихо ничего не делать.
- Формат один: `--profile` (флаг v1) удалён и даёт ошибку с указанием
  `--preset`, а v1-файл любой команды — код 2 с подсказкой
  `docflow roster migrate`.

## Резолвер

Резолвер сливает политику с условиями и каталогом и для каждой роли
строит кандидатов. Один доступ даёт не больше одного кандидата на роль;
порядок кандидатов — `prefer`, затем `normal`, затем `lean`, `minimal` в
конце (у порядка один владелец — резолвер).

Бюджет доступа задаёт, какие роли он обслуживает:

| Бюджет | Роли |
|---|---|
| `prefer`, `normal` | все |
| `lean` | `cheap`, `executor`, `review` |
| `minimal` | `acceptance`, `replan` |
| `off` | никакие |

Фильтры ролей:

- `check`-доступ исключён из судейских ролей: доступ, который сам требует
  ревью, не судит.
- Для `trusted` нужен `trusted = true`; требование `trusted` поднимает
  планку класса до `strong`.
- Для `heavy` нужен известный контекст: модель с `context unknown` не
  ставится в тяжёлую роль.

Выбор модели внутри доступа: минимальный подходящий класс, затем цена
`input + output`, затем больший контекст, затем id. Неизвестная цена идёт
после известной — `nil` не выглядит бесплатным.

Цепочка роли — по одному маршруту с разных доступов; fallback повторяет
доступ, а не агента. Строка матрицы `review:` — только `check`-доступы,
реально дающие маршрут; выключенный `check`-доступ юнитов не производит и
ревьюера не требует. Нет независимого ревьюера — ошибка политики, а не
self-review. Пустая цепочка роли и цепочка из одного маршрута —
предупреждения брифа: резолвер не знает, какие роли использует план.
`apply` отказывает до записи, если пустая цепочка нужна открытому юниту,
а план с юнитом такой роли иначе упал бы на своём ключе в `lint`.

## Бюджет контекста

Бюджет чтения юнита — рекомендация брифа для нарезки плана, не ключ плана
и не проверка `lint`:

```
usable = context - max_out - reserve
target = clamp(usable * share * class_factor, 20000, 250000)
reserve = max(10% context, 32000)
```

`share` роли: `cheap 0.25`, `executor 0.35`, `heavy 0.45`; у судейских
ролей бюджета нет — они читают diff и вывод тестов (`scope = diff/test`).
`class_factor`: `cheap 0.75`, `standard 1.0`, `strong 1.25` — слабая
модель деградирует на полном контексте раньше сильной. Неизвестный
контекст даёт нулевой `Target` и строку `context unknown` в `why`, а не
догадку; неизвестный `max_out` считается нулём, и `why` это говорит.
`roster apply` только предупреждает о юните, чей `Read:`-прокси больше
бюджета роли.

## Команды

Все команды принимают `--roster PATH`; каталог и состояние живут вне
рабочего дерева.

| Команда | Что делает |
|---|---|
| `roster scan [--online] [--refresh] [--json]` | собирает каталог, пишет кэш, печатает сводку доступов; ошибка источника — предупреждение в stderr при коде 0 |
| `roster models [ACCESS] [--all] [--json]` | модели доступа, ростерных доступов или всего каталога; читает только кэш. Неизвестный `ACCESS` — код 2 со списком известных; пустой кэш — код 0 с подсказкой `roster scan` |
| `roster status [--json]` | доступы с каналами, auth, числом моделей и источниками, затем активные условия с источником; только кэш |
| `roster brief [--preset NAME] [разовые флаги] [--json]` | условия в силе, цепочка, бюджет и scope каждой роли, матрица `review:`, `why:` и предупреждения |
| `roster show` | алиас `brief` |
| `roster explain PLAN [--json]` | сравнивает шапку плана с брифом и печатает `ключ: старое → новое` и предупреждения ролей плана; ничего не пишет |
| `roster apply PLAN [--preset NAME] [разовые флаги] [--dry-run] [--json]` | пишет шапку плана; см. ниже |
| `roster off`, `on`, `budget`, `expire`, `allow`, `deny`, `reset` | правят `roster.state.toml` |
| `roster migrate [--write]` | переводит v1-ростер или v2-политику на v3 |

`scan`, `models` и `status` принимают `--json`. Неизвестные `context`,
`max_out` и цена печатаются как `unknown`, не как `0` или прочерк: ноль
читается как реальное значение, а резолвер обязан отличать неизвестный
контекст. Колонка `source` в таблицах доступа собирается из провенанса
доступа и его моделей, иначе после `ScanAuth` у всех было бы `auth`.

`--preset NAME` в `brief`, `show`, `explain` и `apply`, как и `preset =`
в `roster.state.toml`, ищет имя среди пресетов всех трёх слоёв: политики,
глобальных вариантов и вариантов проекта. Команды `roster` файлы
вариантов не пишут: их целиком переписывает TUI, а `roster.toml` остаётся
рукописным.

`roster apply` пишет только шапку плана (`docs/plans/`): `executor:`,
`fallback:`, `replan:` и ключи ролей, на которые ссылается `Role:` хотя бы
одного юнита. Ключи ролей без юнитов удаляет, `Executor:` юнитов не
трогает, прочие ключи и их порядок сохраняет, новые ставит после
`executor:`/`fallback:`. Открытый юнит, которому условия не дают
цепочки `executor` или его роли, останавливает `apply` до записи: без
ключа план ушёл бы в legacy-маршрут или упал бы на `lint` уже после
правки. План — `draft`, `active` или `frozen`; идёт
прогон (`run.lock`) — код 5. После записи план проверяется `lint`, при
ошибке файл восстанавливается и код 2. Предупреждения (`roster …` в
stderr) не меняют код успеха: юнит с `Executor:` вне текущих условий,
`Read:`-прокси больше бюджета, роль без fallback. Изменений нет — код 1;
`apply` не коммитит. `--json` сохраняет код выхода.

`roster explain` сравнивает объединение ключей шапки плана и брифа, а
предупреждения фильтрует по ролям плана (`executor`, `replan` и роли из
`Role:`), поэтому строка совпадает с тем, что сделает `apply`, и пустая
`heavy` не шумит на плане без heavy-юнитов.

## Рабочее место ростера

Для планирования пункта Backlog рабочее место перечитывает активный бриф
и берёт первый маршрут `heavy`, а при пустой цепочке — первый `executor`.
Выбранный на «Проекте» план не служит источником маршрута нового плана.
Если обе цепочки пусты, запуск отказывается и показывает промпт для
ручного переноса. `Workspace.PlanningRoute` возвращает обычный
`agents.Route` без зависимости от терминала; интерактивные argv описаны
в [профилях агентов](runner.md#профили-агентов), клавиши — в
[терминальном приложении](tui.md#экраны).

Модель рабочего места ростера не содержит историю активности прогона.
Объединение дельт сообщений и ссылки на исходный лог принадлежат модели
экрана прогона и не меняют разрешение политик и вариантов.
Шапка и строки юнитов на «Прогоне» показывают наблюдавшийся маршрут
раннера; для ещё не запущенного executor-юнита маршрут берётся из шапки
плана. Сводка usage относится к прогону и не служит бюджетом или условием
ростера. Представление потока описано в
[терминальном приложении](tui.md#история-и-просмотр).
В повторе прошлого прогона маршруты читаются из журнала: текущие условия,
активный вариант и нынешняя шапка плана его не пересчитывают. Просмотр
не применяет вариант и не меняет состояние ростера.

Экран ростера читает модель `roster.LoadWorkspace(rosterPath, root)` —
простую структуру без зависимости от терминала: доступы (каналы, `kind`,
`auth`, число моделей каталога, эффективный бюджет, `check`/`trusted`,
действующий allowlist и deny и последние дни `off --until` и `expires`),
варианты с источником и путём файла, активный пресет, цепочки ролей
брифа с бюджетом и `why`, предупреждения. Проектный слой пресетов
берётся из `root`, а не из рабочего каталога: модель показывает тот
проект, который ей передали.

- Отсутствующий `roster.toml`, v1-ростер и пустой каталог — признаки
  модели, а не ошибка загрузки: экран говорит, какой файл создать, и сам
  запускает `roster scan` или миграцию (ниже). Сломанный бриф
  (check-доступ без независимого ревьюера, роль без `[role]`) — тоже
  признак: доступы остаются, чтобы причину было чем исправить.
- Скан и миграция — те же функции, что у CLI: экран вызывает
  `roster.ScanCatalog` без `--online` в фоне и `roster.MigrateFile(path,
  true)` после предпросмотра нового текста, старый ростер остаётся в
  `roster.toml.bak`. Сводка скана — число моделей по доступам, а
  предупреждения источников идут строками под цепочками вместе с
  предупреждениями брифа. Скан пишет только кэш каталога; миграция пишет
  `roster.toml` и поэтому проверяет checkout lock в момент записи.
- Чтение не меняет файлы: истёкший `off` отбрасывается в памяти, а
  `roster.state.toml` переписывает только следующая мутация.
- Правки идут операциями рабочего места (`off`/`on` с датой, `budget`,
  `expire`, `allow`/`deny` и снятие названного glob, выбор и сброс пресета,
  `reset`): операция проверяет доступ и пресет по политике, валидирует
  условия и пишет через `State.Save`. Отказ не меняет ни файл, ни модель;
  экран перечитывает рабочее место после успешной записи. Снятие glob
  правит только условия: списки `roster.toml` остаются, потому что файл
  рукописный. `reset` политику не читает: снять условия — способ выйти и
  из сломанного ростера.
- «Сохранить условия как вариант» пишет разницу, которую условия дают
  против `roster.toml`, в глобальный или проектный файл вариантов.
  Пресет не умеет дат, запретов и уровня `normal`, поэтому такое условие —
  ошибка, а не вариант с другим смыслом; порядок доступов активного
  пресета сохраняется ключом `order`. Имя проверяется по всем трём слоям.
  Сохранение выбирает новый вариант курсором, но не активирует его:
  `Enter` в панели вариантов меняет условия, `A` отдельно записывает
  шапку выбранного плана. Перед запуском проектный вариант и шапку нужно
  закоммитить; `c` на «Проекте» включает оба файла.
- Удаляется вариант только из машинного файла: пресет `roster.toml` —
  ошибка с путём файла, рукописный файл docflow не переписывает. Вариант,
  который стоит в условиях, снимается вместе с удалением; проектный файл
  пишется только при свободном `run.lock`.
- `ExplainPlan` и `ApplyPlan` — те же разница шапки и запись, что у
  `roster explain` и `roster apply`: тот же отказ при `run.lock`, тот же
  откат после `lint`, второго пути записи шапки нет. Экран открывает их
  клавишей `A` с «Проекта» и с самого ростера для плана, выбранного в
  дереве, и держит отказ рядом с разницей в диалоге; карточка плана
  предупреждает о расхождении активного варианта с шапкой.

## Миграция

`roster migrate` читает ростер старого формата, печатает политику v3 и с
`--write` атомарно заменяет `roster.toml`, сохраняя старый текст в
`roster.toml.bak`. Правила:

- **v1** (`spend`, `[provider]`, `[role]`, `[route]`, `[profile]`):
  префикс модели Pi/OpenCode становится доступом; самый сильный маршрут
  модели даёт одну запись `[route."ACCESS/MODEL"]` — усилие маршрута
  становится ключом (`-` остаётся `-`), ступень — классом; модели доступа —
  точные id из маршрутов (не `*` и не пустой allowlist); профиль —
  пресетом.
- **v2**: файл переписывается на месте — `[model]` и `[effort]` дают по
  одной записи `[route]` на модель: ключ — пин из `[effort]`, а без пина —
  усилие лестницы классов (cheap → low, standard/strong → high), как v2
  и резолвил; класс — из `[model]`, а для пина без класса — автоматический
  класс по имени модели. Комментарии внутри `[model]`/`[effort]` пропадают,
  весь остальной файл (бюджеты, пресеты, комментарии) остаётся как был,
  строка версии становится `version = 3`.
- `spend` профиля даёт пресету `order` плюс `off` для доступов, которые
  профиль не называет: в v1 профиль заменял верхний порядок, и голый
  `order` перестал бы беречь доступ.
- Отличающееся переопределение флагов провайдера в профиле — комментарий
  в пресете, а не ошибка и не правка `[access]`.
- Миграция валидирует вход парсером v1 и проверкой «маршрут в spend», но
  не подбирает цепочки: ростер с ролью из одного маршрута конвертируется.
- Сгенерированный текст перечитывается `ParsePolicy` до возврата и
  записи: форма, которую v3-парсер не принимает, — ошибка миграции.
- Уже v3-ростер — код 2, ничего не пишется. Остальные команды читают
  только v3: файл старого формата даёт код 2 с подсказкой
  `docflow roster migrate`.
- `bench/roster.toml` переведён на v3 вручную рядом с каталогом
  `bench/catalog.json`; бенчмарк из-за этого не перезапускается, а
  изменившиеся цепочки записаны в `docs/design/bench.md`.

## Сценарий

Приёмка P055: `claude` и `local` выключены, `codex` по минимуму, `zai`
только flash, `opencode-go` первым. Пресет `low` из примера политики
даёт:

`zai` с `check = true` не судит и остаётся в матрице `review:` как

юнитов и цепочку `fallback:` — ростер в прогоне уже не участвует.

## Открытые вопросы

- Значения `share`, `class_factor` и границ `20000..250000` подобраны по
  текущим моделям; обкатка покажет, не надо ли их менять.
- Условия и пресеты пока не умеют задавать `check`/`trusted`: это
  стабильные свойства политики, и расширение временного слоя сюда не
  планируется.
