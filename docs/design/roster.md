# Ростер

Ростер — отдельная подсистема планирования: собирает доступные модели,
держит таблицу «доступ × роль» с именованными политиками поверх неё и
временные условия, а на выходе даёт цепочки маршрутов ролей, бюджет
чтения юнита и объяснение выбора.
Резолвинг идёт только при составлении плана; **раннер ростер не читает**,
`run`, `lint` и `cycle` не получают новой логики, формат плана остаётся
`docflow: 3` без новых ключей. Временное условие действует на новый план
или на явный `roster apply`, а не на идущий прогон: это цена
воспроизводимости плана.

Раннер по-прежнему проверяет квоту на старте прогона; живые квоты в v2 не
опрашиваются. Осознанная граница первого релиза: планирование использует
auth-статус, expiry и условия, второго источника правды о квоте нет.

## Слои

| Слой | Файл | Что хранит | Кто меняет |
|---|---|---|---|
| Каталог | `$XDG_CACHE_HOME/docflow/roster/catalog.json` | найденные доступы, модели, контекст, цену, ризонинг, auth | `roster scan` |
| Политика | `~/.config/docflow/roster.toml` (или `--roster PATH`) | доступы в порядке приоритета, `check`, таблица ячеек «роль → модель@усилие» | человек, `roster web` |
| Варианты | рядом с политикой, `roster.variants.toml` | именованные политики: `off`, порядок, ячейки поверх таблицы | `roster web` (машинный файл) |
| Варианты проекта | `docs/roster.variants.toml` от корня checkout | политики проекта, общие для всех машин | `roster web`, файл коммитится |
| Условия | рядом с политикой, `roster.state.toml` | `off/on`, expiry, активная политика | `roster off|on|expire|reset` |
| Резолвер | — | кандидаты, цепочки, матрица ревью, бюджет, предупреждения | `roster brief/show/explain/apply` |

Каталог расходный: его перезапишет следующий `scan`, файл с незнакомым
`version` считается отсутствующим. Условия не переписывают политику —
временное состояние живёт отдельным файлом и в `roster.toml` не попадает.
Пакет `internal/roster` не импортирует `internal/runner`; `apply` вправе
использовать `cycle`, `format` и `lint`.

Связь с прошлым: формат `Role:` и ключи ролей в шапке — [P036](../archive/P036-roster.md);
локальный маршрут `pi | strata/…` и отображение `Local` без квоты —
[P043](../archive/P043-local-worker.md). Этот документ заменяет v1-описание
ростера (`spend`, `[provider]`, `[route]`, `[profile]`) на политику v2 —
замена проведена [P055](../archive/P055-roster-v2.md): каталог, условия,
резолвер, миграция и удаление v1-пути. Классы маршрутов v3
([P059](../archive/P059-roster-web.md)) заменены явной таблицей v4 —
[почему](#почему-таблица).

## Каталог

`roster scan` собирает каталог из источников в порядке слияния:

| Источник | Что даёт |
|---|---|
| `pi-store` | `~/.pi/agent/models-store.json` — точные модели Pi |
| `pi-models` | `~/.pi/agent/models.json` — собственные провайдеры пользователя |
| `pi-list` | `pi --list-models`, если store отсутствует: модели и округлённый контекст |
| `opencode` | `opencode api get /api/model` через CLI, не напрямую по сети |
| `builtin` | встроенная офлайн-таблица Codex, Claude и dsh |
| `auth` | пробы авторизации Pi, OpenCode, Codex, Claude; у dsh — только наличие CLI |
| `models.dev` | необязательное обогащение с `--online` |

Правила:

- `ScanPi` сливает store, затем `pi-list` (только при отсутствии store),
  затем `models.json`: точный конфиг перекрывает округлённую таблицу, а
  неизвестное поле остаётся заполненным предыдущим источником. Пустое не
  затирает непустое, поэтому `reasoning = false` не перекрывает `true`.
- `Agents` доступа при слиянии объединяются: `opencode-go` может
  приходить через `pi` и через `opencode`, и это один доступ — одна
  единица квоты. `ModelInfo.Provider` — имя провайдера, как его отдал
  источник; `family`/`headers` OpenCode не декодируются (в `headers` есть
  идентификаторы организации).
- `ModelInfo.Agents` — каналы, чей каталог перечислил модель: store Pi
  знает весь платный каталог OpenCode Zen, а CLI OpenCode без ключа Zen —
  только бесплатные модели. Пустой список (старый кэш) — «любой канал».
- У OpenCode цена — массив живого API, берётся первый элемент; `Efforts`
  — id вариантов, потому что роутер передаёт их как `#variant`.
- Контекст и `max_out`, равные нулю, означают «неизвестно», а не ноль
  токенов. `Cost` — указатель: `nil` значит «цена неизвестна», и модель не
  выдаётся за бесплатную.
- `Provenance map[string]string` хранит источник каждого поля: единый
  `Source` — это последний вклад, он скрывает, пришёл ли контекст из
  точного store или из округлённой таблицы `pi --list-models`.
- Auth-статус — свёрнутое поле на доступ (`ready`, `not_ready`,
  `unknown`; готовый канал побеждает) и `Channels` — ответ каждого канала:
  маршрут идёт через одного агента, и доступ, готовый через `opencode`,
  не делает готовым `pi` без ключа. Claude без конфига и без CLI —
  `unknown`, не `not_ready`: скан не догадывается о машине, которой не
  видел. У OpenCode выключен только провайдер с `activation: disabled`;
  `enabled` и `auto` (так сервер отвечает на сохранённый вход OpenCode Go)
  — готовы.
- `kind` скан ставит доступам, которые узнаёт: `opencode` — OpenCode Zen,
  `metered`; `opencode-go` — OpenCode Go, `subscription`; `zai`, `codex`,
  `claude` и `deepseek-account` — `subscription`, но Codex, вошедший по
  API-ключу, — `metered`; `deepseek-official` — `metered`;
  провайдер `models.json` с `baseUrl` на loopback, частном адресе или
  имени без точки/`.local` — `local`. Базовый URL только классифицирует и в
  кэш не пишется. Незнакомый провайдер остаётся без `kind`: догадка о чужом
  тарифе хуже пустоты. Та же таблица даёт человеческое имя доступа
  (`AccessTitle`) для редактора.
- Ошибка источника (HTML вместо JSON, битый JSON, отсутствующий CLI) —
  предупреждение рядом с частичным каталогом, код успеха остаётся 0.
  Тело ответа в текст предупреждения не попадает; пробы печатают статусы,
  не секреты.
- Сканеры вызывают только `agentio.CallAgent` с таймаутом 30 с, не
  запускают модели и не тратят квоту; каталог сортируется на выходе.
- `models.dev` заполняет только неизвестные поля и никогда не перекрывает
  значение сканера или встроенной таблицы. Доступ сопоставляется с
  провайдером models.dev явной картой (`codex`/`openai` → `openai`,
  `claude`/`anthropic` → `anthropic`, `opencode` и `opencode-go` →
  `opencode`, `zai` → `zai`), не по префиксу. Кэш `models.dev.json` лежит рядом с каталогом, TTL — сутки,
  `--refresh` ходит в сеть заново; без сети остаются встроенные метаданные.
- Встроенная таблица Codex берёт `context_window` самого CLI (500k у
  `gpt-6.1-sol`, 272k у `gpt-6-luna`), а не API-окно models.dev: CLI
  определяет, сколько реально доступно юниту.
- Встроенная таблица dsh — каталог `dsh-llm-deepseek` 0.2.2-rc.1:
  `deepseek-flash` и `deepseek-v4-pro` у обоих провайдеров dsh
  (`deepseek-account` — подписка DeepSeek, `deepseek-official` —
  `DEEPSEEK_API_KEY`), окно 1M, `max_out` 256k, усилия `off`/`low`/`high`/
  `max`, цена неизвестна. Вход dsh без генерации не проверить: с `dsh` на
  PATH доступы `unknown` (маршрут идёт), без него — `not_ready` молча —
  таблица перечисляет доступы dsh на любой машине
  ([P061](../archive/P061-dsh-roster-model.md)).
- Кэш каталога пишется атомарно, `version = 1`; файл с другим `version`
  читается как пустой без ошибки. `--refresh` пересканирует локальные
  источники и игнорирует свежий кэш models.dev; без `--online` флаг
  ничего не меняет.

## Политика `roster.toml`

Версия формата — `version = 4`: явная таблица «доступ × роль». Ростер
старого формата (v1 без `version`, v2 и v3 с классами) даёт код 2 и
подсказку `docflow roster migrate`. Разбор строгий: неизвестный ключ, имя
доступа с пробелом, `/`, `|`, `,` или `=`, неизвестная роль — ошибка с
файлом и строкой.

```toml
version = 4

# Порядок доступов в файле — приоритет по умолчанию: цепочка роли — её
# столбец сверху вниз.
[access.opencode-go]
agents  = ["pi", "opencode"]     # каналы одного доступа
kind    = "subscription"         # subscription | metered | local
expires = "2026-12-31"           # необязательная дата

[access.opencode-go.roles]       # строка таблицы: роль = "МОДЕЛЬ@УСИЛИЕ"
executor = "deepseek-v4.1@high"
cheap    = "deepseek-v4.1-flash@high"
heavy    = "deepseek-v4.1@max"
review   = "deepseek-v4.1@high"

[access.zai]
agents = ["pi"]
kind   = "subscription"
check  = true                    # нужен независимый ревьюер; сам не судит

[access.zai.roles]
executor = "glm-5.3@high"
cheap    = "glm-5.3-flash@low"
heavy    = "glm-5.3@max"

[access.codex]
agents = ["codex"]
kind   = "subscription"

[access.codex.roles]
heavy      = "gpt-6.1-sol@high"
acceptance = "gpt-6.1-sol@medium"
replan     = "gpt-6.1-sol@medium"

[access.local]
agents = ["pi"]
kind   = "local"
check  = true

[access.local.roles]
cheap = "strata/swift-1.5-iq3_s"  # без @ — усилие не передаётся
```

- **Доступ** — единица квоты и независимости, а не провайдер. Подписка
  `opencode-go` одна, даже если к ней ходят `pi` и `opencode`; fallback
  повторяет доступ, а не пару `agent|model`.
- `agents` обязателен и непуст (`claude`, `codex`, `pi`, `opencode`,
  `dsh`); порядок — предпочтение среди каналов
  одной квоты (см. резолвер). `kind` — тип оплаты: `subscription` — квота
  плана, `metered` — оплата за токены, `local` — своя машина. Ключ в
  политике переопределяет то, что определил скан; без ключа действует
  `kind` каталога. Маршрут `kind` не меняет — это подпись для человека.
- **Ячейка** `[access.NAME.roles]` — модель и усилие, которыми доступ
  закрывает роль: `МОДЕЛЬ@УСИЛИЕ` (усилие — после последнего `@`) или
  голая `МОДЕЛЬ` без усилия. Нет ключа роли — доступ роль не берёт; пустая
  строка в базовой таблице — ошибка (ключ просто не пишется). Один доступ —
  не больше одной ячейки на роль.
- `check = true` исключает доступ из судейских ролей: ячейка `review`,
  `acceptance` или `replan` у check-доступа — ошибка политики. Отдельного
  `trusted` нет: судья — тот, у кого стоит ячейка судейской роли.
- Пресетов в `roster.toml` нет — политики живут в файлах вариантов.
- Удалённые ключи v3 (`budget`, `trusted`, `models`, `exclude`, `[route]`,
  `[role]`, `[preset]`) дают ошибку с подсказкой миграции, а не молчат.

Почему таблица ([v4 ниже](#почему-таблица)): в v3 ячейку вычислял
резолвер — класс маршрута по `[route]` или по имени семейства, минимальный
класс роли по `[role]`, сравнение «не меньше» и фильтр бюджета. Итог
видно было только в брифе, и править его было нечем.

### Варианты `roster.variants.toml`

Вариант (в интерфейсах — «политика») — именованное отличие от таблицы
по умолчанию. Глобальный файл `roster.variants.toml` лежит рядом с
`roster.toml`, проектный — `docs/roster.variants.toml` от корня checkout.
Файл содержит `version = 3` и только таблицы `[preset.NAME]`.

```toml
version = 3

[preset.zai-first]
order = ["zai", "opencode-go"]   # эти доступы первыми, остальные — по политике
off   = ["local"]                # выключены в этой политике

[preset.zai-first.roles.codex]   # ячейки, которые политика меняет
executor = "gpt-6-luna@high"
heavy    = ""                    # пустая строка — очистить ячейку
```

- Политика по умолчанию — сама таблица `roster.toml`; удалить её нельзя.
  Остальные создаются, переименовываются и удаляются в `roster web`.
- `off`, `order` и ячейки — всё, что умеет политика: `prefer` — это
  `order`, бывшие `lean`/`minimal` — очищенные ячейки, видимые в таблице.
  Ячейка политики проверяется тем же правилом `check`.
- Загрузчик сливает два слоя: глобальные варианты, затем проектные.
  `Preset.Source` называет слой — `variants` или `project`. Одно имя в двух
  файлах — ошибка с обоими путями: `--preset NAME` значит одно и то же
  везде. Вариант, называющий неизвестный доступ, — ошибка; отсутствие
  файла — пустой слой.
- Файлы вариантов машинные: веб-редактор пишет файл целиком
  (`SaveVariants`, атомарно, с перечитыванием парсером), комментарии и
  ручной порядок не сохраняются.

## Условия `roster.state.toml`

Условия — временный слой поверх политики, соседний файл
`roster.state.toml` (у `--roster PATH` — то же имя с `.state.toml`).
Отсутствие файла — отсутствие условий, не ошибка. Файл пишут только
команды условий; команды чтения его не переписывают.

```toml
version = 2
preset = "zai-first"
off = ["claude", "local"]

[until]
claude = "2026-11-30"      # последний день, когда off ещё действует
[expires]
codex = "2026-12-31"
```

- `off ACCESS [--until DATE]` выключает доступ до конца указанного дня
  включительно или до `on`. Истёкший `off` отбрасывается в памяти при
  загрузке; файл переписывает только следующая мутация.
- `on ACCESS` снимает `off` и его дату.
- `expire ACCESS DATE` убирает доступ после даты; условие может только
  сократить срок политики, не продлить.
- `reset` удаляет файл состояния.
- Разовые флаги `brief`/`show`/`explain`/`apply` (`--preset`, `--off`,
  `--expires`) применяются к in-memory состоянию и никогда не сохраняются.
- Условие, называющее доступ или пресет, которых нет в политике, — код 2
  до любой записи. Ключи `budget`, `models`, `exclude` старого состояния —
  ошибка с подсказкой `roster migrate` (или `roster reset`).

## Резолвер

Резолвер сливает политику с условиями и каталогом. Цепочка роли — столбец
таблицы сверху вниз: доступы в порядке политики (или порядке активного
пресета), от каждого — его ячейка роли. Доступ без ячейки, выключенный,
истёкший, неизвестный каталогу или с `auth not_ready` ничего не даёт;
причина пишется в `Skipped`.

- Модель ячейки ищется в каталоге доступа: нет её там — ячейка
  пропускается с причиной «model … is not in the catalog; run `docflow
  roster scan`».
- Агент маршрута (`RouteAgent`) — первый канал из `agents`, который
  перечисляет модель и у которого вход `ready`, иначе первый такой с
  `unknown`; канал с `not_ready` маршрут не получает. Нет подходящего
  канала — ячейка пропускается с причиной («no channel with auth» или
  «listed only by …»). Кэш без `Channels` берёт свёрнутый auth доступа.
- Модель маршрута через `pi`, `opencode` и `dsh` — `ACCESS/ID`
  (`deepseek-account/deepseek-v4-pro`), через `codex` и `claude` — голый id.
- Заполненная ячейка, которую резолвер пропустил (не «нет ячейки» и не
  `check`), — предупреждение брифа `ACCESS: причина; skipped for ROLE`:
  иначе ошибочная ячейка молча выпадала бы из цепочки.
- Для `heavy` нужен известный контекст: модель с `context unknown` не
  ставится в тяжёлую роль.
- Усилие кандидата — ровно то, что в ячейке; модель без `@` идёт без
  усилия. Строка брифа и `why:` печатают `access/model@effort`.
- check-доступ в судейскую роль не попадает (это и так ошибка политики).

Цепочка роли — по одному маршруту с разных доступов; fallback повторяет
доступ, а не агента. Строка матрицы `review:` — только `check`-доступы,
реально дающие маршрут; выключенный `check`-доступ юнитов не производит и
ревьюера не требует. Нет независимого ревьюера — ошибка политики, а не
self-review. Пустая цепочка роли и цепочка из одного маршрута —
предупреждения брифа: резолвер не знает, какие роли использует план.
`apply` отказывает до записи, если пустая цепочка нужна открытому юниту,
а план с юнитом такой роли иначе упал бы на своём ключе в `lint`.

## Бюджет контекста

Бюджет чтения юнита — рекомендация брифа для нарезки плана, не ключ плана
и не проверка `lint`:

```
usable = context - max_out - reserve
target = clamp(usable * share, 20000, 250000)
reserve = max(10% context, 32000)
```

`share` роли: `cheap 0.25`, `executor 0.35`, `heavy 0.45`; у судейских
ролей бюджета нет — они читают diff и вывод тестов (`scope = diff/test`).
Множителя класса больше нет: классы ушли вместе с v3. Неизвестный
контекст даёт нулевой `Target` и строку `context unknown` в `why`, а не
догадку; неизвестный `max_out` считается нулём, и `why` это говорит.
`roster apply` только предупреждает о юните, чей `Read:`-прокси больше
бюджета роли.

## Команды

Все команды принимают `--roster PATH`; каталог и состояние живут вне
рабочего дерева.

| Команда | Что делает |
|---|---|
| `roster scan [--online] [--refresh] [--json]` | собирает каталог, пишет кэш, печатает сводку доступов; ошибка источника — предупреждение в stderr при коде 0 |
| `roster models [ACCESS] [--all] [--json]` | модели доступа, ростерных доступов или всего каталога; читает только кэш. Неизвестный `ACCESS` — код 2 со списком известных; пустой кэш — код 0 с подсказкой `roster scan` |
| `roster status [--json]` | доступы с каналами, `kind`, auth (канал с другим ответом — в скобках: `ready(pi:not_ready)`), числом моделей и источниками, затем активные условия с источником; только кэш |
| `roster brief [--preset NAME] [разовые флаги] [--json]` | условия в силе, цепочка, бюджет и scope каждой роли, матрица `review:`, `why:` и предупреждения |
| `roster show` | алиас `brief` |
| `roster explain PLAN [--json]` | сравнивает шапку плана с брифом и печатает `ключ: старое → новое` и предупреждения ролей плана; ничего не пишет |
| `roster apply PLAN [--preset NAME] [разовые флаги] [--dry-run] [--json]` | пишет шапку плана; см. ниже |
| `roster off`, `on`, `expire`, `reset` | правят `roster.state.toml` |
| `roster migrate [--dry-run]` | переводит ростер v1, v2 или v3 на v4 вместе с файлами вариантов и условиями |
| `roster web [--addr ADDR]` | браузерный редактор таблицы «доступ × роль» и политик на 127.0.0.1; см. «Веб-редактор» |

`scan`, `models` и `status` принимают `--json`. Неизвестные `context`,
`max_out` и цена печатаются как `unknown`, не как `0` или прочерк: ноль
читается как реальное значение, а резолвер обязан отличать неизвестный
контекст. Колонка `source` в таблицах доступа собирается из провенанса
доступа и его моделей, иначе после `ScanAuth` у всех было бы `auth`.

`--preset NAME` в `brief`, `show`, `explain` и `apply`, как и `preset =`
в `roster.state.toml`, ищет имя среди вариантов обоих слоёв: глобального и
проектного. Команды `roster` файлы
вариантов не пишут: их целиком переписывает веб-редактор, он же правит
`roster.toml` («Веб-редактор»).

`roster apply` пишет только шапку плана (`docs/plans/`): `executor:`,
`fallback:`, `replan:` и ключи ролей, на которые ссылается `Role:` хотя бы
одного юнита. Ключи ролей без юнитов удаляет, `Executor:` юнитов не
трогает, прочие ключи и их порядок сохраняет, новые ставит после
`executor:`/`fallback:`. Открытый юнит, которому условия не дают
цепочки `executor` или его роли, останавливает `apply` до записи: без
ключа план ушёл бы в legacy-маршрут или упал бы на `lint` уже после
правки. План — `draft`, `active` или `frozen`; идёт
прогон (`run.lock`) — код 5. После записи план проверяется `lint`, при
ошибке файл восстанавливается и код 2. Предупреждения (`roster …` в
stderr) не меняют код успеха: юнит с `Executor:` вне текущих условий,
`Read:`-прокси больше бюджета, роль без fallback. Изменений нет — код 1;
`apply` не коммитит. `--json` сохраняет код выхода.

`roster explain` сравнивает объединение ключей шапки плана и брифа, а
предупреждения фильтрует по ролям плана (`executor`, `replan` и роли из
`Role:`), поэтому строка совпадает с тем, что сделает `apply`, и пустая
`heavy` не шумит на плане без heavy-юнитов.

## Веб-редактор

`roster web` поднимает локальный сервер на `127.0.0.1` (флаг `--addr`
задаёт порт, по умолчанию случайный) со встроенным UI. Экран — одна
таблица «доступ × роль»: строка — доступ (порядок строк — приоритет),
столбец — роль, столбцы сгруппированы в «исполнение» и «судьи». Ячейка —
выбор модели из каталога скана для этого доступа или «—» и под ним выбор
усилия: уровни, которые объявил источник каталога, а у модели с
ризонингом без объявленных уровней — уровни её агентов (`pi` —
`off…xhigh`, `codex` — `low…xhigh`, `claude` — `low…max`; у доступа с
несколькими каналами — общие для них, `opencode` список не сужает);
«по умолчанию» пишет модель без `@`. Номер в ячейке — её место в цепочке
роли, в заголовке столбца — число маршрутов и предупреждение при одном
или нуле. Столбец доступа закреплён при горизонтальной прокрутке; в нём
стрелки приоритета, имя провайдера и тип оплаты («OpenCode Zen · за
токены»), каналы с отметкой входа (`pi ✗`, `opencode ✓`) и, у доступа с
несколькими каналами, выбор «через …» — какой канал первый в `agents`.
Тип оплаты — «авто: …» (как определил скан) или явное значение; явное,
расходящееся со сканом, подсвечено. У доступа не по подписке в списке
моделей видна цена `$вход/$выход` за миллион токенов или «бесплатно».
Ячейка, которую резолвер не запустит (нет модели в каталоге, нет канала
со входом), отмечена `!` с причиной, в цепочке зачёркнута и не считается;
маршрут в цепочке называет своего агента. Вкладки сверху — политики: `default`
(сама `roster.toml`, удалить нельзя) и варианты; «сделать активной»
пишет `preset` в условия. На вкладке варианта ячейка, отличная от
`default`, подсвечена, пункт «↩ … (default)» снимает отличие, «—» очищает
ячейку только в этой политике; стрелки двигают доступ в порядке варианта,
флажок «в политике» пишет его `off`. Под таблицей — итоговые цепочки
этой вкладки (столбец сверху вниз без выключенных доступов) и
предупреждения; модель, которой нет в каталоге, отмечена.

Без `roster.toml` редактор открывается с пустой таблицей и подсказкой:
первый доступ из каталога создаёт файл (и его каталог) — так ростер
начинается с нуля без ручного TOML. Отказ в первом доступе файла не
создаёт.

Пишет редактор в два места: `roster.toml` — атомарной полной записью
(`SavePolicy`: временный файл, перечитывание парсером, rename; комментарии
и ручная вёрстка не сохраняются) и файлы вариантов — через `SaveVariants`.
Операции — методы рабочего места: `AddAccess`, `RemoveAccess`,
`SetAccessCheck` (включение `check` убирает судейские ячейки доступа во
всех слоях), `SetAccessKind` (пустое значение — «авто»; доступ из
каталога добавляется без `kind`, чтобы действовал скан),
`SetAccessAgent` (ставит канал первым в `agents`), `MoveAccess`,
`SetCell`; `CreateVariant`, `RenameVariant`,
`DeleteVariant`, `SetVariantOff`, `MoveVariantAccess`, `SetVariantCell`
(значение, пустая строка или `inherit`); `SetPreset`. Каждая операция
валидирует политику до записи; отказ не меняет ни файл, ни модель.
Пишущие запросы сериализованы одним мьютексом.

Остаётся за CLI: каталог собирает только `roster scan` (веб читает кэш),
временные условия правят `off/on/expire/reset`.
Пакет сервера — `internal/roster/web`, импортирует только `internal/roster`
и стандартную библиотеку; фронтенд — нативные HTML/JS без сборки и
внешних CDN.

## Рабочее место ростера

Модель `roster.LoadWorkspace(rosterPath, root)` — простая структура без
зависимости от интерфейса, её читают CLI и веб-редактор: доступы (каналы, `kind`,
`auth`, число моделей каталога, `check`, ячейки политики и ячейки в силе,
выключатель и последние дни `off --until` и `expires`), порядок в силе,
варианты с источником и путём файла, активный пресет, цепочки ролей
брифа с бюджетом и `why`, предупреждения. Проектный слой пресетов
берётся из `root`, а не из рабочего каталога: модель показывает тот
проект, который ей передали.

- Отсутствующий `roster.toml`, v1-ростер и пустой каталог — признаки
  модели, а не ошибка загрузки: клиент говорит, какой файл создать, и
  запускает `roster scan` или миграцию (ниже). Сломанный бриф
  (check-доступ без независимого ревьюера) — тоже
  признак: доступы остаются, чтобы причину было чем исправить.
- Скан и миграция — те же функции, что у CLI: клиент вызывает
  `roster.ScanCatalog` без `--online` и `roster.MigrateFile(path,
  true)` после предпросмотра нового текста, старый ростер остаётся в
  `roster.toml.bak`. Сводка скана — число моделей по доступам, а
  предупреждения источников идут строками под цепочками вместе с
  предупреждениями брифа. Скан пишет только кэш каталога; миграция пишет
  `roster.toml` и поэтому проверяет checkout lock в момент записи.
- Чтение не меняет файлы: истёкший `off` отбрасывается в памяти, а
  `roster.state.toml` переписывает только следующая мутация.
- Правки условий идут операциями рабочего места (`off`/`on` с датой,
  `expire`, выбор и сброс пресета, `reset`): операция проверяет доступ и
  пресет по политике и пишет через `State.Save`. Отказ не меняет ни файл,
  ни модель; клиент перечитывает рабочее место после успешной записи.
  `reset` политику не читает: снять условия — способ выйти и из
  сломанного ростера. Ячейки правит `roster web`.
- «Сохранить условия как вариант» пишет активную политику вместе с
  выключенными условиями доступами в глобальный или проектный файл
  вариантов. Политика не умеет дат, поэтому датированный `off` и `expires`
  — ошибка, а не вариант с другим смыслом. Имя проверяется по обоим слоям.
  Сохранение не активирует вариант и не пишет шапку плана. Перед
  запуском проектный вариант и шапку нужно закоммитить.
- Вариант, который стоит в условиях, снимается вместе с удалением;
  проектный файл пишется только при свободном `run.lock`.
- `ExplainPlan` и `ApplyPlan` — те же разница шапки и запись, что у
  `roster explain` и `roster apply`: тот же отказ при `run.lock`, тот же
  откат после `lint`, второго пути записи шапки нет.

## Миграция

`roster migrate` читает ростер старого формата и атомарно заменяет
`roster.toml`, файлы вариантов и условия, сохраняя старый текст каждого в
`ФАЙЛ.bak`; с `--dry-run` только печатает политику v4 и файлы, которые
перепишет. Запись по умолчанию — как у `roster apply`: миграция
обратима через `.bak`, а молчаливый предпросмотр читался как «ничего не
произошло». Старый `--write` принимается и ничего не меняет.
Цепочка: v1 → v3 → v4, v2 → v3 → v4.

- **v1** (`spend`, `[provider]`, `[role]`, `[route]`, `[profile]`):
  префикс модели Pi/OpenCode становится доступом; самый сильный маршрут
  модели даёт одну запись `[route]` v3 — усилие маршрута становится
  ключом, ступень — классом; профиль — пресетом.
- **v2**: `[model]` и `[effort]` дают по записи `[route]` v3 на модель.
- **v3 → v4**: миграция один раз прогоняет правила v3 (класс по `[route]`
  или по семейству, минимальный класс роли, `trusted`, бюджеты,
  allowlist) и записывает их итог ячейками. Модели берутся из кэша
  каталога, а для доступа, которого каталог не знает, — из `[route]` и
  точных id allowlist; пустой кэш — примечание в stderr. Поэтому
  `roster scan` работает и на ростере старого формата (только пропускает
  проверку недостающих доступов и подсказывает `migrate`): сначала скан,
  потом миграция. Порядок доступов — порядок кандидатов v3: `prefer`, `normal`,
  `lean`, `minimal`, затем `off`. Доступ с `budget = "off"` получает свои
  ячейки и условие `off` в `roster.state.toml`.
- Пресет v3 (из `roster.toml` или файла вариантов v2) становится вариантом
  v3-файла: его `off`, его порядок, если он отличается от базового, и
  ячейки, которые он меняет (пустая ячейка — роль, которую пресет у доступа
  отнимал). Пресеты `roster.toml` переезжают в глобальный файл вариантов;
  файл, уже записанный в текущей версии, не переписывается, а только
  дополняется перенесёнными пресетами.
- Условия `budget = "off"` становятся `off`; остальные бюджеты, `models`
  и `exclude` отбрасываются с примечанием в stderr.
- Сгенерированные тексты перечитываются парсерами v4 до записи. Уже
  v4-ростер — код 2, ничего не пишется. Остальные команды читают только
  v4: файл старого формата даёт код 2 с подсказкой `docflow roster migrate`.
- `bench/roster.toml` переведён на v4 той же миграцией по
  `bench/catalog.json`; цепочки бенчмарка не изменились.

(`claude`, `local`, `opencode` выключены, у `zai` очищена ячейка
`executor`) даёт:

```

-       preset     low         state
```

цепочку `fallback:` — ростер в прогоне уже не участвует.

## Почему таблица

Решение 2026-11-08, принято без отдельного плана по просьбе пользователя
после первой версии `roster web`. В v3 роль закрывалась косвенно: класс
маршрута (`[route]` или автоматический по имени семейства), минимальный
класс роли (`[role]`, сравнение «не меньше»), бюджет доступа
(`prefer/normal/lean/minimal/off`) и `trusted`. Редактор показывал
итоговые цепочки отдельным блоком, но править их было нельзя: модель
попадала в роль, которую человек не выбирал (`standard` проходит в
`cheap`), а автоматический класс ставил в роли модели, которых в
карточке не было видно. Таблица делает источник правды тем, что видно:
ячейка — это и есть маршрут. Что убрано: классы, `[route]`, `[role]`,
бюджеты, `trusted`, allowlist/`exclude` и их условия, команды
`roster budget|allow|deny`, флаги `--lean|--minimal|--prefer|--only`,
множитель класса в бюджете чтения. Цена: новая модель из каталога сама в
роли не встаёт, её ставят в ячейку. Отвергнуто: оставить классы и сделать
нижний блок редактируемым — два источника правды для одной цепочки.

## Почему канал и kind из скана

Решение 2026-11-08, принято без отдельного плана по просьбе пользователя.
Строка `opencode` с `agents = ["pi", "opencode"]` и `kind =
"subscription"` выглядела как подписка OpenCode Go, а была OpenCode Zen с
оплатой за токены: резолвер всегда брал `agents[0]` (pi без ключа), auth
сворачивался через «или» и показывал `ready` благодаря бесплатным
моделям Zen в CLI OpenCode, `kind` был ручной подписью, которую никто не
проверял, а настоящая подписка `opencode-go` числилась `not_ready` из-за
`activation: auto`. Теперь агент маршрута выбирается по входу канала и
по тому, знает ли канал модель; `kind` и имя доступа определяет скан;
пропущенная ячейка — предупреждение. Новых ключей формата нет: `agents`
получил смысл порядка предпочтения, `kind` в политике стал
переопределением. Отвергнуто: отдельная строка на пару «доступ × агент» —
она удвоила бы одну квоту в fallback.

## Открытые вопросы

- Значения `share` и границ `20000..250000` подобраны по текущим моделям;
  обкатка покажет, не надо ли их менять.
- Порядок доступов один на все роли; если понадобится, например, в
  `heavy` ставить codex первым, а в `executor` — zai, это решается
  ячейками политики или отдельным порядком роли — пока не нужно.
