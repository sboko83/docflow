# Цикл, размер, учёт, ветки, коммиты

## Цикл юнита

```
prompt → работа → verify* → finish   (finish = verify → done → commit)
```

Каждый шаг — отдельная команда; порядок держит записанное состояние, а не
дисциплина агента: команда отказывает, если предыдущий шаг не выполнен.

| Шаг | Делает | Отказ |
|---|---|---|
| `prompt [id]` | промпт юнита, ставит `[~]` | при `[ ]` → `[~]`: рабочее дерево грязное (кроме файла плана); повторный `prompt` юнита `[~]` дерево не проверяет |
| `verify <id> [--no-gate]` | запускает `Verify:`, затем `gate:` плана, если есть (`--no-gate` — без gate и без отпечатка); при падении — только хвост вывода; при успехе — отпечаток дерева в `.git/docflow/verified/<id>` | Verify упал (4) |
| `done <id> --handoff … [--decision …]` | `[x]`, Handoff, строки в `## Decisions` | юнит не `[~]`, нет отпечатка или дерево изменилось после `verify` (5) |
| `commit <id>` | `git add -A`, коммит: subject из `Commit:`, body из Handoff; печатает список файлов | юнит не `[x]` или дерево изменилось после `verify` (5) |
| `finish <id> --handoff … [--decision …] [--skip …]` | `verify`, `done`, `commit` одним вызовом в одном процессе; первый ненулевой код — стоп и выход с ним | как у вызванного шага |

- Отпечаток — хэш `git diff HEAD` и неотслеживаемых файлов, без файла плана,
  снятый после команды `Verify`. Почему так и порядок проверок — [P001](../archive/P001-docflow-cli.md).
  Закоммичено ровно то, что проверено.
- Чистое дерево на входе — поэтому `commit` может брать всё: изменения
  принадлежат юниту, мусор отсекает `.gitignore`.
- `finish` — путь агента: экономит ~2 запроса на юнит; раннер по-прежнему
  зовёт три команды отдельно (у него повторы между `verify` и `done`) —
  [P009](../archive/P009-docflow-retro-fixes.md).
- `verify` годится и для промежуточных итераций: при успехе — одна строка,
  экономит контекст против полного вывода сборки.
- Команды плана (`Verify:`, `gate:`, `preflight:`, prerequisites раннера) —
  POSIX sh на любой ОС: на Unix `/bin/sh -c`, на Windows `bash.exe -c` из
  Git for Windows (`<корень git>\bin\bash.exe`, корень — на один-два уровня
  выше `git.exe` из `PATH`; `System32\bash.exe` (WSL) — никогда), без Git
  Bash — `%COMSPEC% /c` — [P040](../archive/P040-windows-support.md).
- Команды `Verify:`, `gate:` и `preflight:` идут в отдельной сессии без
  терминала; Ctrl-C и сигналы остановки убивают всю их группу —
  [P029](../archive/P029-github-release.md).
- Аварийный выход: `verify --skip "<причина>"` ставит отпечаток без запуска;
  причина попадает в Handoff и body коммита. Только когда проверку нельзя
  запустить в окружении, и с согласия пользователя — [P002](../archive/P002-docflow-skills.md).
- Между `done` и `commit` можно посмотреть дифф вручную.
- `--handoff` и `--decision` повторяемы: каждое значение — отдельный пункт
  списка.
- Юнит встал посреди работы → `block <id> --reason [--needs human|plan]`
  ставит `[!]`, причина — пункт Handoff `Blocked (<needs>): …`; последний
  такой пункт решает, кто снимает блок. Блоком считаются только точные формы
  `Blocked (human): …`, `Blocked (plan): …` и legacy `Blocked: …`: похожие
  строки (`Blocked by …`, `Blocked (plan)` без `:`) блоком не считаются и
  последний настоящий блок не перебивают. Блок `plan` (план разошёлся с кодом) →
  `bsv-docflow-plan` в режиме replan правит оставшиеся юниты и снимает блок:
  в `[~]`, если работа юнита в дереве остаётся в силе (`prompt` юнита `[~]`
  дерево не проверяет), иначе в `[ ]` — [P003](../archive/P003-cli-fixes.md).
  Блок `human` — шаг, доступный только человеку (вход, устройство, доступ,
  решение): его снимает `docflow unblock <id> --note "…"` — `[~]` и пункт
  Handoff `Unblocked: …`, без коммита; пункт `Blocked: …` без класса
  считается `human`. Снятый юнит сначала проверяет условие блока: заметка —
  заявление, не доказательство. `status` по последнему пункту `Blocked`
  печатает `(needs human)` или `(needs plan)`, для человека — следующей
  строкой команду `unblock`
  ([P041](../archive/P041-human-unblock.md)).

`status` последней строкой печатает итог `lint` (`lint: ok`, `N warnings`,
`N errors — run docflow lint`); на код выхода он не влияет.

- Что изменено, но не проверено, — пункт Handoff `Unverified: …`; раннер
  берёт его из поля `unverified` result JSON и печатает. Пункт называет риск
  именно этого изменения, который не покрыт `Verify` (раскладка на
  устройстве, поток, которого нет в `Verify`, случай без теста): пункты
  чужих юнитов из `## Handoff from Depends`, идеи улучшить тесты и проверки
  кода, который юнит не трогал, в поле не пишутся. Незакрытый шаг `Do:` или
  требование Goal — не `unverified`: юнит его доделывает или становится в
  блок с `blocker: "plan"`; раннер не отличает «не проверил» от «не сделал».
  Пустой список значит, что `Verify` покрывает все риски изменения. Раннер
  выбрасывает копию пункта, уже открытого в Handoff прямых `Depends` —
  [P044](../archive/P044-unverified-discipline.md). При закрытии каждый
  открытый пункт проверяется, принимается с обоснованием
  `Accepted: <пункт> — <почему это не риск>` или переносится в Backlog, если
  остался разрыв с Goal либо риск с конкретным падающим сценарием.
  Несделанное из Goal всегда уходит в Backlog. План с изменением, видимым
  пользователю, заканчивается юнитом приёмки: сценарии по Goal, полный прогон тестов,
  `Depends:` на все юниты — [P013](../archive/P013-result-verification.md).

`prompt` содержит: Goal, Constraints, Traps, Context, `## Decisions` плана,
юнит, Handoff прямых `Depends`, инструкции по циклу. Для `Role: review`
добавляется `## Phase diff` с базой, commit subjects фазы и командой просмотра
diff; при `repos:` блоки строятся для корневого и каждого вложенного репозитория
([P038](../archive/P038-runner-backlog-batch.md)).

Следом за `## Phase diff` у review и перед `## Cycle` у acceptance стоит раздел
`## Test changes`: пункты блоков `Test changes:` из тел коммитов юнита —
строкой `- <subject коммита>: <пункт>`, у review диапазон фазы, у acceptance
весь план; когда пунктов нет — строка `none`; при `repos:` — подразделы по
репозиториям. Пункты читаются из тела коммита, поэтому источник правды у review
и приёмки тот же git: ослабленный тест виден и ревью, и приёмке ([P050](../archive/P050-verify-guard.md)).

## Размер юнита

- «≤ 220k контекста» не проверяемо: агент не знает расход заранее, а слабые
  модели деградируют уже после 80–120k. Цель — ~100k на юнит.
- Измеримые прокси: (размер промпта + файлы `## Context` + файлы и
  диапазоны из `Read:`) / 4 ≤ `read_budget`; 5–8 изменяемых файлов; один
  `Verify`. Бюджет проверяет `lint` только у открытых юнитов — [P001](../archive/P001-docflow-cli.md).
- Нижняя граница: мелкие юниты объединяются, пока прокси в пределах цели;
  план, все юниты которого вместе укладываются в цель, — один юнит; задача
  на один юнит — без плана, с согласия пользователя. Решает планировщик,
  `lint` не проверяет — [P004](../archive/P004-plan-skill-fixes.md),
  [P009](../archive/P009-docflow-retro-fixes.md).
- Размер — в байтах UTF-8: байты / 4 близки к токенам и для английского
  (~4 символа на токен), и для русского (~2 символа, 2 байта на символ).
- `path#anchor` — от заголовка до следующего заголовка того же или старшего
  уровня.

## Учёт токенов

Прокси размера юнита проверяется только против бюджета; `docflow stats`
сверяет его с фактическим расходом. Данные — `<git-dir>/docflow/stats/<id>.json`,
в дерево и коммиты не попадают.

- `prompt` пишет `{"unit", "proxy_tokens", "prompted_at"}` (прокси — тот же
  расчёт, что в `lint`; время — ISO UTC); повторный `prompt` прокси не
  затирает.
- Раннер после каждого вызова агента дописывает `sessions` (id сессий),
  `tokens` (сумма путей профиля `tokens`), `cost`, `calls`.
- `stats [Pxxx]` — строка на юнит: `unit proxy reqs sum_ctx base_ctx
  peak_ctx peak/proxy grow/proxy source`; внизу — медианы `peak/proxy` и
  `grow/proxy`. `base_ctx` — первый запрос первой сессии в порядке записи;
  `grow/proxy` = `(peak_ctx − base_ctx) / proxy`
  ([P028](../archive/P028-go-cutover.md)). Без транскрипта `base_ctx`,
  `peak_ctx` и отношения выводятся как `-`; если значений нет, медиана тоже
  `-`. Контекст запроса = `input_tokens +
  cache_read_input_tokens + cache_creation_input_tokens`; запрос считается
  один раз по `message.id` (реплика пишется несколькими строками с одним
  `usage`).
- Транскрипты Claude: `$DOCFLOW_CLAUDE_PROJECTS`, иначе
  `~/.claude/projects/<путь проекта, где каждый символ кроме [A-Za-z0-9]
  заменён на ->`. Сессии раннера — файлы `<session>.jsonl`. Интерактив —
  запросы от вызова Bash с `docflow prompt [<id>]` до вызова
  `docflow finish <id>` или `docflow commit <id>` включительно; `prompt` без
  id — id из первой строки результата (`# Pxxx.N.M`). Нет транскрипта —
  `source` = `tokens` (сумма раннера) или `-`. Формат транскрипта
  внутренний для Claude Code: строка, которую не удалось разобрать,
  пропускается.

Почему не только раннер — [P009](../archive/P009-docflow-retro-fixes.md).

Контекстный бюджет репозитория — `python3 tools/context-audit.py` из
корня: каждый вход docflow (старт-читы, скиллы, design-топики с их
Gotchas, промпт fixture-юнита) сейчас / на план / при 200 планах;
`--check` валится по бюджетам (`start_budget`, 1500 токенов описаний
скиллов, `read_budget/2` у ranged-промпта), включая текущий размер при
убывающей проекции. Чтения агента сверх `Read:` юнита —
`tools/read-audit.py` по транскриптам
([P047](../archive/P047-context-audit.md)).

## Ветки и параллельность

- Один план — одна ветка/worktree. Параллельно — только разные планы.
- Захватов юнитов в v1 нет. Если понадобится несколько worktree на один план —
  захваты в `$(git rev-parse --git-common-dir)/docflow/claims/`, решения по
  `Decisions` per-unit (общий хвост плана — гарантированный конфликт merge).
- `Depends`: по умолчанию — предыдущий юнит фазы; `-` — независим.
  Фаза N+1 ждёт фазу N, если не указано иное.
- Ветками docflow не управляет: создаёт и переключает их пользователь;
  `prompt` ветку не проверяет.

## Коммиты

- Один юнит — один коммит через `docflow commit`. Subject из `Commit:`
  (`Pxxx.N.M: <imperative 2–6 words>`), заготовлен при планировании.
- С `repos:` коммит юнита идёт по репо: сначала каждый вложенный репо с
  правками, потом корень, subject везде один; в тело корневого коммита —
  строки `Repo: <path> <sha>`. Первая строка вывода `commit` — sha корня.
  Сбой в репо посередине: уже сделанные вложенные коммиты остаются, корень
  не коммитится, ошибка называет репо; повтор `finish` после исправления
  пропускает `done` и коммитит оставшееся — [P016](../archive/P016-nested-repos-freeze.md).
  Журнал `<git-dir>/docflow/committing/<id>.json` создаётся в `done` и удаляется
  после корневого коммита. `status` показывает `commit pending` и не считает
  такой юнит завершённым; `next`, `prompt`, `run` и `close` не обходят его.
  При повторе `finish`/`run` сохраняются все строки `Repo:`, включая коммиты
  предыдущей попытки. Смена HEAD или новые правки в уже закоммиченном репо
  требуют ручного разбора. Восстанавливается и сбой между созданием коммита
  и записью журнала; старый незавершённый `[x]` определяется по отпечатку и HEAD.
- Коммиты уровня плана делает скилл обычным `git commit`, без
  `docflow commit`: `Pxxx: add plan`, `Pxxx: replan`, `Pxxx: close plan`,
  `Pxxx: add note` — [P002](../archive/P002-docflow-skills.md).
- Ослабление проверок видно: `commit` считает по индексу против `HEAD` пункты
  `<path>: -N lines` (тест-файл потерял строки), `<path>: deleted` (тест-файл
  удалён), `<path>: +skip` (добавлена строка со skip-маркером). Тест-файл — это
  имя (`*_test.go`, `test_*.py`, `*_test.py`, `*.test.*`, `*.spec.*`,
  `*Test.java`, `*Test.kt`, `*Tests.swift`, `*Test.swift`) или каталог пути
  (`test/`, `tests/`, `__tests__/`, `spec/`, `Tests/`, `androidTest/`). Без
  `HEAD` пунктов нет. Блок `Test changes:` из этих пунктов дописывается в тело
  коммита, а после всех строк вывода — по строке `test change: <пункт>`, для
  вложенного репо — `test change: <repo>/<пункт>`; первая строка вывода —
  `<sha> <subject>`, её раннер берёт как sha юнита. Сбой в репо посередине:
  пункты восстанавливаются по диффу уже сделанного коммита и сверяются с телом
  `pending commit`. Правки тестов не запрещены: они легитимны, и их видят
  ревью, приёмка и человек ([P050](../archive/P050-verify-guard.md)).
