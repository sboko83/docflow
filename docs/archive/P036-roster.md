## Outcome

Формат `docflow: 3`: цепочка маршрутов на роль — ключи `cheap:`, `heavy:`,
`review:`, `acceptance:` в шапке и `Role:` в юните, `replan:` — полная
цепочка, `docflow migrate` переводит 2 → 3. Личный ростер
`~/.config/docflow/roster.toml` подбирает цепочки ролей по порядку расхода
и ступеням моделей (`docflow roster show`, `docflow roster apply Pxxx`),
раннер ростер не читает; скилл планирования планирует с ростером и ставит
ревью после фаз провайдера с `check`. Не проверено: составление плана
холодным агентом по новому скиллу; сам репозиторий остаётся на
`docflow: 2` до выпуска.

## Decisions

- Роль юнита — поле `Role:`, цепочки — ключи ролей в шапке — `roster
  apply` переписывает только шапку, роль видна, а не угадывается —
  отвергнуто поле `Fallback:` в юните: роль выводилась бы по правилу, а
  ручной `Executor:` перезаписывался бы как heavy.
- `replan:` — полная цепочка без `fallback:`; migrate 2 → 3 дописывает
  маршруты `fallback:` в `replan:` незакрытых планов — по ростеру replan
  только `trusted`, старые планы сохраняют поведение — отвергнуто «replan,
  затем fallback»: при первом лимите replan уходил бы к недоверенному
  провайдеру.
- В цепочке роли один маршрут на провайдера — квота общая на подписку,
  второй маршрут того же провайдера после лимита упадёт так же —
  отвергнут перебор всех маршрутов по ступеням.
- У каждой роли не меньше двух маршрутов разных провайдеров; запас
  `trusted` — `strong` недоверенного провайдера без `check` — лимит
  единственного провайдера иначе останавливает прогон до сброса (RMG P010
  ждал z.ai до 00:38) — отвергнута цепочка только из `trusted`.
- `check` исключает провайдера из `review` при любом требовании роли,
  `trusted` включительно — юниты провайдера проверяет другой провайдер —
  отвергнуто исключение только в нетрастовой ветке подбора.
- Все шесть ролей обязаны иметь требование в `[role]`, пропуск — код 2 —
  `roster show` печатает каждую цепочку — отвергнуты необязательные роли
  с тихим пропуском.
- Профиль `[profile.<name>]` переопределяет только `spend` и флаги
  провайдеров; таблица флагов заменяет весь набор перечисленного
  провайдера — маршруты и требования ролей общие — отвергнуты отдельные
  файлы ростеров и слияние флагов по ключам.
- Профиль может сократить `spend`: маршруты сверяются с верхним `spend`,
  маршруты выпавшего провайдера подбор пропускает — иначе профиль не
  исключит провайдера (`save-claude`: claude уходит в запас) — отвергнута
  проверка маршрутов по эффективному `spend`.
- Неизвестный `--profile` — ошибка аргумента: код 2, путь ростера и список
  профилей, без строки — в файле нет строки, где ошибка — отвергнута
  синтетическая строка.
- Позиции ошибок ростера — отдельный сканер строк рядом с
  `agents.ParseTOML`, ошибки `spend` — строка ключа, нет позиции — строка
  1 — парсер возвращает карты без позиций — отвергнуто расширение парсера.
- Ревью — отдельный юнит после фазы, ревьюер не правит, дефект —
  `blocked` с `blocker: "plan"`, исправление планирует replan — отвергнута
  правка кода ревьюером.
- Отказ от авто-replan при ростере — в скилле: после `roster apply`
  строка `replan:` удаляется, если пользователь его не выбрал — apply
  печатает изменение `replan:` — отвергнут флаг `--no-replan`.
- `roster apply` не работает во время прогона (код 5 по
  `run/run.lock`) и проверяет план `lint.ActivationIssues` без маркера
  версии — план не меняется под идущим раннером, apply не зависит от
  формата проекта — отвергнут полный `lint` корня.
- Предупреждение о навыках (`PlanAgents`) охватывает агентов всех
  маршрутов цепочек юнитов и `replan:`; при сбое разбора цепочки остаётся
  основной маршрут — резервный маршрут без навыка упал бы в момент отказа
  основного — отвергнута проверка только первых маршрутов.
- Dry-run юнита с `Role:` показывает первый маршрут роли с источником
  `role <имя>`, юнит с ролью не наследует `executor:` — превью совпадает с
  маршрутом запуска.

## Gotchas

- `fallback:` — хвост роли executor, а не общий запас: юнит с `Role:` его
  не использует, юнит с `Executor:` или унаследованным `executor:` —
  использует.
- Ключ `trusted` в `[role]` — требование роли, не ступень маршрута: у
  маршрута `tier` только `cheap|standard|strong`.
- `roster apply` не смотрит маркер `docflow:`: на проекте формата 2 он
  запишет ключи ролей, а `lint` и `run` такого проекта потребуют
  `docflow migrate`.
- Тесты ростера изолируют `XDG_CONFIG_HOME`: без этого они читают личный
  ростер и зелёные только на машине автора. Общая фикстура —
  `internal/roster/testdata/draft.toml`, её читают `cmd/docflow` и
  `internal/runner` по относительному пути.
- Сканер строк не видит ключей инлайн-таблиц (`profile = { x = { … } }`):
  ошибка в них указывает на строку 1.

## Follow-ups

- Составить план холодным агентом по `bsv-docflow-plan`: удаляет ли он
  `replan:` после `roster apply`, ставит ли `Role: acceptance` и ревью
  после фаз провайдера с `check`.
- Перевести `docs/docflow.md` репозитория на `docflow: 3` после выпуска.
- База диффа фазы в `prompt` юнита ревью: сейчас `Do:` вычисляет её
  `git log --grep='^Pxxx\.N\.'`.
